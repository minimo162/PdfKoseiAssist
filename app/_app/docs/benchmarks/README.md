# ベンチマークとスコアリング（Phase 0）

修正計画書 §5 / §2.1 に対応する計測基盤。「指摘件数が増えた」ではなく、gold set
（埋め込んだ既知誤り）に対する recall / precision / review burden で効果を判定する。

## ファイル

| パス | 役割 |
|------|------|
| `score.mjs` | gold set と run 出力を突き合わせ、§2.1 の指標を算出（Node.js、依存なし） |
| `example/gold.json` | gold set スキーマの合成例（架空データ） |
| `example/run.json` | run 出力スキーマの合成例 |
| `runs/*.json` | 実測した run 出力（`fixtures/gold.json` と突き合わせる） |

## gold set の作り方（§5.1）

代表6パケット以上（文章中心／表中心／数値・日付／固有名詞／日本語REFあり／REFなし／
OCR低品質を含む）を用意し、実務上あり得る既知誤りを合計60件以上、6観点へ各8件以上、
ページ先頭・中央・末尾へ分散して埋め込む。実データを置けない場合は架空の会社名・数値で
同じレイアウトを再現する。元資料・埋め込み後資料・誤りID・ページ・観点・正解理由を
本ディレクトリで管理する。

### gold.json スキーマ

```json
{
  "packets": [
    { "packet_id": "P1",
      "planted": [
        { "id": "e1", "page": 7, "lens": "numbers", "quote": "12,345" }
      ] }
  ]
}
```

`lens` は `spelling|grammar|numbers|names|translation|structure` のいずれか。

### run.json スキーマ

各 run（v94 legacy / prompt減量版 / multipass版を各3回）の出力を、パケット単位に整形する。

```json
{
  "packets": [
    { "packet_id": "P1",
      "findings": [ { "page": 7, "quote": "12,345" } ],
      "uncertain_candidates": [ { "page": 8, "quote": "..." } ] }
  ]
}
```

## 合成フィクスチャ（誤りを埋め込んだ日英ペア）

実運用で渡している日英ペアは**人手校正を一通り終えた後**のもので、残存誤りがほぼ無い。
そのため recall（見つけるべき誤りをどれだけ拾えたか）が測れず、「指摘が少ない＝良い」のか
「見落とし」なのか区別がつかない。そこで、**同じ体裁で誤りを既知の位置に埋め込んだ**
合成文書を `fixtures/` に用意する。

| ファイル | 内容 |
|----------|------|
| `fixtures/aoi-seiki_ja_REF.pdf` | 日本語原文（**正**）27ページ |
| `fixtures/aoi-seiki_en_TARGET.pdf` | 英訳（誤り29件を埋め込み済み）26ページ |
| `fixtures/gold.json` | 正解セット（`score.mjs` 互換、`packet_id: "ALL"`） |
| `fixtures/gold.md` | 人が読む誤り一覧（TARGET頁／REF頁／観点／理由） |
| `fixtures/fixture-content.mjs` | 本文と埋め込み誤りの定義（唯一の情報源） |
| `fixtures/build-fixture.mjs` | HTML→PDF 生成と gold 出力（`node docs/benchmarks/fixtures/build-fixture.mjs`） |

架空企業「株式会社アオイ精機」の有価証券報告書抜粋。誤りは29件で、観点内訳は
translation 12 / numbers 9 / structure 4 / names 2 / spelling 1 / grammar 1。
埋め込みの狙いは**単ページでは原理的に取れない誤りを含めること**で、

- 跨ぎでしか出ない（配当 45 vs 54、自己資本比率 42.3 vs 42.8、営業利益 32,450 vs 31,450、
  従業員 3,214 vs 3,241、子会社名・役員名の表記揺れ、「減損なし」と注記「減損1,200」の矛盾）
- 会計連動でしか出ない（CF 三区分の合計が現金増減と合わない、セグメント内訳合計が総計と合わない）
- 日本語特有の省略を逐語訳した結果、英語で主語・目的語・指示対象が消えるもの（3件）
- 訳抜け（文・但し書きが丸ごと消えているもの、3件）

を意図的に混ぜてある。校正パケット（約10p）で取れるものと、整合性レビュー（セクション単位・
現物添付）でないと取れないものが gold.md で区別できる。

`build-fixture.mjs` は planted の `quote` が英語本文に実在するかを毎回検証し、
一致しなければ生成を中断する（gold が本文とずれるのを防ぐ）。日本語 p2 の【表紙】は
英訳版に無いため p3 以降は日英で1ページずれる。これは誤りではなく、ページ対応ズレの再現である。

## 実行

```bash
node docs/benchmarks/fixtures/build-fixture.mjs      # フィクスチャPDFとgoldを再生成
node docs/benchmarks/score.mjs docs/benchmarks/example/gold.json docs/benchmarks/example/run.json
# 位置ズレを許容する場合（±1ページ）:
node docs/benchmarks/score.mjs gold.json run.json --match-window 1
```

出力（§2.1 の指標）:

- `strict_planted_recall_pct` … `findings` のみ
- `assisted_planted_recall_pct` … `findings ∪ uncertain_candidates`
- `findings_precision_pct` / `candidate_precision_pct` / `combined_precision_pct`
- `review_burden` … packetあたり `uncertain_candidates` の avg / p90 / max
- `per_lens` … 観点別 recall

## マッチングの注意（§10.4）

`score.mjs` の突き合わせは「page一致＋正規化quoteの部分一致」による決定的な一次近似で
あり、人手ラベリングを置き換えるものではない。precision の最終判定は人が確認する。閾値
（§2.2）に対する合否は、複数runの中央値で評価し、データ量が不足する場合は理由を記録して
見直す。

## 実行時ログとの関係（§5.3）

`runtime/pass-stats.csv`（`POST /api/review/pass-stats` 経由、または将来のジョブ完了時追記）
に pass 単位の統計が残る。`score.mjs` は run 出力（findings/uncertain）を入力とするため、
CSV とは独立に再計算できる。両者を突き合わせることで incremental yield を観点別に追える。

これにより planted は 32件 → 29件。

## 3run の突き合わせ（2026-08-04）

観点passが実際に走った3回。3回目のみ P1-25、4・5回目は1セクション化後の P1-26。

| | 3回目 | 4回目 | 5回目 | 中央値 |
|---|---|---|---|---|
| recall（実質） | 26/29 = 90% | 24/29 = 83% | 24/29 = 83% | **24/29 = 83%** |
| precision | 96% | 96% | 96% | **96%** |
| 生の指摘 | 29 | 47 | 43 | — |
| カード（dedupe後） | 29 | 26 | 31 | — |
| pass別 | 20/4/3/**3** | 20/4/3/**20** | 18/4/3/**18** | — |
| 所要 | 101.4秒 | 94.2秒 | 77.2秒 | — |

`e18`（綴り）と `e32`（文法）は設計上 consistency の担当外なので、
**担当範囲だけで見れば 24/27 = 89%**。

### 揺れではなく傾向だったもの: 注記の見落とし

`e05`（P.4 の（注）2「臨時従業員は含まれていない」の訳抜け）と
`e23`（P.18 の（注）「自己資本」を Net assets と訳して自己参照化）は、
**3回目だけ検出、4・5回目は連続で未検出**。どちらも **注記（(注)行）** である点が共通する。
broad は本文と表の数値に注意が向き、wording / ellipsis は散文を見るため、
注記の小さい文字が3passとも手薄になる。

3回目で取れたのは gap pass が3件出したときで、4・5回目の gap は18〜20件すべて既出の再掲だった。
**gap の新規歩留まりが 3件 → 0件 → 0件** と落ちており、注記の穴と gap の失速が連動している。

対策として gap の追撃文を次のように変えた（効果は次回以降のrunで測る）:

- 既出一覧を「**報告禁止**リスト」として提示し、出力前に page/quote の重複を1件ずつ自己点検させる
- 本文・表の数値は見終わっている前提を明示し、**注記・脚注・(注)行・表の但し書き・単位の説明**を名指しで指示
- 0件が正しい答えになりうると明示（無理に絞り出させない）

### 引用の切り取り幅違いによる重複（5組）

### 各passの寄与（run間の差分から特定）

broad のみ → 4pass で増えた6件は **すべて translation 系**:

| pass | 拾った gold |
|------|------------|
| wording | `e08`（連結子会社の誤訳）/ `e09`（revenue↔net sales）/ `e23`（自己資本→Net assets） |

**削れる候補は gap だけ**である。gap が単独で拾う `e05` / `e23` は、
パケット側の broad も検出しているため、**併用時には冗長になりうる**（6ターン構成）。

ただし現時点では推奨しない。理由は3つ:

1. パケット broad が `e05`/`e23` を拾ったのは**1 run の観測のみ**。冗長性の根拠として薄い。
2. gap は「他のpassが取りこぼしたものを探す」唯一の**汎用の網**で、
   フィクスチャと性格の違う実文書ほど効く可能性がある。
3. 7ターン中の1ターンでしかない。

`wording`（2件）と `ellipsis`（1件）は、**他のどのpassも拾わない gold** を持つため削れない。

**整合性 4pass + パケット broad 1pass × N = 現行の推奨構成**。
26ページなら合計7ターン。これ以上削るなら gap（→6ターン）だが、
効果を確かめてからにすべきで、削っても 27/30 が保たれるかは実測が要る。

| 併用 | 合計ターン | recall |
|------|-----------|--------|
| **整合性 + complement** | **7** | **27/30** |
| 整合性 + thorough | 34 | 28/30 |

**予測は3点とも当たった。**

1. complement が整合性へ上乗せしたのは **`e18`（綴り）と `e32`（主述不一致）ちょうど2件**。
   狙いどおり「整合性が原理的に取れない層」だけを埋めている。
2. thorough の27ターン増しは、やはり **`e33` 1件**しか追加しない。
3. **誤検知がゼロになった。** thorough で出ていた3件
   （`owners of parent` → `owners of the parent` ×2、`net selling price` → `net selling value`）は
   すべて grammar / translation pass 由来で、それらを外したことで消えた。
   **観点passを削ったことが recall だけでなく precision も改善している。**

### 確定した推奨構成

```json
"review_engine": "multipass",
"review_profile_batch": "complement",
"review_profile_single": "complement",
"review_gap_pass": true
```

- 整合性レビュー: `broad → wording → ellipsis → gap`（4ターン）
- 校正パケット: `broad` のみ（1ターン × パケット数）
- 26ページなら **合計7ターン**、**recall 27/30 = 90%**、**誤検知ゼロ**

## e07（持分法適用関連会社の誤訳）は意図的に保留（2026-08-04 判断）

`e07`（`3 equity-method subsidiaries` — 正しくは associates）は、
**全構成・全runで一度も検出されていない唯一の gold** である。これを追わないと決めた。

### 理由: 追うと precision を落とす

thorough で実際に出た誤検知3件は、いずれも**会計用語の標準訳を「誤り」と指摘する過剰修正**だった。

| 出た誤検知 | 実際は |
|---|---|
| `owners of parent` → `owners of the parent`（2件） | 会計基準の標準英訳は定冠詞なし |
| `net selling price` → `net selling value` | 「正味売却価額」の標準訳は net selling price |

`e07` は「`equity-method subsidiaries` ではなく `associates`」という**会計用語の使い分けそのもの**の指摘である。
これを拾わせるには「会計用語の訳語が規範どおりか」を疑う圧力をかける必要があり、
上と同じ種類の誤検知を増やす方向に働く。

**1件の recall のために precision を落とす取引は割に合わない。**
実務では「正しい英語・正しい会計用語を直せ」と言ってくる指摘が最も信頼を損なう。

### 扱い

- gold から**削除しない**。削ると recall が実態より良く見えるため、`e07` は**天井として残す**。
- したがって現行構成の上限は **29/30**（`e07` を除く）で、実測 27/30 はその94%にあたる。
- `gold.md` の e07 行に保留の旨を明記した。

### 再開する場合の条件

会計用語の対訳表（社内の用語集など）を外部データとして与えられるようになったとき。
モデルの知識に判断させるのではなく、**照合表との突き合わせ**にできれば誤検知のリスクなく拾える。
それまでは追わない。

## ページ幅を決めるための長尺フィクスチャ（2026-08-04 追加）

### なぜ26ページ版では答えられないか

26ページのフィクスチャは、末尾セクションの畳み込みにより**幅を何にしても1セクション**になる。
文書全体が常に1回で入るので、幅を変えても結果が変わらない。校正パケット側も
3パケット（10/10/6）に固定で、幅の効果と分割数の効果が分離できない。

### 何を測る文書か

| ファイル | 内容 |
|----------|------|
| `fixtures/aoi-long_ja_REF.pdf` | 日本語原文（**正**）140ページ |
| `fixtures/aoi-long_en_TARGET.pdf` | 英訳（誤り61件を埋め込み済み）139ページ |
| `fixtures/gold-long.json` | 正解セット（`distance` / `kind` / `alt` 付き） |
| `fixtures/gold-long.md` | 人が読む誤り一覧と、幅ごとの検出可能性の予測 |
| `fixtures/long-fixture-content.mjs` | 本文と埋め込み誤りの定義（唯一の情報源） |
| `fixtures/build-long-fixture.mjs` | 生成と自己検証 |
| `tools/Test-LongFixture.mjs` | 生成物どうしの突き合わせ（gold と本文のずれ検出） |

埋め込みは合計61件。

必要なのは2つで、要求が正反対である。

**A 翻訳校正**（REF が正。逐語ではなく言語差を踏まえる）… 1文ずつ突き合わせる。狭い窓が要る。
**B 整合性**（原文と訳文がセットで誤りうる）… 離れた2箇所を同時に見る。広い窓が要る。

1本にまとめると窓幅を1つに決めることになり、必ずどちらかを捨てる。これが2本立ての理由である。

| 種類 | 件数 | 属する | 役割 |
|------|------|------|------|
| num-tr（数値の誤訳） | 6 | A | 桁・単位・スケール・年・符号・％ |
| name-tr（固有名詞・日付） | 4 | A | 社名・県名・部署名・日付 |
| supply（補完不足） | 4 | A | 日本語が省いた主語を補えていない逐語訳 |
| over（補い過ぎ） | 2 | A | 原文にない情報を足している |
| omission（訳抜け） | 7 | A | 文がまるごと落ちている |
| spelling / grammar | 8 / 8 | A | 英語単体の誤り（REFと無関係） |
| **drift**（訳語の揺れ） | 16 | B | 距離の計器。距離 3/10/20/40/60/80/100/120 × 各2件 |
| **number**（数値の食い違い） | 3 | B | 距離の計器。距離 5/30/90。**原文と英訳の両方**に食い違いがある |
| accounting（会計連動） | 2 | B | 内訳の合計が別ページの総計と合わない |
| number-local（対照群） | 1 | — | 距離20。EN のみ誤りで、ローカルでも気づける |

### drift が距離の計器として成立している理由

同じ日本語の用語（例「工程内検査」）が離れた2ページに出て、英訳が
`in-process inspection` と `in-line inspection` に食い違っている。
**どちらの訳語も単独では正しく読める**ので、片方のページだけを見ても、
そのページの REF と突き合わせても、誤りにならない。2ページを同時に見て初めて分かる。

生成時に次を機械検証しており、破れたら生成が止まる。

- 日本語用語が文書全体でちょうど2回（anchor と error だけ）出ること
  → より近い別ページで気づけてしまうと実効距離が縮み、実験が壊れる
- 2つの英訳語がそれぞれ1回だけ出ること
- すべての引用が文書全体で一意であること（ページ単位の採点が成立する条件）
- 埋め込み先のページが重複していないこと（1ページ1件）
- `.page` が印刷1ページに収まり、PDF の総ページ数が想定と一致すること
  → ずれると gold のページ番号が全部無効になる

### number も距離の計器にする — 原文と英訳の両方を間違えておく

数値のほうは当初「REF は数値を繰り返さず、英訳だけが誤った数値を書く」形にしていたが、
これは**ローカルでも「原文にない数値が足されている」と指摘できてしまう**。距離の計器にならない。

そこで **原文と英訳の両方に同じ食い違いを入れた**。
先行ページは日英とも 17,400、後続ページは日英とも 17,900。
そのページだけを見れば**日英は完全に一致している**ので、REF との突き合わせでは何も出ない。
文書自身が2箇所で違うことを言っている、という跨ぎの矛盾だけが残る。
実務でも「原文の数値が古いまま残り、翻訳者は忠実に訳した」という形で普通に起きる。

> この3件だけは「REFは正」の前提から外れる。整合性レビューのプロンプトは
> A: TARGET内部の跨ぎ整合 / B: REFとの照合 の二本立てで、これは **A の担当**である。
> どちらのページが正しいかは原理的に決まらないが、採点は「矛盾を指摘したか」だけを見るので支障はない。

対照群として、旧来の形（EN のみ誤り・距離20）を1件だけ残してある。
**対照が取れて本体が取れないなら、モデルは跨ぎを見ておらずローカルなREF比較しかしていない**
と分かる。この切り分けができるようにするための1件である。

### 跨ぎ指摘はどちらのページで報告してもよい

26ページ版の `e14` で、Copilot が相手方のページを主たる箇所として報告したために
`score.mjs` が取りこぼす問題があった。長尺版では planted に `alt`（相手方の page/quote）を持たせ、
どちらで報告されても検出とみなすようにした。`score.mjs` 側も対応済み。

#### 5. 採点

`Run-Benchmark.ps1` を使ったなら `docs/benchmarks/runs/raw/<日付>_<構成>.json` が
すでに指摘.json と同じ内容なので、そのまま変換できる。
手で走らせたなら「ZIPを保存」→ 展開 → **`指摘.json`** を使う（画面から書き写す必要はない）。

```bash
node docs/benchmarks/report-to-run.mjs docs/benchmarks/runs/raw/2026-08-05_consistency25.json \
     --out docs/benchmarks/runs/2026-08-05_consistency_w25.json --note "整合性 幅25・重ね3"
```

そのうえで採点する。

```bash
node docs/benchmarks/score.mjs docs/benchmarks/fixtures/gold-long.json \
     docs/benchmarks/runs/<run>.json --reachable 25 --by kind,distance
```

`per_distance` が距離別 recall、`per_kind` が種類別 recall、`missed_ids` が未検出の一覧。

`--reachable <幅>` は**幅を変えた run どうしを比べるときに必須**である。
跨ぎのペアは両ページが同じセクションに入らないと取りようがないので、
これを外すと「幅を広げたら悪くなった」のか「そもそも届いていなかった」のか区別できない。
`gold-long.md` の表のとおり、到達可能な件数は**幅に対して単調ではない**
（境界がどこに落ちるかで、距離の短いペアでも分断される）。素の recall を幅どうしで比べてはいけない。

### 追撃passは費用に見合っているか（2026-08-04 の実測）

139ページ・幅25・重ね3 の run（5セクション成功、1セクションは失敗）から:

| | 指摘 | 所要 |
|---|---|---|
| broad（1ターン目） | 111件 | 557秒 |
| 追撃3pass（訳語の揺れ・省略・見落とし探し） | 12件 | 581秒 |

**追撃は時間の51%を使って指摘の9.8%しか出していない**（訳語の揺れ2件 / 省略6件 / 見落とし4件）。
139ページに19分かかる内訳がこれである。

ただし件数は歩留まりであって recall ではない。追撃の12件が
「broad が取り逃した跨ぎのペア」なら価値は件数以上になる。
`--by kind` で採点して初めて判断できる。**採点前に追撃を消してはいけない。**

そこで統合1ターン構成（`combined`）を用意した。追撃で聞いていた観点を
broad のプロンプトへ畳み込み、passは1本にする。

- 幅25なら 6ターン（約9分）、幅40なら 4ターン
- 「注記・脚注・(注)行・表の但し書き・単位の説明を最後に必ず一巡する」も
  プロンプトへ入れた（見落とし探しpassが担っていた役割）
- `combined: true` と `profile: "consistency1"` は**必ず両方**指定する。
  片方だけだと「1ターンなのに観点の指示が無い」か「指示はあるのに4ターン走る」になる

### 実測（2026-08-04・gold 61件）

| | ターン | recall | precision | 所要 |
|---|---|---|---|---|
| 統合1ターン 幅25 | 6 | 53.2%（到達可能47件） | **100%** | 5分 |
| 統合1ターン 幅50 | 3 | 49.0%（到達可能49件） | 78.1%※ | 5分 |
| 統合1ターン 幅100 | — | 添付が60秒以内に完了せず失敗（**原因未確定**） | — | — |
| 校正 幅10 | — | Copilotページの取り違えで失敗 | — | — |

※幅50の誤検知6件はフィクスチャ側の不備（事業別の売上高比率がセグメント売上高と
　整合していなかった）。修正済みなので、次回はもっと高く出るはず。

観点別（strict recall）:

| 観点 | 幅25 | 幅50 |
|------|------|------|
| num-tr 数値の誤訳 | **100%** (6/6) | **100%** (6/6) |
| name-tr 固有名詞・日付 | **100%** (4/4) | **100%** (4/4) |
| omission 訳抜け | **100%** (7/7) | **100%** (7/7) |
| over 補い過ぎ | **100%** (2/2) | 50% |
| supply 補完不足 | **100%** (4/4) | **25%** |
| spelling 綴り | 12.5% | 12.5% |
| grammar 文法 | **0%** | **0%** |
| drift 訳語の揺れ | 20% | 16.7% |

分かったこと。

1. **A（翻訳校正）のうち A1〜A3 は幅25でほぼ完璧に取れる。**
   数値の誤訳（桁・単位・スケール・年・符号・％）を6件すべて、
   固有名詞・日付を4件すべて、訳抜けを7件すべて拾った。実務の第一関心はここで満たせる。
2. **A4（英語単体の綴り・文法）は整合性モードでは取れない。** 綴り12.5%、文法0%。
   プロンプトが「REFと突き合わせて」と指示する限り、モデルは意味の差しか見ない。
   幅の問題ではなく役割の問題であり、校正パケット（10p）が別に要る。
3. **幅を25→50に広げると、繊細な観点から先に落ちる。** supply が 100%→25%。
   数値や固有名詞のような「照合すれば分かる」観点は幅50でも落ちない。
   **広げてよいのは照合系だけ**で、読解が要る観点は幅に敏感である。
4. **B（跨ぎ整合）は幅を変えても20%前後で低い。** 幅を広げれば届く、という単純な話ではない。

幅100の失敗は原因が確定していない。この run は可視判定の修正より前のビルドであり、
かつ添付の待ち時間が60秒固定だった（0.3MBの幅25と1MB超の幅100を同じ物差しで測っていた）。
「100ページは添付の限界」と結論づけるには根拠が足りない。
待ち時間を中身の大きさに追随させ、ログに totalMB と waitSec を残すようにしたので、
次に失敗したときは「大きくて遅い」のか「検出できていない」のかを切り分けられる。

### 結果の読み方

- **Q1（整合性は何ページ幅か）** … `per_distance` が 100% から落ちる距離が、その幅の実力。
  幅 W なら距離 W 未満のペアしか同一セクションに入らないので、
  「理論上の上限」は `gold-long.md` の表にある。実測がそれをどれだけ下回るかを見る。
  幅を広げても距離の長いペアが取れないなら、**広げること自体に意味がない**。
- **Q2（校正は何ページ幅か）** … `per_kind` の spelling / grammar / omission。
  幅10と幅25で落ちるなら「各行精読は幅に効く」が裏づけられ、
  落ちないなら**パケットを大きくしてターン数を減らせる**。
- **Q3（分ける必要があるか）** … 1本の run で drift と行レベルの両方が取れる幅があるなら、
  分ける必要はない。26ページ版の実測では
  「26p一括では綴り・文法が落ち、10p分割では跨ぎが取れない」という相補性が出ていたが、
  それが**幅の連続的な効果**なのか**2つの別物**なのかは、この文書でないと分からない。

### 予測（実測前に書いておく）

外すかもしれないが、書いておかないと後付けの解釈になる。

1. drift は幅25で距離20まで、幅60で距離40〜60まで取れる。ただし幅60では
   **距離の短いペアの取りこぼしが増える**（見る量が増えて注意が薄まる）。
2. 行レベルは幅10 > 幅25。特に spelling が幅25で落ちる。
3. したがって Q3 の答えは「分ける必要がある」。ただし整合性側の最適幅は
   現行の25より広い可能性がある（139ページを幅25で切ると6セクション＝24ターンで、
   幅60なら12ターンで済む。距離40以下が取れるなら幅60のほうが有利）。
4. 対照群 `n020x`（EN のみ誤り）は幅によらず取れる。これが取れて `n005`（距離5・原文と英訳の
   両方が食い違う）が取れないなら、モデルは**ページ内のREF比較しかしておらず跨ぎを見ていない**。
   その場合、幅を広げること自体が効かないので、プロンプト側の作り直しが先になる。
