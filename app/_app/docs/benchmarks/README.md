# ベンチマークとスコアリング（Phase 0）

修正計画書 §5 / §2.1 に対応する計測基盤。「指摘件数が増えた」ではなく、gold set
（埋め込んだ既知誤り）に対する recall / precision / review burden で効果を判定する。

## ファイル

| パス | 役割 |
|------|------|
| `score.mjs` | gold set と run 出力を突き合わせ、§2.1 の指標を算出（Node.js、依存なし） |
| `score-runs.mjs` | 生の指摘JSONを構成ごとに正しい分母（幅・担当範囲）で採点し、距離別に並べる |
| `example/gold.json` | gold set スキーマの合成例（架空データ） |
| `example/run.json` | run 出力スキーマの合成例 |
| `runs/*.json` | 実測した run 出力（`fixtures/gold.json` と突き合わせる） |

## gold set の作り方（§5.1）

代表6パケット以上（文章中心／表中心／数値・日付／固有名詞／日本語REFあり／REFなし／
OCR低品質を含む）を用意し、実務上あり得る既知誤りを合計60件以上、6観点へ各8件以上、
ページ先頭・中央・末尾へ分散して埋め込む。実データを置けない場合は架空の会社名・数値で
同じレイアウトを再現する。元資料・埋め込み後資料・誤りID・ページ・観点・正解理由を
本ディレクトリで管理する。

### gold.json スキーマ

```json
{
  "packets": [
    { "packet_id": "P1",
      "planted": [
        { "id": "e1", "page": 7, "lens": "numbers", "quote": "12,345" }
      ] }
  ]
}
```

`lens` は `spelling|grammar|numbers|names|translation|structure` のいずれか。

### run.json スキーマ

各 run（v94 legacy / prompt減量版 / multipass版を各3回）の出力を、パケット単位に整形する。

```json
{
  "packets": [
    { "packet_id": "P1",
      "findings": [ { "page": 7, "quote": "12,345" } ],
      "uncertain_candidates": [ { "page": 8, "quote": "..." } ] }
  ]
}
```

## 合成フィクスチャ（誤りを埋め込んだ日英ペア）

実運用で渡している日英ペアは**人手校正を一通り終えた後**のもので、残存誤りがほぼ無い。
そのため recall（見つけるべき誤りをどれだけ拾えたか）が測れず、「指摘が少ない＝良い」のか
「見落とし」なのか区別がつかない。そこで、**同じ体裁で誤りを既知の位置に埋め込んだ**
合成文書を `fixtures/` に用意する。

| ファイル | 内容 |
|----------|------|
| `fixtures/aoi-seiki_ja_REF.pdf` | 日本語原文（**正**）27ページ |
| `fixtures/aoi-seiki_en_TARGET.pdf` | 英訳（誤り29件を埋め込み済み）26ページ |
| `fixtures/gold.json` | 正解セット（`score.mjs` 互換、`packet_id: "ALL"`） |
| `fixtures/gold.md` | 人が読む誤り一覧（TARGET頁／REF頁／観点／理由） |
| `fixtures/fixture-content.mjs` | 本文と埋め込み誤りの定義（唯一の情報源） |
| `fixtures/build-fixture.mjs` | HTML→PDF 生成と gold 出力（`node docs/benchmarks/fixtures/build-fixture.mjs`） |

架空企業「株式会社アオイ精機」の有価証券報告書抜粋。誤りは29件で、観点内訳は
translation 12 / numbers 9 / structure 4 / names 2 / spelling 1 / grammar 1。
埋め込みの狙いは**単ページでは原理的に取れない誤りを含めること**で、

- 跨ぎでしか出ない（配当 45 vs 54、自己資本比率 42.3 vs 42.8、営業利益 32,450 vs 31,450、
  従業員 3,214 vs 3,241、子会社名・役員名の表記揺れ、「減損なし」と注記「減損1,200」の矛盾）
- 会計連動でしか出ない（CF 三区分の合計が現金増減と合わない、セグメント内訳合計が総計と合わない）
- 日本語特有の省略を逐語訳した結果、英語で主語・目的語・指示対象が消えるもの（3件）
- 訳抜け（文・但し書きが丸ごと消えているもの、3件）

を意図的に混ぜてある。校正パケット（約10p）で取れるものと、整合性レビュー（セクション単位・
現物添付）でないと取れないものが gold.md で区別できる。

`build-fixture.mjs` は planted の `quote` が英語本文に実在するかを毎回検証し、
一致しなければ生成を中断する（gold が本文とずれるのを防ぐ）。日本語 p2 の【表紙】は
英訳版に無いため p3 以降は日英で1ページずれる。これは誤りではなく、ページ対応ズレの再現である。

## 実行

```bash
node docs/benchmarks/fixtures/build-fixture.mjs      # フィクスチャPDFとgoldを再生成
node docs/benchmarks/score.mjs docs/benchmarks/example/gold.json docs/benchmarks/example/run.json
# 位置ズレを許容する場合（±1ページ）:
node docs/benchmarks/score.mjs gold.json run.json --match-window 1
```

出力（§2.1 の指標）:

- `strict_planted_recall_pct` … `findings` のみ
- `assisted_planted_recall_pct` … `findings ∪ uncertain_candidates`
- `findings_precision_pct` / `candidate_precision_pct` / `combined_precision_pct`
- `review_burden` … packetあたり `uncertain_candidates` の avg / p90 / max
- `per_lens` … 観点別 recall

## マッチングの注意（§10.4）

`score.mjs` の突き合わせは「page一致＋正規化quoteの部分一致」による決定的な一次近似で
あり、人手ラベリングを置き換えるものではない。precision の最終判定は人が確認する。閾値
（§2.2）に対する合否は、複数runの中央値で評価し、データ量が不足する場合は理由を記録して
見直す。

## 実行時ログとの関係（§5.3）

`runtime/pass-stats.csv`（`POST /api/review/pass-stats` 経由、または将来のジョブ完了時追記）
に pass 単位の統計が残る。`score.mjs` は run 出力（findings/uncertain）を入力とするため、
CSV とは独立に再計算できる。両者を突き合わせることで incremental yield を観点別に追える。

### この実測で見つかった gold 自体の欠陥（修正済み）

- 「正しい側」を planted に挙げていた2件（旧 e02 / 旧 e21）を削除。誤りは対になる e09 / e04 の側。

これにより planted は 32件 → 29件。

## 3run の突き合わせ（2026-08-04）

観点passが実際に走った3回。3回目のみ P1-25、4・5回目は1セクション化後の P1-26。

| | 3回目 | 4回目 | 5回目 | 中央値 |
|---|---|---|---|---|
| recall（実質） | 26/29 = 90% | 24/29 = 83% | 24/29 = 83% | **24/29 = 83%** |
| precision | 96% | 96% | 96% | **96%** |
| 生の指摘 | 29 | 47 | 43 | — |
| カード（dedupe後） | 29 | 26 | 31 | — |
| pass別 | 20/4/3/**3** | 20/4/3/**20** | 18/4/3/**18** | — |
| 所要 | 101.4秒 | 94.2秒 | 77.2秒 | — |

`e18`（綴り）と `e32`（文法）は設計上 consistency の担当外なので、
**担当範囲だけで見れば 24/27 = 89%**。

### 揺れではなく傾向だったもの: 注記の見落とし

`e05`（P.4 の（注）2「臨時従業員は含まれていない」の訳抜け）と
`e23`（P.18 の（注）「自己資本」を Net assets と訳して自己参照化）は、
**3回目だけ検出、4・5回目は連続で未検出**。どちらも **注記（(注)行）** である点が共通する。
broad は本文と表の数値に注意が向き、wording / ellipsis は散文を見るため、
注記の小さい文字が3passとも手薄になる。

3回目で取れたのは gap pass が3件出したときで、4・5回目の gap は18〜20件すべて既出の再掲だった。
**gap の新規歩留まりが 3件 → 0件 → 0件** と落ちており、注記の穴と gap の失速が連動している。

対策として gap の追撃文を次のように変えた（効果は次回以降のrunで測る）:

- 既出一覧を「**報告禁止**リスト」として提示し、出力前に page/quote の重複を1件ずつ自己点検させる
- 本文・表の数値は見終わっている前提を明示し、**注記・脚注・(注)行・表の但し書き・単位の説明**を名指しで指示

## 整合性側も削れるか（2026-08-04 / 検証結果: 削れない）

|------|-------|--------|
| 整合性 broadのみ | 1 | 18〜19/30 |
| **整合性 4pass** | 4 | **25/30** |
| パケット broadのみ（3パケット） | 3 | 21/30 |

### 併用（これが判断材料）

| 構成 | 合計ターン | recall |
|------|-----------|--------|
| 整合性broad + パケットbroad | 4 | 24/30 |
| **整合性4pass + パケットbroad** | **7** | **27/30** |

### 費用対効果はパケット側と27倍違う

| 追加した pass | 追加ターン | 併用時の上乗せ | 1ターンあたり |
|--------------|-----------|--------------|-------------|
| 整合性 wording+ellipsis+gap | +3 | **+3件**（e08 / e09 / e19） | **1.000件** |
| パケット thorough の9pass | +27 | +1件（e33） | 0.037件 |

パケット側は「broadで足りる」が成り立ったが、**整合性側は3ターンで3件、
つまり1ターン1件のペース**で拾っている。同じ論理は適用できない。

### 各passの寄与（run間の差分から特定）

broad のみ → 4pass で増えた6件は **すべて translation 系**:

| pass | 拾った gold |
|------|------------|
| wording | `e08`（連結子会社の誤訳）/ `e09`（revenue↔net sales）/ `e23`（自己資本→Net assets） |
| ellipsis | `e11`（主語欠落）/ `e12`（主語・目的語欠落）/ `e19`（「当該」の脱落） |
| gap | `e05`（（注）2 訳抜け）/ `e23` を回収（run5→run6 の差分。この間の変更は gap 追撃文のみ） |

**削れる候補は gap だけ**である。gap が単独で拾う `e05` / `e23` は、
パケット側の broad も検出しているため、**併用時には冗長になりうる**（6ターン構成）。

ただし現時点では推奨しない。理由は3つ:

1. パケット broad が `e05`/`e23` を拾ったのは**1 run の観測のみ**。冗長性の根拠として薄い。
2. gap は「他のpassが取りこぼしたものを探す」唯一の**汎用の網**で、
   フィクスチャと性格の違う実文書ほど効く可能性がある。
3. 7ターン中の1ターンでしかない。

`wording`（2件）と `ellipsis`（1件）は、**他のどのpassも拾わない gold** を持つため削れない。

### 結論

**整合性 4pass + パケット broad 1pass × N = 現行の推奨構成**。
26ページなら合計7ターン。これ以上削るなら gap（→6ターン）だが、
効果を確かめてからにすべきで、削っても 27/30 が保たれるかは実測が要る。

## e07（持分法適用関連会社の誤訳）は意図的に保留（2026-08-04 判断）

`e07`（`3 equity-method subsidiaries` — 正しくは associates）は、
**全構成・全runで一度も検出されていない唯一の gold** である。これを追わないと決めた。

### 理由: 追うと precision を落とす

thorough で実際に出た誤検知3件は、いずれも**会計用語の標準訳を「誤り」と指摘する過剰修正**だった。

| 出た誤検知 | 実際は |
|---|---|
| `owners of parent` → `owners of the parent`（2件） | 会計基準の標準英訳は定冠詞なし |
| `net selling price` → `net selling value` | 「正味売却価額」の標準訳は net selling price |

`e07` は「`equity-method subsidiaries` ではなく `associates`」という**会計用語の使い分けそのもの**の指摘である。
これを拾わせるには「会計用語の訳語が規範どおりか」を疑う圧力をかける必要があり、
上と同じ種類の誤検知を増やす方向に働く。

**1件の recall のために precision を落とす取引は割に合わない。**
実務では「正しい英語・正しい会計用語を直せ」と言ってくる指摘が最も信頼を損なう。

### 扱い

- gold から**削除しない**。削ると recall が実態より良く見えるため、`e07` は**天井として残す**。
- したがって現行構成の上限は **29/30**（`e07` を除く）で、実測 27/30 はその94%にあたる。
- `gold.md` の e07 行に保留の旨を明記した。

### 再開する場合の条件

会計用語の対訳表（社内の用語集など）を外部データとして与えられるようになったとき。
モデルの知識に判断させるのではなく、**照合表との突き合わせ**にできれば誤検知のリスクなく拾える。
それまでは追わない。

## ページ幅を決めるための長尺フィクスチャ（2026-08-04 追加）

### なぜ26ページ版では答えられないか

26ページのフィクスチャは、末尾セクションの畳み込みにより**幅を何にしても1セクション**になる。
文書全体が常に1回で入るので、幅を変えても結果が変わらない。校正パケット側も
3パケット（10/10/6）に固定で、幅の効果と分割数の効果が分離できない。

### 何を測る文書か

| ファイル | 内容 |
|----------|------|
| `fixtures/aoi-long_ja_REF.pdf` | 日本語原文（**正**）201ページ |
| `fixtures/aoi-long_en_TARGET.pdf` | 英訳（誤り112件を埋め込み済み）200ページ |
| `fixtures/gold-long.json` | 正解セット（`distance` / `kind` / `alt` 付き） |
| `fixtures/gold-long.md` | 人が読む誤り一覧と、幅ごとの検出可能性の予測 |
| `fixtures/long-fixture-content.mjs` | 本文と埋め込み誤りの定義（唯一の情報源） |
| `fixtures/build-long-fixture.mjs` | 生成と自己検証 |
| `tools/Test-LongFixture.mjs` | 生成物どうしの突き合わせ（gold と本文のずれ検出） |
| `tools/Test-FixtureTextLayer.mjs` | PDFの**抽出テキスト**の検査（gold との一致・マスカーを通せるか） |

埋め込みは合計112件。

> ⚠️ **2026-08-05 より前の長尺runの数字は 139ページ・gold 61件版**のものである。
> 跨ぎ数値の計器を作り直した際に 200ページ・gold 102件へ増補した（最終節）。
> 既存 planted のIDとページ番号は動かしていないが、セクションの切れ方は変わるので、
> **幅に関する数字は取り直しが要る**。

必要なのは2つで、要求が正反対である。

**A 翻訳校正**（REF が正。逐語ではなく言語差を踏まえる）… 1文ずつ突き合わせる。狭い窓が要る。
**B 整合性**（原文と訳文がセットで誤りうる）… 離れた2箇所を同時に見る。広い窓が要る。

1本にまとめると窓幅を1つに決めることになり、必ずどちらかを捨てる。これが2本立ての理由である。

| 種類 | 件数 | 属する | 役割 |
|------|------|------|------|
| num-tr（数値の誤訳） | 8 | A | 桁・単位・スケール・年・符号・％ |
| name-tr（固有名詞・日付） | 5 | A | 社名・県名・部署名・日付 |
| supply（補完不足） | 5 | A | 日本語が省いた主語を補えていない逐語訳 |
| over（補い過ぎ） | 3 | A | 原文にない情報を足している |
| omission（訳抜け） | 11 | A | 文がまるごと落ちている |
| spelling / grammar | 11 / 11 | A | 英語単体の誤り（REFと無関係） |
| **term**（形式の揺れ） | 24 | B | 距離の計器。距離 5/15/30/50/70/90/110/130 × 各3件。固有名詞・制度名の表記が2箇所で違う |
| **number**（数値の食い違い） | 24 | B | 距離の計器。同上の8距離 × 各3件。**原文と英訳の両方**に食い違いがある |
| drift（訳語の揺れ・対照群） | 8 | B | 距離 3/10/20/40/60/80/100/120 × 各1件。**REFが無いと原理的に判定できない層** |
| number-local（対照群） | 2 | — | 距離20/75。EN のみ誤りで、ローカルでも気づける |

### drift が距離の計器として成立している理由

同じ日本語の用語（例「工程内検査」）が離れた2ページに出て、英訳が
`in-process inspection` と `in-line inspection` に食い違っている。
**どちらの訳語も単独では正しく読める**ので、片方のページだけを見ても、
そのページの REF と突き合わせても、誤りにならない。2ページを同時に見て初めて分かる。

生成時に次を機械検証しており、破れたら生成が止まる。

- 日本語用語が文書全体でちょうど2回（anchor と error だけ）出ること
  → より近い別ページで気づけてしまうと実効距離が縮み、実験が壊れる
- 2つの英訳語がそれぞれ1回だけ出ること
- すべての引用が文書全体で一意であること（ページ単位の採点が成立する条件）
- 埋め込み先のページが重複していないこと（1ページ1件）
- `.page` が印刷1ページに収まり、PDF の総ページ数が想定と一致すること
  → ずれると gold のページ番号が全部無効になる

### number も距離の計器にする — 原文と英訳の両方を間違えておく

数値のほうは当初「REF は数値を繰り返さず、英訳だけが誤った数値を書く」形にしていたが、
これは**ローカルでも「原文にない数値が足されている」と指摘できてしまう**。距離の計器にならない。

そこで **原文と英訳の両方に同じ食い違いを入れた**。
先行ページは日英とも 17,400、後続ページは日英とも 17,900。
そのページだけを見れば**日英は完全に一致している**ので、REF との突き合わせでは何も出ない。
文書自身が2箇所で違うことを言っている、という跨ぎの矛盾だけが残る。
実務でも「原文の数値が古いまま残り、翻訳者は忠実に訳した」という形で普通に起きる。

> `number` と `number-local` は「REFは正」の前提から外れる。整合性レビューのプロンプトは
> A: TARGET内部の跨ぎ整合 / B: REFとの照合 の二本立てで、これは **A の担当**である。
> どちらのページが正しいかは原理的に決まらないが、採点は「矛盾を指摘したか」だけを見るので支障はない。

対照群として、旧来の形（EN のみ誤り）を距離20と距離75に1件ずつ残してある。
**対照が取れて本体が取れないなら、モデルは跨ぎを見ておらずローカルなREF比較しかしていない**
と分かる。この切り分けができるようにするための2件である。

### 跨ぎ指摘はどちらのページで報告してもよい

26ページ版の `e14` で、Copilot が相手方のページを主たる箇所として報告したために
`score.mjs` が取りこぼす問題があった。長尺版では planted に `alt`（相手方の page/quote）を持たせ、
どちらで報告されても検出とみなすようにした。`score.mjs` 側も対応済み。

#### 5. 採点

`Run-Benchmark.ps1` を使ったなら `docs/benchmarks/runs/raw/<日付>_<構成>.json` が
すでに指摘.json と同じ内容なので、そのまま変換できる。
手で走らせたなら「ZIPを保存」→ 展開 → **`指摘.json`** を使う（画面から書き写す必要はない）。

```bash
node docs/benchmarks/report-to-run.mjs docs/benchmarks/runs/raw/2026-08-05_consistency25.json \
     --out docs/benchmarks/runs/2026-08-05_consistency_w25.json --note "整合性 幅25・重ね3"
```

そのうえで採点する。

```bash
node docs/benchmarks/score.mjs docs/benchmarks/fixtures/gold-long.json \
     docs/benchmarks/runs/<run>.json --reachable 25 --by kind,distance
```

`per_distance` が距離別 recall、`per_kind` が種類別 recall、`missed_ids` が未検出の一覧。

`--reachable <幅>` は**幅を変えた run どうしを比べるときに必須**である。
跨ぎのペアは両ページが同じセクションに入らないと取りようがないので、
これを外すと「幅を広げたら悪くなった」のか「そもそも届いていなかった」のか区別できない。
`gold-long.md` の表のとおり、到達可能な件数は**幅に対して単調ではない**
（境界がどこに落ちるかで、距離の短いペアでも分断される）。素の recall を幅どうしで比べてはいけない。

### 追撃passは費用に見合っているか（2026-08-04 の実測）

139ページ・幅25・重ね3 の run（5セクション成功、1セクションは失敗）から:

| | 指摘 | 所要 |
|---|---|---|
| broad（1ターン目） | 111件 | 557秒 |
| 追撃3pass（訳語の揺れ・省略・見落とし探し） | 12件 | 581秒 |

**追撃は時間の51%を使って指摘の9.8%しか出していない**（訳語の揺れ2件 / 省略6件 / 見落とし4件）。
139ページに19分かかる内訳がこれである。

ただし件数は歩留まりであって recall ではない。追撃の12件が
「broad が取り逃した跨ぎのペア」なら価値は件数以上になる。
`--by kind` で採点して初めて判断できる。**採点前に追撃を消してはいけない。**

そこで統合1ターン構成（`combined`）を用意した。追撃で聞いていた観点を
broad のプロンプトへ畳み込み、passは1本にする。

- 幅25なら 6ターン（約9分）、幅40なら 4ターン
- 「注記・脚注・(注)行・表の但し書き・単位の説明を最後に必ず一巡する」も
  プロンプトへ入れた（見落とし探しpassが担っていた役割）
- `combined: true` と `profile: "consistency1"` は**必ず両方**指定する。
  片方だけだと「1ターンなのに観点の指示が無い」か「指示はあるのに4ターン走る」になる

### 実測（2026-08-04・gold 61件）

| | ターン | recall | precision | 所要 |
|---|---|---|---|---|
| 統合1ターン 幅25 | 6 | 53.2%（到達可能47件） | **100%** | 5分 |
| 統合1ターン 幅50 | 3 | 49.0%（到達可能49件） | 78.1%※ | 5分 |
| 統合1ターン 幅100 | — | 添付が60秒以内に完了せず失敗（**原因未確定**） | — | — |
| 校正 幅10 | — | Copilotページの取り違えで失敗 | — | — |

※幅50の誤検知6件はフィクスチャ側の不備（事業別の売上高比率がセグメント売上高と
　整合していなかった）。修正済みなので、次回はもっと高く出るはず。

観点別（strict recall）:

| 観点 | 幅25 | 幅50 |
|------|------|------|
| num-tr 数値の誤訳 | **100%** (6/6) | **100%** (6/6) |
| name-tr 固有名詞・日付 | **100%** (4/4) | **100%** (4/4) |
| omission 訳抜け | **100%** (7/7) | **100%** (7/7) |
| over 補い過ぎ | **100%** (2/2) | 50% |
| supply 補完不足 | **100%** (4/4) | **25%** |
| spelling 綴り | 12.5% | 12.5% |
| grammar 文法 | **0%** | **0%** |
| drift 訳語の揺れ | 20% | 16.7% |

分かったこと。

1. **A（翻訳校正）のうち A1〜A3 は幅25でほぼ完璧に取れる。**
   数値の誤訳（桁・単位・スケール・年・符号・％）を6件すべて、
   固有名詞・日付を4件すべて、訳抜けを7件すべて拾った。実務の第一関心はここで満たせる。
2. **A4（英語単体の綴り・文法）は整合性モードでは取れない。** 綴り12.5%、文法0%。
   プロンプトが「REFと突き合わせて」と指示する限り、モデルは意味の差しか見ない。
   幅の問題ではなく役割の問題であり、校正パケット（10p）が別に要る。
3. **幅を25→50に広げると、繊細な観点から先に落ちる。** supply が 100%→25%。
   数値や固有名詞のような「照合すれば分かる」観点は幅50でも落ちない。
   **広げてよいのは照合系だけ**で、読解が要る観点は幅に敏感である。
4. **B（跨ぎ整合）は幅を変えても20%前後で低い。** 幅を広げれば届く、という単純な話ではない。

幅100の失敗は原因が確定していない。この run は可視判定の修正より前のビルドであり、
かつ添付の待ち時間が60秒固定だった（0.3MBの幅25と1MB超の幅100を同じ物差しで測っていた）。
「100ページは添付の限界」と結論づけるには根拠が足りない。
待ち時間を中身の大きさに追随させ、ログに totalMB と waitSec を残すようにしたので、
次に失敗したときは「大きくて遅い」のか「検出できていない」のかを切り分けられる。

### 結果の読み方

- **Q1（整合性は何ページ幅か）** … `per_distance` が 100% から落ちる距離が、その幅の実力。
  幅 W なら距離 W 未満のペアしか同一セクションに入らないので、
  「理論上の上限」は `gold-long.md` の表にある。実測がそれをどれだけ下回るかを見る。
  幅を広げても距離の長いペアが取れないなら、**広げること自体に意味がない**。
- **Q2（校正は何ページ幅か）** … `per_kind` の spelling / grammar / omission。
  幅10と幅25で落ちるなら「各行精読は幅に効く」が裏づけられ、
  落ちないなら**パケットを大きくしてターン数を減らせる**。
- **Q3（分ける必要があるか）** … 1本の run で drift と行レベルの両方が取れる幅があるなら、
  分ける必要はない。26ページ版の実測では
  「26p一括では綴り・文法が落ち、10p分割では跨ぎが取れない」という相補性が出ていたが、
  それが**幅の連続的な効果**なのか**2つの別物**なのかは、この文書でないと分からない。

### 予測（実測前に書いておく）

外すかもしれないが、書いておかないと後付けの解釈になる。

1. drift は幅25で距離20まで、幅60で距離40〜60まで取れる。ただし幅60では
   **距離の短いペアの取りこぼしが増える**（見る量が増えて注意が薄まる）。
2. 行レベルは幅10 > 幅25。特に spelling が幅25で落ちる。
3. したがって Q3 の答えは「分ける必要がある」。ただし整合性側の最適幅は
   現行の25より広い可能性がある（139ページを幅25で切ると6セクション＝24ターンで、
   幅60なら12ターンで済む。距離40以下が取れるなら幅60のほうが有利）。
4. 対照群 `n020x`（EN のみ誤り）は幅によらず取れる。これが取れて `n005`（距離5・原文と英訳の
   両方が食い違う）が取れないなら、モデルは**ページ内のREF比較しかしておらず跨ぎを見ていない**。
   その場合、幅を広げること自体が効かないので、プロンプト側の作り直しが先になる。

## 整合性チェックから REF を外す（2026-08-04 提案・未測定）

日英とも同じ誤りがある場合、REF と突き合わせても**原理的に検出できません**。
しかし**英訳文書の中だけを見れば検出できます**——p3 と p10 で同じ営業利益に違う値が
書いてあれば、原文が無くても矛盾だと分かるからです。

そこでモードごとに渡すものを変えます。

| モード | 渡すもの | 見つけるもの |
|---|---|---|
| 校正（10ページ） | TARGET ＋ REF | 訳の誤り。原文と突き合わせる必要がある |
| **整合性（広い幅）** | **TARGET のみ** | 文書内の自己矛盾。原文は要らない |

期待される効果は3つ。

1. **原理的に REF が要らない。** 自己矛盾の検出に原文は使いません。
2. **同じ添付サイズで TARGET を倍近く入れられます。** 跨ぎの検出は幅で決まるので、
   到達できる距離がそのまま伸びます。実測で `drift` は幅25/50/100 のどれでも20%前後でしたが、
   あれは**REF がページの半分を食っていた状態**での比較でした。
3. **タスクが純化します。** 実測で整合性モードは「REFと突き合わせて」という指示のせいで
   英語単体の観点を一切見ませんでした（綴り 12.5% / 文法 0%）。
   REF を外せば「この文書は自己整合的か」だけを問う形になります。

構成 `consistency-noref`（幅25・50・100 × REF なし）を `tools/Run-Benchmark.ps1` に追加して測ります。
**未測定。** 見るべきは `per_distance` と `drift` / `number`（跨ぎ）です。

最初の測定でマスクありが −11.5pt と出ましたが、**原因は2つとも実験側の欠陥**でした。

2. **プロンプトが記号照合の手順を指示していなかった。**
   「IDが違えば数値が違う」と書いただけでは、モデルは照合作業をしません。

**検証器（§4.5）が警告ではなく送信中止でなければならない理由**が、実例で確認できました。
「一部だけ漏れる」は「全部漏れる」への入口です。

引き継ぎ書は `proofread10` を「14パケット×約80秒で約19分」としていた。PDFを添付しなくなった分が
そのまま効いて **1パケット約80秒 → 54.3秒** になっている。

ただし内訳を見ると `attachMs 3〜4秒 / sendMs 約1秒 / responseMs 49〜60秒` で、
**残りの約88%は Copilot の生成時間**である。ここから先は並列化でしか縮まない。

> ⚠️ 途中で「添付は元々ボトルネックではないので分母は動いていない」と書いたが**これは誤り**だった。
> 根拠にした `attachMs` は既にマスク済み run のログで、PDF添付時の値ではなかった。

### この run で見つけたマスカーの欠陥2件（修正済み）

初回は **PACKET_008 で送信が中止**された（`unmasked-number@2871`）。`verify()` は設計どおり
警告ではなく中止した。139ページ全体を本番と同じ経路でマスクし直したところ、
**14パケット中5パケットで計8件**の漏れが再現し、原因は2つとも
**マスカーではなく、マスカーに渡す前の加工**にあった。

| # | 欠陥 | 実害 |
|---|---|---|
| 1 | `TARGET_CHECK_FAST_REVIEW_INDEX` の抜粋が `safeText(text,160)` で**数値の途中を切っていた** | `12,650` が `12,6…` になり、マスカーは `12` だけを伏せ、`,6` が平文で残る。**送信中止で1本も流せない** |
| 2 | 役割ブロックより前（前書き）を**丸ごと "ja" でマスク**していた | 前書きの抜粋は英文なので、`68,921 million yen` が index行では 68,921、本文では 68,921×10⁶ と読まれ、**同じ文に別の記号**が付く |

#2 は `verify()` では絶対に検出できない。検証器は「平文の数字が残っていないか」しか見ないので、
**記号どうしが矛盾していても通る**。そして §2.3 の `百\n万` と同じく、
記号しか見えないモデル側でも見抜けない。正しい訳を誤りとして報告させる型の欠陥である。

直し方:

- `truncateWithoutSplittingNumber()` を新設し、切り詰めが数字にかかったらその数字ごと落とす
- 前書きのうち `TARGET_CHECK_FAST_REVIEW_INDEX:` 以降は **TARGET の言語**でマスクする

修正後、139ページ全14パケットで漏れ **0件**。実際に送られた `TEXT_*.txt` 14本を
本番の `verify()` で再検査しても漏れ0・記号177〜368個・括弧付き負値の残存なし。

|---|---|

| PDFが添付されていないか | ジョブディレクトリに PDF **0件**（`PROMPT_*` と `TEXT_*` のみ）。プロンプト1行目は「**今回はPDFを添付していません。**」 |

## Copilot は並列に叩けるか（2026-08-05 / §6.1・§6.2 の実測）

引き継ぎ書 §6.1 の「同一ユーザーが並列に投げたとき、テナント側で直列化されるのか、
429 が返るのか」を実測した。**ここが塞がっていたら RunspacePool 化は無意味**なので、
実装より先に測るべき唯一の問いだった。

`tools/Measure-Concurrency.ps1` で、**製品と同じ `Invoke-KoseiPacket`** を
ワーカーごとの別ウィンドウ（`Target.createTarget` の `newWindow=$true`）で呼ぶ。
UI を模した別経路は作らない。作ると測ったものが製品とずれる。

### 結果: 塞がっていない

| ワーカー | パケット | 実時間 | 各パケットの和 | **重なり倍率** | 成功 |
|---|---|---|---|---|---|
| 2 | 4 | 110.2秒 | 209.1秒 | **1.90x** | 4/4 |
| 4 | 8 | 120.1秒 | 426.5秒 | **3.55x** | 8/8 |

重なり倍率 = 各パケットの所要の和 ÷ 実時間。直列化されていれば 1.0 になる。

**1パケットあたりの所要は 47〜59秒で、逐次のときの平均 54.3秒と変わらない。**
同時に投げても1本ごとの生成が遅くなっていない、という点が重要である。
「並列にしたぶん1本ずつが遅くなる」なら、重なり倍率が上がっても総時間は縮まない。

429 も「少し時間をおいてから」も観測されず、失敗は 0 件だった。

### 4ワーカーの 3.55x は制限ではなく割り切れ

8パケットを4ワーカーで回すと2巡になるので、理論下限は `2 × 約55秒 = 110秒`。
実測 120.1秒はその 92% にあたり、差はウィンドウ準備と巡回の粒度である。
**テナント側の絞りではない。**

### §6.2（タブが隠れると読めなくなる）も別ウィンドウ方式で解消

4ワーカーすべてが `visibilityState=visible`・実寸 1256×774 を報告した。

```
worker0 の可視性: {"state":"visible","w":1256,"h":774}
worker1 の可視性: {"state":"visible","w":1256,"h":774}
worker2 の可視性: {"state":"visible","w":1256,"h":774}
worker3 の可視性: {"state":"visible","w":1256,"h":774}
```

`newWindow=$true` と、Edge 起動時の `--disable-backgrounding-occluded-windows` /
`--disable-features=CalculateNativeWinOcclusion` が効いている。
**同じウィンドウにタブを並べてはいけない**という結論は変わらない（そちらは実測で踏んでいる）。

### 段0 への当てはめ

段0（139ページ・14パケット）は **760.6秒・1ターン平均54.3秒**で、そのうち
**87.7% が Copilot の生成時間**だった。ここが重なるようになるので、

| 構成 | 巡回数 | 見込み |
|---|---|---|
| 逐次 | 14 | 760.6秒（実測） |
| 4ワーカー | 4 | 約 240〜260秒 |

**約3倍**の短縮が見込める。実装（§6.4 の #1・#4・#5）に進んでよい。

### この計測でやっていないこと

- **ワーカー数の上限は分かっていない。** 4までしか試していない。
  8・16 で 429 が出るのか、1本あたりが遅くなり始めるのかは未測定。
- **長時間の連続実行**は見ていない。4パケット・8パケットの短い実行だけである。
  14パケットを4ワーカーで通しで回したときに、途中でセッションが切れないかは別途要確認。
- 追撃pass（`Reuse`）を含むパケットでは測っていない。上の実測は `complement`（broad 1pass）である。
  同一チャットを使い回す追撃passが並列で干渉しないかは、`consistency` プロファイルで要確認。

## 並列実行を製品へ入れた（2026-08-05 / §6.4 #1・#4・#5）

`review_max_workers` を追加した。**既定は 1 で、従来どおりの逐次**である。
2以上にすると、ワーカーごとに Copilot のウィンドウを1つ持ち、パケットを round-robin で配る。

### 実機での結果（139ページ・14パケット・同じフィクスチャ）

| | 逐次（段0） | **4ワーカー** |
|---|---|---|
| **実時間** | 783秒（13分3秒） | **282秒（4分42秒）** |
| 短縮率 | — | **2.78x** |
| strict recall | 88.1% | **90.5%** |
| findings precision | 97.6% | 95.6% |
| 指摘 | 43件 | 46件 |

実時間は `Run-Benchmark.ps1` のログの最初と最後の時刻の差である。
**画面の「合計 N 秒」は各パケットの所要の和なので、並列では実時間にならない**（逐次では一致する）。

recall / precision の差は単発runの振れの範囲で、**検出品質の劣化は観測されていない**。

### 2.78x であって 3.55x ではない理由

14パケットを4ワーカーで配ると `4+4+4+2` の4巡になり、最後の巡は2ワーカーが遊ぶ。
加えてパケット作成（139ページのテキスト抽出）は並列化していない共通コストで、実測で約20秒ある。
Copilot の往復だけで見ると 763秒 → 約260秒（約2.9x）だった。

パケット数がワーカー数で割り切れないほど尾が出る。ワーカー数を増やすときはこの粒度も効く。

### #5 で分かったこと: 既存のロックは並列では効いていなかった

引き継ぎ書は `Server.ps1` の `$script:KoseiPassStatLock` と同じ形にせよとしていたが、
**その既存ロック自体が並列時には機能しない**。ワーカーは runspace ごとに `.ps1` を
dot-source するので、`$script:` のロックオブジェクトは runspace ごとに別インスタンスになり、
`[System.Threading.Monitor]` は素通りする。

そこでログと pass-stats の両方を**名前付き Mutex**（`Local\PdfKoseiAssist.Log` /
`Local\PdfKoseiAssist.PassStat`）で直列化した。`Write-KoseiLog` の書き込み例外は
`catch {}` に飲まれるので、直さないと**並列にしたとたんログ行が静かに消える**。

あわせてログ行へ `worker=N` を付けた。これが無いと並列時のログは読めない。

### 安全側の作り

- ワーカー用ウィンドウの用意に失敗したら**逐次へ落とす**。並列にできないことは走らない理由にならない
- 致命的失敗（Copilot画面の準備失敗）は共有フラグで全ワーカーへ伝え、全員が止まる
- `review_max_workers` は 1〜8 の範囲外なら 1 に落として警告する。
  **上限8は安全側の歯止めであって、8まで出せるという実測ではない**（実測は4まで）

### 推奨設定

```json
"review_max_workers": 4
```

ただし `config/settings.json` は gitignore 対象なので、実機ごとに設定が要る。
既定のままだと逐次で動く（＝これまでと同じ）。

## 整合性から REF を外し、幅100を測り直した（2026-08-05）

`CONSISTENCY_NO_REF = true`。整合性レビューへ日本語原文(REF)を添付しなくなった。
狙いは「翻訳照合ではなく、文書が自分と矛盾していないか」だけを問うこと。

### 幅100は通る。失敗の原因は幅ではなく PDF の添付だった

```
添付完了 files=PROMPT_SEC_001_TARGET_P1-100.txt,TEXT_SEC_001_TARGET_P1-100.txt
        totalMB=1 doneBy=stable-chip elapsedMs=3790
```

以前「添付が60秒以内に完了せず失敗（原因未確定）」としていた幅100が、**3.8秒**で添付完了した。
masked-text にして PDF を送らなくなったことで消えている。**2セクション・2ターン・186.8秒**
（幅25は6ターン）。整合性セクションは `review_max_workers` の並列実行にそのまま乗った
（`並列実行 workers=2 packets=2`、2ウィンドウとも `visible`）。

### 死んでいた2観点が動き出した

| 観点 | 幅25＋REF | **幅100＋REFなし** |
|---|---|---|
| **number 跨ぎ数値** | **0%** | **50%** |
| **accounting 会計整合** | **0%** | **50%** |
| drift 訳語の揺れ | 12.5% | 11.1% |
| spelling / grammar | 12.5% / 0% | 0% / 0% |

`number`（日英とも同じ数値が誤り）と `accounting`（内訳の合計が別ページの総計と合わない）は、
これまで**全構成・全runで一度も検出できていなかった**。REF を外したことで動き出している。
`drift` は REF の有無と無関係だった。

全体 recall は 53.2% → 39.6% だが、これは REF 依存の観点を校正パケット側へ移した当然の結果で、
**和集合で評価しないと意味がない**。

### ⚠️ この数字を鵜呑みにしてはいけない

- **単発run。** number は到達可能2件中1件、accounting は2件中1件。母数が小さすぎる。
- **REF が無いのに `omission` 100% / `num-tr` 100% が出ている。** 原文が無いのに訳抜けを
  全部取れるのは理屈に合わない。**`score.mjs` の quote 部分一致が緩く当たっている疑い**があり、
  ここを確かめないまま新しい素材で測ると、同じ緩さを引き継いだ数字が出る。

### プロンプトの分岐を足した

REF を外すと、作業指示 B（翻訳整合）が「添付していない REF に合わせて修正案を出せ」になる。
§2.1 #3（添付していないPDFを参照させていた）とまったく同じ型の欠陥なので、
`hasRefInPacket` で分岐させ、REF が無いときは

> 翻訳の当否は**判断しないでください**。「原文ではこうなっているはず」という推測に基づく指摘はしないでください。

と明示する。推測による訳の指摘は誤検知に直結する。
あわせて D（日本語特有の省略）も REF が無いときは飛ばす。
なお REF が無いと `ellipsis` 観点は `REF_REQUIRED_LENSES` により自動で skip される
（整合性は `broad → wording → gap` の3passになる）。

## 跨ぎ数値の計器を作り直す（2026-08-05 / ①②完了・③未実施）

いまの `number` は **3件（距離 5/30/90 に各1件）** しかなく、幅の比較に耐えない。
`drift`（8距離 × 各2件 = 16件、生成時に一意性を機械検証）と同じ水準へ引き上げる。

設計:

- **日英とも同じ値を間違える**こと。片方だけだとページ内で気づけて距離の計器にならない
  （対照群 `number-local` がその切り分け役）
- **1距離あたり3件以上**。1件では当たり外れと区別がつかない
- 距離は 5/15/30/50/70/90/110/130 のように**幅100を超える帯まで**引く。
  そうしないと「幅100で足りる」が言えない
- `--reachable W` は距離が幅を超えた planted を分母から外すので、
  **各幅の到達範囲内に十分な件数**が要る
- `accounting` も別機構なので独立に増やす

順序は **① 採点の当たり方を1件ずつ確認 → ② 素材を作り直す → ③ 25/50/100 を各3回**。
①を飛ばすと、緩い照合を引き継いだ数字で幅を決めてしまう。

> ①②は実施済み（下記）。③は **各1回まで**。中央値を取るには残り2回ずつが要る。

並列化で1本が数分になったため、§2.2 が要求する「複数runの中央値」が現実的になった。
従来は1構成1回が精一杯で、単発runの振れを承知で読むしかなかった。

### 訳抜けを採点から外した（`--no-ref`）

REF を渡していない run で `omission` が 100% と出た件を1件ずつ確認したところ、
**照合は壊れておらず、モデルは実際にそのページのその文を引用していた**。ただし理由が違った。

```
gold  : These figures are calculated based on internal management materials  （後続節が訳抜け）
指摘  : 同じ文を「指示対象が不明瞭」として指摘
```

planted は「後続の節が丸ごと落ちた」もので、残った英文は単体で読むと指示対象が曖昧になる。
モデルは REF なしでも**内部の不明瞭さとして正しく指摘できてしまう**。
ページも引用も一致するので、採点器は「訳抜けを検出した」と数える。
**理由がまったく違うのに、quote 一致では原理的に区別できない。**

原文が無ければ判定できない観点（`omission` / `supply` / `over` / `num-tr` / `name-tr`）を
分母から外す `--no-ref` を追加した。

```
node docs/benchmarks/score.mjs gold-long.json run.json --reachable 100 --no-ref --by kind
```

幅100・REFなしの run を測り直すと **39.6% → 13.3%**（planted 30件）。
差の23件はすべて担当範囲外の観点が別の理由で偶然一致していた分である。

> ⚠️ `spelling` / `grammar` は REF に依存しないので `--no-ref` では残るが、
> **これらも整合性モードの担当ではない**（校正10p が 87.5% / 62.5% で取っている）。
> 「原文が要るか」と「そのモードの担当か」は別の軸で、後者の絞り込みは別途必要。

### 担当外の観点も分母から外す（`--scope`）

上の ⚠️ に対応して `--scope <モード>` を足した。そのモードが担当する観点だけを分母にする。

| モード | 分母に残す kind |
|---|---|
| `consistency` | `drift` / `number` / `number-local` / `accounting` |
| `proofread` | `spelling` / `grammar` / `omission` / `supply` / `over` / `num-tr` / `name-tr` |

```
node docs/benchmarks/score.mjs gold-long.json run.json --reachable 100 --scope consistency --by kind,distance
```

`--no-ref` が「原文が無いと**判定できない**か」で切るのに対し、`--scope` は「そのモードの**担当か**」で切る。
綴りは REF 無しでも判定できるが整合性の担当ではないので、`--no-ref` だけでは残ってしまう。
担当外を分母に残したまま幅を比べると、幅の効果ではなく分担のずれを見ることになる。

最初の割り当ては文書の前・中・後へ均等に散らしただけで、**距離90の3件が3件とも幅100の境界をまたいでいた**。

そこで「距離 < 幅なら、その幅の実際のセクションに両ページとも収まる」ことを条件に割り当て直した
（`computeSections` の分割規則そのもので判定。等幅＋重ね3＋末尾畳み込み）。
同じ帯の3件は28ページ以上離し、境界の落ち方に3件まとめて巻き込まれないようにしてある。

### ⚠️ Windows で刷り直したら、抽出テキストだけが別物になっていた

## ③ の1本目で masked-text の欠陥が出た（2026-08-05・幅25で中止）

200ページ版で `Run-Benchmark.ps1` を回し、1本目（幅25・9セクション・18指摘）を採点した。

| 指標 | 値 |
|---|---|
| strict recall | 0%（14件中0） |
| **assisted recall** | **42.9%**（14件中6） |
| findings precision | 16.7% |

### 18件のうち6件が「同じ値どうしを不一致」と言っていた

```
P.6 の売上高 458,921 と P.22 の売上高 458,921 が一致しない
```

原因はモデルではなく**マスカー**である。財務諸表の表は単位を行や列の見出しに書き、
セルは裸の数字にする。

```
Net sales (Millions of yen) 361,400 … 458,921     ← セルは裸の 458,921
Net sales for the current fiscal year were 458,921 million yen.   ← こちらは 458,921×10⁶
```

同じ金額に**別の記号**が付き、モデルは設計どおり「記号が違う＝別の値」と報告する。
§2.3 の `百
万`、前書きの言語取り違えと同じ系統で、**記号しか見えないモデル側では見抜けない**。
しかも整合性レビューは離れた2箇所の突き合わせが仕事なので、表と本文が別記号だと仕事が成立しない。
残りの構成を回しても幅の比較にならないので、**1本目で中止した**。

### 直したこと（2つ）

1. **マスカー**: 単位が書かれている**同じ行**の裸の数字は、その単位を継承する。
   - 行をまたいでは効かせない（同じ表に「従業員数（人）3,214」のような別単位の行が並ぶため）
   - 単位語が付いている数値には継承を重ねない（二重に掛けない）
   - **自分の単位を持つ数値には継承しない**。`(Millions of yen) … (up 7.2%)` の 7.2 まで
     百万倍にすると、他ページの 7.2% と別記号になり、**直そうとした幻の不一致を別の形で作る**
   - 継承した数値は西暦の許可を受けない（金額であって年ではない）
2. **フィクスチャ**: 金額の表に単位が1つも書かれていなかった。実在の有価証券報告書は必ず書くので、
   行の見出しへ `（百万円）` / `(Millions of yen)` を入れた。

結果、**同じ表記に複数の記号が付く箇所が 73 → 5**。残る5件は
`18,900千株` と `18,900百万円` のように**実際に別の量**で、別記号が正しい。

### 残る限界（未対応）

実文書では単位を表のキャプション（「（単位：百万円）」）に**1回だけ**書くことが多い。
行に無ければ継承できないので、この型の文書では同じ欠陥が出る。
ブロック単位の継承は、散文へ漏れると**逆に誤検知を作る**（裸の数値が一斉に百万倍になる）。
`docs/plan/NUMBER_MASKING_SPEC.md` に規則を足してから実装するべきで、今回は手を付けていない。

### ⚠️ 直した直後の run が「直す前」のまま走った

マスカーを直してすぐ回し直したところ、**同じ幻の不一致が7件出た**。原因は
`Reset-App` が**画面を読み込み直さない**ことである（読み込み直すと `beforeunload` が
`/__page-closed` を投げてサーバーが止まるため、意図してそうしてある）。
つまりコードを直しても、開いたままの画面は古い JS のまま走る。
出力は一見まともなので、気づくのは採点した後になる。

対策として入口に `loadedAt`（画面の読み込み時刻）を持たせ、`Run-Benchmark.ps1` が
`js/**` と `index.html` の更新時刻と比べて、画面のほうが古ければ**中止する**ようにした。
**実装を直したらアプリを再起動する**（あるいはタブを再読込する）のが正しい手順である。

### 中止した run から分かった有効な信号

- 幅25で到達可能な跨ぎ数値6件のうち **4件**（`n005b` / `n015` / `n015b` / `n015c`）を実際に検出していた。
  距離5・15の帯は幅25で取れている。
- ただし **strict ではなく assisted** である。モデルは整合性モードの指摘に
  `needs_human_review=true` を付ける（REFが無く確信を持てないため、プロンプトの指示どおり）。
  **整合性レビューは assisted recall で読む**のが正しい。strict で読むと一律 0% になる。

## 会計連動を廃止し、「形式の揺れ」を主計器にした（2026-08-05）

### 会計連動は**マスクとは両立しない**ので廃止

実測（幅25/50/100/200）で `accounting` は **0/6**。距離でも幅でもなく、機構の問題である。

```
内訳: 人件費 ⟦#ABC⟧ / 減価償却費 ⟦#DEF⟧ / その他 ⟦#GHI⟧
総計: ⟦#JKL⟧
```

**記号は足せない。** 「内訳の合計が総計と合わない」は値の演算を要求するので、
実量を伏せたまま成立させる方法が無い。プロンプトで直せる類ではないので、
計器から外した（`ACCOUNTING_PAIRS` 削除）。金額の演算に基づく検査が要るなら、
マスクを外すか、モデルではなく決定的なチェックとして別立てにするしかない。

### 訳語の揺れ（drift）は「原文が同じ」を知らないと判定できない

`in-process inspection` と `in-line inspection` は**どちらも英語として正しく読める**。
同じ日本語から訳されたことを知って初めて「揺れ」になる。
整合性レビューは REF を添付しない設計なので、**原理的に不利**な層である。
実測でも幅を変えても検出は1〜2件で頭打ちだった（40% → 6.3% は分母が増えただけ）。

そこで drift は **各距離1件・計8件の対照群**に縮小し、主計器の座を term に譲った。
「原文を知らないと分からない層は本当に取れないのか」を見るために残してある。

### 代わりに置いた計器: 形式の揺れ（`term`・24件）

**同じものを指しているのに表記が揃っていない**——英語だけを読んで判定できる層である。

| anchor 側 | error 側 |
|---|---|
| `the AOI Quality Standard` | `the AOI Quality Standards` |
| `Aoi Advanced Materials Co., Ltd.` | `Aoi Advanced Material Co., Ltd.` |
| `the Nagoya Branch` | `the Nagoya Branch Office` |
| `the Certified Health & Productivity Management Organization` | `the Certified Health and Productivity Management Organization` |
| `the Whistleblowing Regulations` | `the Whistle-blowing Regulations` |

固有名詞・制度名・規程名は文書内で表記を揃えるのが規範なので、
**「形式上そろえるべきものがそろっていない」だけで指摘できる**。
距離統制は number と同じ 5/15/30/50/70/90/110/130 × 各3件。

生成時の検証は drift と同じ（日本語の呼称は文書全体でちょうど2回、2つの英語表記はそれぞれ1回）だが、
**一方が他方の一部になる組**（Standard / Standards、Branch / Branch Office）をわざと入れているので、
包含を除いて数える。形式の揺れは元来そういう形をしているためで、
素直に数えると「表記が漏れている」と誤って生成を止めてしまう。

`Test-LongFixture.mjs` は、2つの表記が**語の半分以上を共有している**ことも確認する。
まったく別語の組が紛れ込むと drift と同じ層になり、「REFなしでも取れる層」を測れなくなる。

| 種類 | 件数 |
|---|---|
| term（形式の揺れ） | 24 |
| number（跨ぎ数値） | 24 |
| drift（訳語の揺れ・対照群） | 8 |
| number-local（対照群） | 2 |
| 同一ページの翻訳誤り（num-tr / name-tr / supply / over） | 21 |

**term と number が同じ距離・同じ到達範囲で並ぶ**ので、
「記号の照合はできるが表記の照合はできない（またはその逆）」が読み取れる。

#### 脚注の手順を入れて structure-local が上がった（2026-08-06）

未検出を3run分そろえたら、`structure-local` の落ちは**すべて脚注の対応**に集中していた
（`sl02` `sl06` `sl08`）。観点の指示は「注記番号・脚注記号の対応」と1行あるだけで、
**どう探すかが書いていなかった**。特に「脚注はあるのに本文から参照されていない」型は、
ラウンド2の「欠番・重複・順序を確かめる」では原理的に見つからない。

本文側と脚注側を**両方向**で突き合わせる手順に展開した結果:

| | 前 | 後 |
|---|---|---|
| structure-local | 4・5・5 /8（3回・中央値5） | 4・5・7・7・7・7・7・8 /8（**8回・中央値7**） |

> ⚠️ **訂正（同日中）。** 最初にここへ「後の最小値(7)が前の最大値(5)を上回るので振れでは
> 説明できない」と書いたが、**後の3回だけを見た言い過ぎだった**。その後の5回で 5 と 4 が出て、
> **範囲は重なる**。言えるのは「8回中6回が7件以上（前は3回とも5件以下）で、中央値が 5 → 7 に動いた」まで。
> **3回で範囲が離れて見えても、それだけで『振れではない』と言ってはいけない。**

同じ日に `term` にも同じやり方（探し方を手順で書く）を入れたが、**効果は確認できなかった**
（19・19・21 → 17・19・18）。**手順を書けば必ず効くわけではない。**

#### term は「判断基準」を変えたら実物で効いた（合成では測れなかった）

未検出を距離別に見ると **d=110 が 8/9 なのに d=90 は 2/9** で単調でない。距離は原因ではなかった。
落ちる組の中身は、どれも**修飾語が同じで種別を表す語だけが入れ替わっている**形で、
「別の実体かもしれない」と読める。指示が**確実性を要求していた**ためモデルが見送っていた。
そこで判断基準を「別のものだと分かる根拠が資料の中に無いかぎり報告する」に変えた。

| | 合成（term /24） | 実物・埋めた版（term /2） |
|---|---|---|
| 変更前 | 19・19・21（中央値19・3回） | 0/2 |
| 変更後 | 17・18・19・21・22（中央値**19**・5回） | **2/2 が2回連続** |

**⚠️ 合成フィクスチャではこの改善を測れない。** term 24件は形の違い（複数形・記号の書き分け）に
偏っていて、狙った型は少数派なので ±2〜3の振れに埋もれる。実物に埋めた2件は**その型そのもの**だった。
**素材が測れない改善がある**、という実例である。→ `real/README.md` と引き継ぎ書 §7.11。

素材を増やして分かったこと:

- **`structure-local` は 62.5% 前後**。v1（分母2件）では 1/2 と 2/2 を行き来するだけで、
  「毎回1/2」とも「2/2で問題なし」とも読めてしまっていた。**同一ページの番号の乱れは弱い**、
  というのが分母8件で初めて言えるようになった。
- **`number` の振れが大きい**（15〜22件）。v1（分母24件・4回）では 17〜18件で安定して見えたが、
  それは4回とも同じような結果を引いただけだった可能性がある。ここは回数を増やして測り直す価値がある。
- `structure`（跨ぎ）は分母を4→8にしたら 100% ではなくなった（6〜8件）。
  v1 の「4回とも 4/4」は**天井に張り付いていただけ**で、分解能が無かった。

> ⚠️ **マスカー修正の前後を比べて「良くなった/悪くなった」と言えるだけの回数は無い。**
> 修正前の v2 実測は1回（83.3%）で、修正後3回の幅（71.2〜83.3%）の中に収まっている。
> 計器の不変条件（同じ実量に同じ記号・日英で記号が揃う）は `Test-FixtureTextLayer` が
> 通っているので、跨ぎ比較の土台は保たれている。

> ⚠️ **これは合成フィクスチャの数字である。実物では出ない。**
> 実物の有価証券報告書（167p）は、マスカー修正で**送信は通るようになった**（伏せ損ね 42件 → 0件）が、

> 回答している。**実物には正解が無いので、0件が正しいかは判定できない。**
> 詳細は `docs/plan/NUMBER_MASKING_SPEC.md` §4.2c、診断は `tools/Audit-DocumentMask.mjs`。

#### 振れ幅の読み方

- **全体の recall は 43〜47/56（幅4件）**。構成どうしの差（26.6% → 81.3%）とは桁が違うので、
  構成の順位は動かない。一方で**1回の測定で 1〜4件の差を語ってはいけない**。
- **観点ごとの内訳は全体よりよく振れる**。number は 17〜18件、term は 18〜22件で、
  同じ構成のまま term が 75% にも 91.7% にもなる。
  以前ここに書いていた「number 21/24 = 87.5%」「term 18/24 = 75%」は
  **どちらも1回だけの値**である。4回そろえると中央値は 17.5/24・20/24 に落ち着く。
- `structure-local`（同一ページの項番の欠番）は分母が2件しかないので、
  **1/2 と 2/2 を行き来する。「毎回1/2」ではない**（2026-08-05 の6本では 1/2 が3本・2/2 が3本）。
  計器として弱いので、ここを根拠に何かを決めないこと。

### なぜこの形なのか（実測で決まった順）

| 決めたこと | 根拠 |
|---|---|
| 幅を分割しない | 広げるほど実検出数は増え、ターン数は減る。距離110/130 でも取れており、距離ではなく**同じ窓に入っているか**が効く |
| 観点を分ける | 1ターンに詰め込むと出力の枠を数値の照合が食い切り、表記の揺れが 2/24 まで落ちる。分けると 17/24 に戻る |
| 観点を**並列**にする | terms / numbers / structure は既出一覧に依存しないので、追撃（直列）である必要がない。ワーカー4本にそのまま乗る |
| 2ラウンドにする | 取りこぼしは同じ場所に固定されず、構成を変えると出たり出なかったりする（term 24件中17件）。穴は注意の配分なので、もう一巡が効く |
| ラウンド2は**探し方を変える** | 同じ指示を繰り返すと同じものが見つかり、それは報告禁止リストに載っているので**0件になる**（numbers で実際に踏んだ）。手順を変えると 0件 → 4〜6件 |
| 会計連動は廃止 | マスクした状態では記号を足すことになり原理的に成立しない（全幅で 0/6） |
| `needs_human_review` は使わない | REFなしでは指摘の半分以上に付き、旗として機能しない（strict 42% / assisted 77%）。**指示文で禁じるだけでは消えない。出力JSONのひな型から消して初めて0件になり、strict = assisted になる**（下の⚠️） |

### 前提（変えると結果が変わる）

- **200ページまで**でしか確認していない。それ以上で添付サイズ・文脈長のどこが限界かは未測定
- **`review_max_workers` は4**。減らすと4観点が直列化し、素直に4倍の時間がかかる
- **`attach_mode` は masked-text**（PDFを添付しない）。数値は記号で送る
- 整合性レビューに**日本語原文(REF)は添付しない**

### 担当していない層（意図的）

| 層 | 理由 |
|---|---|
| drift（訳語の揺れ） | 原文が同じことを知らないと判定できない。整合性はREFなし、校正パケットは10ページで跨げない。**どちらも担当しない**。素材には対照群として8件残す |
| accounting（会計連動） | マスクしたまま記号を足すことはできない。廃止済み |
| e07 型（会計用語の使い分け） | 26ページ版で判断済み。追うと precision を落とす |

### ⚠️ この数字の読み方

- **rounds2（この推奨構成）だけが3回**である。他の構成は各1回のままなので、
  構成どうしの比較表の値には数件の幅があると思って読むこと。
  構成間の差（26.6% → 82.1%）は振れ（±2件）より桁が大きいので、順位は動かない。
- **`needs_human_review` が0件であることを毎回確かめる**。1件でも付いていたら、
  出力ひな型が復活しているか、プロンプトのどこかで旗を要求している。
  旗が付くと採点側（`report-to-run.mjs`）が findings と uncertain_candidates に分けるため、
  **strict だけが別のものを測り始める**（実測: 同じ構成で 76.8% と 12.5%）。

  ```powershell
  node -e "const j=require('./docs/benchmarks/runs/raw/<file>.json');console.log(j.findings.filter(x=>x.needs_human_review).length)"
  ```

- term の「例を消したら 87.5% → 75%」は、**1回対1回の比較だった**。
  3回そろえると例なしでも 79.2 / 87.5 / 91.7% と出るので、
  **集計値のうえでは混入の影響と振れを分離できていない**。
  ただし混入の証拠は run の中にある — 例に書いた4件が 4/4、例に無い20件が 17/20 で、
  同じ run の中で差が付いていた。**素材の答えを指示に書かないこと自体は原則の問題**なので、
  `Test-ConsistencyLenses.mjs` の照合（gold 断片158個）はそのまま残す。
- `structure-local` は分母2件しかない。**「毎回1/2」ではなく 1/2 と 2/2 を行き来する**。
  ここを根拠に判断しないこと。増やすなら素材側に件数を足すのが先。
