# PDF校正アシスト 網羅性改善 修正計画書 V3.3

- 対象: PDF校正アシスト v94
- 基準コミット: `ea40f3d021121170479a631ed398c7de0440afce`
- 作成日: 2026-07-30
- 改訂: V3.2 → V3.3（marker厳格化とJSON修復経路の両立、tail_hash計算場所、要素数巻き戻しの誤判定を修正）
- 目的: Copilot校正の見落としを減らし、再実行を重ねても新規指摘が出続ける状態を、測定可能かつ安全に収束させる

## 0. 結論

V2の方向性である「観点別の複数パス」「同一チャットの再利用」「決定的フィルタ」「網羅性の計測」は妥当である。

ただし、V2のまま実装を始めるべきではない。現行実装との照合で、次の重大な問題が確認された。

1. `BaselineLength` は通常の回答切り出しに使われていない。現行の `Wait-KoseiCopilotReviewResponse` では、通常経路は最新assistant応答要素、代替経路は `Get-KoseiMainResponseRegion` を使い、`BaselineLength` はタイムアウト時の末尾ログにしか使われない。したがってV2の「baseline管理が正しさの核心」という前提は誤り
2. 現行の分割再試行は `ReviewJob.ps1` で findings を `ConvertFrom-Json` し、結合後に `ConvertTo-Json` している。「findings構造をPowerShell側で再構築しない」というV2の方針と矛盾したまま
3. 2回の実行結果の和集合を分母にした被覆率は recall ではない。両方の実行が同じ指摘を見落とせば100%になる
4. チャット喪失をmain textの文字数減少だけで判定する設計は、DOM仮想化、折りたたみ、UI文言変更で誤判定する
5. `issue_scope` を観点識別子へ転用すると、既存フィールドの意味を壊す。観点はpassメタデータとして管理すべき
6. `page|category|quote` だけで重複を削除すると、同じ引用箇所に対する別の修正案を誤って失う
7. `page_checks` の95%閾値は「全ページ確認」という目的と矛盾する。新形式では100%を完了条件にすべき
8. 同一チャットへの周期的な同一ファイル再添付は、添付の重複や参照混乱を起こしうる。参照喪失時は新規チャットへ再添付し、短い継続コンテキストを渡す方が安全
9. 「quick設定ならv94と同じ挙動・同じ所要時間」という保証は、Phase 1でプロンプトを変更する限り成立しない。厳密な旧経路をfeature flagで残す必要がある

本書では、これらを修正したうえで段階導入する。

### 0.1 V3.1 → V3.2 の変更点

V3.1はselector依存を明示した点は正しいが、そのまま実装すると新規チャットで正常なselectorを「不健全」と判定する。さらに、CDP一時障害をDOM非互換と誤認し、marker文字列がJSON内に偶然現れた場合に早期確定する余地があった。次のとおり修正した。

| # | 論点 | 反映箇所 |
|---|------|----------|
| A | 新規チャットではassistant要素がまだ存在しないため、**最初のpass送信前のselector健全性probeは必ずしも成立しない**。初回passをbootstrap turnとし、回答取得後にmultipass適格性を決める方式へ変更 | §7.3、§7.4、K5 |
| B | selectorを1つだけ返す方式は、空のstreaming要素やselector重複時にpoll間で揺れる。全selectorのsnapshotを返し、bootstrapで採用selectorを固定する方式へ変更 | §7.3 |
| C | markerの単純な部分文字列一致はJSON内の文字列でも成立する。**valid JSONの直後に独立行markerがあり、その後が空白だけ**であることを確定条件へ変更 | §7.3 |
| D | CDP例外をselector不健全扱いすると、一時的なtarget切断をDOM非互換と誤診断する。`empty-conversation` / `selector-unmatched` / `cdp-error` を分離 | §7.4、§7.6 |
| E | `uncertain_candidates`をrecallに数え、precisionから除外すると候補への大量退避を評価できない。strict/assisted recallと層別・総合precisionへ分離 | §2.1、§6.2、K21/K22 |

### 0.2 V3.2 → V3.3 の変更点

V3.2のmarker確定条件は誤確定を確実に防ぐが、そのまま実装すると現行のJSON修復と `incomplete-json` 脱出を無効化し、今日は救えている応答をtimeoutまで待たせる。あわせて、tail_hash計算の実装場所と、要素数巻き戻し判定に実装上の穴があった。次のとおり修正した。

| # | 論点 | 反映箇所 |
|---|------|----------|
| F | markerの「単一valid JSON」確定条件を成功の必須条件にすると、現行 `Get-KoseiReviewAnswerJson` の修復（末尾カンマ・全角引用符・コードフェンス・切断）と `incomplete-json` 脱出を失い、復旧可能応答がtimeoutまでhangする。**完了検知**と**成功分類**を分離し、両経路を維持 | §7.3、§7.9、K25、§16 |
| G | `tail_hash` をCDP注入JSで計算すると、Web Cryptoの `crypto.subtle.digest` が非同期で、同期的に値を返す `Invoke-KoseiCdpEval` の戻り値へ載らない。snapshotは `latest_text` を返し、**PowerShell側でtail_hashを導出**する方式へ変更 | §7.3、§14.1、§16 |
| H | assistant要素数の巻き戻し単独をsession喪失とすると、DOM仮想化による過去turn要素の除去で誤ってrestartする。**今回turnの応答も取得できない場合に限定** | §7.6 |

補足: main text用anchor `'その後には何も出力しないでください。'`（`Get-KoseiMainResponseRegion`）は自動経路の初回promptでは利用できるが、手動経路・観点pass・gap passの追撃文では保証されない。したがって、main textフォールバックはlegacy初回passだけに残し、multipass turnでは診断専用へ降格する。V3.3の変更F〜Hは、いずれも新規機能ではなく現行実装（`Repair-KoseiJsonText`／`incomplete-json`脱出／CDP同期eval／DOM仮想化）との整合を取るための実装忠実度の修正である。

## 1. 対象実装と確認済み事実

### 1.1 確認対象

- `app/_app/src/CopilotClient.ps1`
- `app/_app/src/ReviewJob.ps1`
- `app/_app/src/Settings.ps1`
- `app/_app/src/Server.ps1`
- `app/_app/index.html`
- `app/_app/tools/`
- `tools/Verify-Repo.ps1`

行番号は将来の編集で変わるため、本計画では原則として関数名・定数名を基準にする。

### 1.2 現行の応答取得経路

`Wait-KoseiCopilotReviewResponse` の優先順位は次のとおり。

1. `Get-KoseiLatestResponseText` による最新assistant応答要素
2. 直前に取得できたassistant応答のスナップショット
3. `Get-KoseiMainResponseRegion` によるmain領域のフォールバック
4. タイムアウト時だけ、main textを `BaselineLength` 以降で切り出して末尾ログへ使用

このため、複数ターン化で守るべきものは文字数baselineではなく、次の3点である。

- 同じ会話を再利用していること
- 待機対象が「今回送信後に生じたassistant応答」であること
- 今回の終了マーカーだけを判定していること

`Get-KoseiLatestResponseText` は次のselectorを順に試し、最後の一致要素の `innerText` を返す。この一覧が現行の応答取得の生命線であり、§7.3の全selector snapshotと§7.4のbootstrapが対象とする。

```text
[data-testid="markdown-reply"]
[data-content="ai-message"]
[class*="ai-message" i]
[role="article"][data-author="assistant"], [role="article"][aria-label*="Copilot" i]
[data-message-author-role="assistant"]
```

### 1.3 現行の応答JSON抽出と分割再試行

`Get-KoseiReviewAnswerJson` は、コードフェンス除去（```json / ``` の除去）と `Repair-KoseiJsonText`（末尾カンマ・全角引用符・切断などの修復）を適用してから候補をparse・スコアリングする。marker検知後に修復してもcompleteに満たない場合は、生成停止・安定を確認して `completedBy=incomplete-json` で脱出し、上位層へ渡す。V3.3はこの修復・脱出経路をmultipass経路でも維持する（§7.3）。

`ReviewJob.ps1` は通常再試行に失敗すると対象ページを二分し、PowerShell側で次を行う。

- `ConvertFrom-Json`
- `findings` / `checked_page_summaries` / `pages_checked` の結合
- `ConvertTo-Json`

V3では、この既存経路も含めて「raw回答を別passとして返し、JavaScript側で取り込む」方式へ統一する。

## 2. 成功条件

「指摘件数が増えた」を成功条件にしない。件数増加だけでは誤検知の増加と区別できない。

### 2.1 主要指標

| 指標 | 定義 |
|---|---|
| strict planted recall | 事前に埋め込んだ既知誤りのうち `findings` で検出できた割合 |
| assisted planted recall | 事前に埋め込んだ既知誤りのうち `findings` または `uncertain_candidates` で検出できた割合 |
| findings precision | `findings` を人が妥当と判定した割合 |
| candidate precision | `uncertain_candidates` を人が妥当と判定した割合 |
| combined precision | `findings` と `uncertain_candidates` の全件を人が妥当と判定した割合 |
| review burden | packetあたりの `uncertain_candidates` 件数（平均、p90、最大） |
| stability | 同一条件の反復実行間のJaccard係数 |
| incremental yield | 各追加passで初めて見つかった妥当な指摘数 |
| valid page coverage | 構文的に正しい `page_checks` が対象ページを覆った割合 |
| latency | packet単位・job単位の中央値、p90、最大値 |
| failure rate | timeout、incomplete-json、refusal、session-lost、selector-unmatched、cdp-errorの発生率 |

**指標の集計対象（V3.2で修正）**

- `findings` のみで strict planted recall と findings precision を算出する
- `findings` と `uncertain_candidates` の和集合で assisted planted recall と combined precision を算出する
- `uncertain_candidates` 単独の candidate precision と review burden も必ず算出する
- 同一のplanted誤りが両方に出た場合、recallの分子では1件として数える
- この層別により、低確信度候補への大量退避でrecallだけを引き上げることを防ぐ

### 2.2 初期の受入目標

Phase 0で実測したv94をbaselineとし、少なくとも次を満たすこと。

- `thorough` の assisted planted recall: 90%以上
- `thorough` の strict planted recall: v94から3ポイントを超えて悪化しない
- `quick` の strict planted recall: v94から3ポイントを超えて悪化しない
- findings precision: v94から3ポイントを超えて悪化しない
- combined precision: v94から10ポイントを超えて悪化しない
- review burden: packetあたり平均5件以下、p90 10件以下、最大20件
- `standard` の追加passのうち、2回連続で incremental yield が0のpassは既定構成から外す候補とする
- 新形式 `page_checks` の構文妥当率: 95%以上
- legacy modeの中央値所要時間: v94比 +10%以内

上記数値はPhase 0のデータ量が不足する場合、理由を記録して見直す。

## 3. 改善原則

1. **正解集合を作ってから改善する**  
   2回のモデル出力の和集合を正解扱いしない。

2. **会話再利用は文字数ではなくturn識別で守る**  
   assistant応答要素の識別子・件数・fingerprintを使う。

3. **raw回答を保存し、構造の統合はJavaScript側で行う**  
   PowerShell側はジョブ制御と最小限の読み取りに限定する。既存のJSON修復・incomplete-json脱出は破棄せず維持する。

4. **観点はpassの属性として持つ**  
   finding内の既存フィールドを流用しない。

5. **重複は即削除せず、まず束ねる**  
   別提案を失わない。

6. **新形式の全ページ確認は100%を完了条件にする**  
   95%は警告表示の参考値にのみ使える。

7. **旧経路をfeature flagで完全に残す**  
   問題が出たとき、プロンプトを含めてv94相当へ戻せるようにする。

8. **応答取得の土台（selector）は壊れたら黙らず止める**  
   新規チャットではassistant要素がまだないため、送信前の0件を異常扱いしない。初回turnをbootstrapとしてselectorを確定し、その後の不一致、session喪失、CDP障害を別状態として扱う。

9. **完了検知と成功分類を分ける**  
   markerの厳格な行照合は誤確定防止に使う。JSON修復とincomplete-json脱出は無効化せず、復旧可能な応答をtimeoutまで待たせない。

### 4.1 導入順

| Phase | 内容 | 前提 | 主な効果 |
|---|---|---|---|
| 0 | ベンチマーク、計測、feature flag | なし | 効果判定と安全な比較 |
| 1 | プロンプト減量とフィルタ検証 | Phase 0 | 単一passのrecall改善 |
| 2 | turn/session基盤 | Phase 0 | 安全な同一チャット追撃 |
| 3 | 見落とし探しpass | Phase 2 | 少ない追加コストでrecall改善 |

| 5 | `page_checks` と限定追撃 | Phase 2 | 未確認ページの可視化 |
| 6 | 文書横断候補表 | Phase 0〜5 | 表記ゆれ・数値差の検出補助 |

Phase 0の計測は最後まで継続する。Phase 7まで計測を後回しにしない。

### 4.2 feature flag

最低限、次を追加する。

```json
{
  "review_engine": "legacy",
  "review_prompt_version": "v94",
  "review_profile_batch": "quick",
  "review_profile_single": "standard",
  "review_gap_pass": true,
  "review_page_checks": true,
  "review_cross_document_context": false
}
```

- `review_engine="legacy"`: v94のプロンプト・単一pass・既存再試行をそのまま使う
- `review_engine="multipass"`: V3.3のpass制御を使う
- `review_prompt_version`: prompt変更だけを独立比較できるようにする

設定値はallowlistで検証し、未知値はログへ警告して安全な既定値へ戻す。

## 5. Phase 0: ベンチマークと計測基盤

### 5.1 正解データ

代表的な6パケット以上を用意する。

- 文章中心
- 表中心
- 数値・日付が多い
- 固有名詞が多い
- 日本語REFあり
- REFなし
- OCR品質が低いページを含む

各資料に、実務上あり得る既知誤りを合計60件以上埋め込む。6観点の各観点に最低8件を置き、ページ先頭・中央・末尾へ分散する。

元資料と埋め込み後資料、誤りID、ページ、観点、正解理由を `docs/benchmarks/` で管理する。実データを置けない場合は、架空の会社名・数値で同じレイアウトを再現する。

### 5.2 実行方法

- v94 legacyを各パケット3回
- prompt減量版を各パケット3回
- multipass版を各パケット3回
- Copilotモデル、添付方式、パケット境界、実行時刻を記録

反復間の和集合は「未ラベル候補の発見」には使えるが、recallの分母には使わない。

### 5.3 ログ

packetとpassの両方を記録する。

```text
timestamp,app_version,prompt_version,engine,job_id,packet_id,pass_id,
pass_lens,turn_index,status,completed_by,response_source,snapshot_state,
findings_total,uncertain_total,pages_expected,
pages_covered,coverage,attach_ms,send_ms,response_ms,total_ms,
session_restart_count,cdp_retry_count,warning_code
```

要件:

- CSV値を正しくescapeする
- 数値はInvariantCultureで書く
- header作成と追記を同一lockで行う
- 改行を含む自由記述をCSVへ直接入れない
- `warning_code` は固定コード、詳細は通常ログへ出す
- raw回答は従来どおり7日で削除する

### 5.4 Phase 0の完了条件

- gold setに対するstrict/assisted recall、findings/candidate/combined precision、review burdenを算出できる
- pass単位の所要時間と失敗理由が残る
- legacyと新方式を同じ画面から切り替えられる
- benchmark結果を再計算できるスクリプトがある

## 6. Phase 1: プロンプト減量と決定的フィルタ

### 6.1 先に行うこと

プロンプトから抑止ルールを削除する前に、該当するコード側フィルタのfixtureテストを追加する。

対象:

- `whitespaceOnlyDiff`
- `normalizeHyphenationComparisonText`
- `isLikelyLineEndHyphenFalsePositive`
- formatting表示切替

テストには、既知の除外例だけでなく「似ているが除外してはいけない例」を同数以上含める。

例:

- 数値内の空白差で意味が変わるケース
- minusとhyphenの混同
- 行末hyphenに見える正式名称
- `available-for-sale` のような正しい複合語
- dashの種類が財務数値の符号を変えるケース

### 6.2 prompt変更

コード側テストで同等性が確認できた抑止だけをpromptから削除する。

残す:

- 対象は `TARGET_CHECK` のみ
- 判読不能文字を推測しない
- ページ番号、定型header/footer、目次navigationは対象外
- REFがない場合は翻訳整合を判定しない

`reading_confidence` と `evidence_quality` は返させる。ただし低確信度を通常指摘と同列に大量出力させると回答予算を圧迫するため、次の2層に分ける。

```json
{
  "findings": [],
  "uncertain_candidates": []
}
```

- `findings`: 通常の指摘
- `uncertain_candidates`: `page`、`quote`、`category`、`reason`、`reading_confidence`、`evidence_quality` の最小フィールド
- `uncertain_candidates` は各pass最大20件。exact dedupe後のpacket統合結果も最大20件とし、超過時は `reading_confidence`、`evidence_quality`、安定したtie-break keyの順で残す
- UIでは既定で折りたたむ
- **計測上の扱い**: §2.1の strict/assisted recall、findings/candidate/combined precision、review burdenをすべて算出する。gold set採点時に、planted誤りがどちらの層で検出されたかを記録する

### 6.3 受入条件

- prompt文字数と推定token数を変更前後で記録
- strict/assisted planted recallが§2.2の範囲内
- findings/candidate/combined precisionとreview burdenが§2.2の範囲内
- 除外してはいけないfixtureが1件も決定的フィルタで落ちない

「findings件数が増えた」は補助情報に留める。

## 7. Phase 2: turn/session基盤

### 7.1 API設計

`Invoke-KoseiCopilotReviewRequest` にswitchを増やし続けず、明示的なmodeを使う。

```powershell
[ValidateSet('New','Reuse','RestartWithContext')]
[string]$ChatMode = 'New'
```

- `New`: 新規チャット、モデル選択、添付
- `Reuse`: 現在のチャットを維持し、添付とモデル選択を省略
- `RestartWithContext`: 新規チャット、再添付、既出概要を短文で引き継ぐ

禁止する組合せを関数入口で検証する。

- `Reuse` で新規添付を渡さない
- `New` / `RestartWithContext` で必要添付がない場合は明示エラー
- `RestartWithContext` の継続文は文字数上限を設ける

`-SkipFreshChatWait` は呼出側を含めて削除する。

### 7.2 TurnSession

packetごとに次を保持する。

```text
job_id
packet_id
conversation_key
turn_index
assistant_selector_index
assistant_element_count
assistant_tail_hash
assistant_dom_key
last_marker
attachment_generation
restart_count
```

`conversation_key` は、取得できる場合は会話URLまたはCopilot側の会話識別子を使う。取得できない場合は、ページURL、assistant要素数、直前応答fingerprintの組合せを使う。

`assistant_dom_key` はDOM側に安定した属性がある場合だけ保持する補助情報であり、正しさの必須条件にはしない。DOM要素のオブジェクトIDは再評価や仮想化で変わり得るため、永続的な識別子として扱わない。

`assistant_tail_hash` はPowerShell側で導出する（§7.3）。

main textの長さは診断情報として残してよいが、session継続の正否判定には使わない。

### 7.3 今回turnの応答識別（V3.3）

`Wait-KoseiCopilotReviewResponse` に次を渡す。

```powershell
-Marker $TurnMarker
-AssistantSelectorIndex $Session.assistant_selector_index
-PreviousAssistantCount $Session.assistant_element_count
-PreviousTailHash $Session.assistant_tail_hash
```

`Get-KoseiLatestResponseText` の「最初に非空だったselectorだけを返す」方式は、ストリーミング中の空要素やselector間の重複を観測できない。共通helperを `Get-KoseiAssistantSnapshot` とし、§1.2の**全selector**について次を返す。

```text
state
matches[] = {
  selector_index,
  element_count,
  latest_text,
  assistant_dom_key
}
```

- 非表示かどうかではなく、documentに接続されたassistant要素を数える。DOM仮想化で一時的に画面外となった要素を除外しない
- `latest_text` は空文字も返し、空のストリーミング要素を観測可能にする
- `assistant_dom_key` は安定属性が取得できる場合だけ設定する

**tail_hashの計算場所（V3.3で修正）**  
`tail_hash` はCDP注入JS内では計算しない。Web Cryptoの `crypto.subtle.digest` は非同期であり、同期的に値を返す `Invoke-KoseiCdpEval` の戻り値へ含められないためである（同期の自作ハッシュをJSに書くと、PS側テストと二重管理になり決定性検証も割れる）。`Get-KoseiAssistantSnapshot` は各selectorの `latest_text` を返し、**PowerShell側で**次の正規化とハッシュを行って `tail_hash` を導出する。

1. 改行を LF へ統一する
2. タブと LF 以外の C0 制御文字と DEL を除去する
3. 末尾256 Unicode文字を取り、UTF-8 でエンコードする
4. SHA-256 を計算し、小文字hexにする

これにより §14.1 の「tail_hashが同一入力で決定的」を単体テストできる。

**bootstrapとselector固定**  
初回passを送信する前はassistant要素0件でも正常である。初回passをbootstrap turnとして送信し、完了markerを含む有効な応答が得られたselectorを `assistant_selector_index` として固定する。2turn目以降は固定selectorを優先し、消失した場合だけ全selectorのsnapshotを走査する。別selectorへ切り替える場合も、今回turnの有効な完了markerを含む候補だけを採用する。

**「今回turnの応答」と判定する条件（すべて満たす）**  
1. candidateの `latest_text` が非空
2. marker直前の本文が、許可されたオプションのcode fence wrapper除去後に単一の有効なJSON objectとしてparseできる
3. 今回の `TurnMarker` が独立した最終非空行としてJSONの直後にある
4. markerの後は空白だけである
5. 同一selectorなら前turnより `element_count` が増えた、または `tail_hash` が変化した。selector切替時は今回markerと前turnからの `tail_hash` 変化を必須にする

marker検索ではmarker文字列をregex escapeし、`^<escaped-marker>[ \t]*$` を行単位で照合する。JSON文字列値や説明文にmarkerと同じ部分文字列が含まれても完了扱いしない。要素数+1だけでも完了扱いしない。

**完了検知と成功分類の分離（V3.3で追加。現行の修復・incomplete-json経路を維持）**  
上記5条件は turn を**成功**として確定する条件である。ただし現行 `Get-KoseiReviewAnswerJson` は末尾カンマ・全角引用符・コードフェンス・切断を `Repair-KoseiJsonText` で修復してからparseし、marker検知後にJSONが厳密でない場合の `incomplete-json` 脱出も持つ。上記条件2の「単一valid JSON」を成功の**必須**条件とだけ実装すると、これらを失い、今日は修復で救えている応答がtimeoutまでhangする回帰になる。次のとおり分離する。

- **完了検知**: markerが有効JSONらしきブロックの直後に独立最終行（`^<escaped-marker>[ \t]*$`）として現れ、かつ生成停止を確認できたこと
- **成功分類**: 完了検知に加え、**現行の修復パイプライン（コードフェンス除去・`Repair-KoseiJsonText`・全角引用符補正）適用後に**単一valid JSON objectとしてparseでき、`Get-KoseiReviewCompleteness` を満たすこと。満たせば `completedBy=marker` で確定する（条件2の「valid JSON」は修復後を指す）
- **不完全終了**: marker検知済みだが修復後もparse／completeを満たさず、生成停止かつ一定時間安定した場合は、現行どおり `completedBy=incomplete-json` でrawを返し、JavaScript側の構造検証・取り込みへ委ねる（PowerShell側でfindingsを再構築しない）。timeoutまで待たない
- markerの厳格な行照合は誤確定防止のためであり、JSON修復の無効化ではない

**マーカー**

```text
KOSEI_END_<job短縮ID>_<packet連番>_<turn連番>_<random8>
```

- packet名をそのまま埋め込まない
- turnごとに一意
- assistant応答要素の中だけで判定する
- main全体の `LastIndexOf` を正常経路に使わない

### 7.4 bootstrapと取得状態（V3.2）

`Get-KoseiMainResponseRegion` が固定日本語anchor（`'その後には何も出力しないでください。'`）に依存する設計は、追撃promptの文言変更に弱い。実際、このanchorは自動経路のプロンプトにしか含まれず、手動経路・観点pass・gap passの追撃文には存在しない。したがってmain text解析は複数ターン化では信頼できない。

優先順位を次のようにする。

1. 最新assistant要素
2. 取得済みassistant応答スナップショット
3. assistant要素一覧の最後の要素
4. main textは診断ログのみ（正常経路の応答本文には使わない）

どうしてもmain textを解析する場合、今回のuser turnと次のassistant turnのDOM境界を使う。固定文言anchorと全文marker検索には戻さない。

main textを診断専用へ降格した代償として、初回passを次のbootstrap手順で実行する。

1. 新規チャットへ初回passを送信する。送信前のassistant要素0件は `empty-conversation` として正常扱いする
2. `Get-KoseiAssistantSnapshot` で全selectorをpollし、§7.3の完了条件を満たすselectorを固定する
3. selector経由で初回結果を取得できた場合だけ、同じpacketでmultipassを継続する
4. 初回結果をlegacy main-text fallbackでしか取得できなかった場合、その初回結果は保持するが、当該packetは単一passへdowngradeする。取得元の曖昧な応答を土台にmultipassを開始しない
5. selectorでもlegacy fallbackでも初回結果を取得できなければ明示エラーで止める

snapshotの状態を次の4種に分ける。

| 状態 | 意味 | 処理 |
|---|---|---|
| `empty-conversation` | 初回送信前でassistant要素0件 | 正常。異常通知しない |
| `ready` | 有効なassistant候補を取得 | 継続 |
| `selector-unmatched` | 応答が存在すべき状況で生成終了またはtimeout後も全selector 0件 | DOM非互換。multipassを止め、初回だけlegacy fallbackを許可 |
| `cdp-error` | CDP評価・target接続に失敗 | DOM非互換と判定せず、target再取得後に最大2回再試行。それでも失敗ならインフラエラー |

送信後に全selectorが0件でも、生成中は直ちに `selector-unmatched` としない。生成終了のUI状態を確認できた場合、またはturn timeoutへ達した場合にのみ確定する。`selector-unmatched` と `cdp-error` のどちらでも `RestartWithContext` は発動しない。

### 7.5 同一チャットretry

`Invoke-KoseiSameChatRetry` が内部で送信まで行う設計をやめ、通常turnと同じ「入力→送信→今回応答の識別→待機」経路へ統一する。

retry、観点pass、未確認ページ追撃のすべてが同じturn実行関数を使うこと。

### 7.6 session喪失（V3.3で取得障害・仮想化と分離）

次のいずれかで喪失と判定する。

- `conversation_key` が変わった
- 前回のassistant selector／件数／tail hashに対応する応答が現在の会話内に存在しない
- assistant要素数が不自然に巻き戻り、**かつ今回turnの応答（今回markerを含む要素）も取得できず**、再取得しても回復しない（DOM仮想化による過去turn要素の除去だけでは喪失としない）
- 添付参照確認用の短いprobeに失敗した

喪失時は同一チャットへの再添付ではなく `RestartWithContext` を使う。

- 新規チャット
- 元添付を1回だけ再添付
- 完了済みpass、既出件数、次に確認する観点だけを短文で引き継ぐ
- 既存のraw pass結果は保持
- restartはpacketあたり最大1回

**取得障害とsession喪失の切り分け**  
session喪失、selector不一致、CDP障害は原因が異なる。`selector-unmatched` はDOM非互換として明示エラーにし、`cdp-error` はtarget再取得と最大2回の再試行後にインフラエラーとする。いずれも新規チャットでは回復しないため `RestartWithContext` を発動しない。`RestartWithContext` はsnapshot取得が `ready` で、会話識別子または添付参照の喪失を確認できた場合だけ発動する。DOM仮想化による要素数の巻き戻しは、今回turnの応答が取得できるかぎり喪失として扱わない。

### 7.7 PS側とJavaScript側の責務

PowerShell:

- passの実行順制御
- raw回答文字列の保持
- 既存のJSON修復（`Repair-KoseiJsonText`）と `incomplete-json` 脱出の維持
- tail_hashの導出
- status、timing、warning code
- gap prompt用の最小フィールド抽出
- `page_checks` の検証用最小抽出

JavaScript:

- findingsの構造検証
- finding取込
- exact dedupe
- 類似findingのgroup化
- pass間統合
- UI表示

現行の分割再試行は、二分した各結果を `split-a` / `split-b` の別passとして返す。PowerShell側でfindingsを結合・再JSON化しない。

### 7.8 状態公開

`passes` の各要素:

```text
pass_id
pass_kind
pass_lens
turn_index
status
marker
chat_mode
raw_answer
findings_count
pages_checked
coverage
elapsed_ms
phase_timings

```

`issue_scope` は既存の意味のまま保持する。観点集計には `pass_lens` を使う。

polling中に半端な配列を返さないよう、status object生成時にpass配列をsnapshot化する。

### 7.9 受入条件

- 2turn目以降の `attach_ms` と `model_select_ms` が0
- 各turnが当該turnのassistant応答だけを取得
- 前turnのJSONやuser promptを誤取得しない
- retryも同じturn識別経路を通る
- session喪失テストで最大1回だけ `RestartWithContext`
- 初回送信前のassistant要素0件を正常扱いし、初回turn後にmultipass適格性を決める
- `selector-unmatched` と `cdp-error` をsession喪失と区別し、`RestartWithContext` を発動しない
- legacy main-text fallbackで初回結果を取得したpacketは、その結果を保持して単一passへdowngradeする
- **marker検知後に厳密parseできない応答は、現行の修復パイプラインを適用し、なお満たせなければ `incomplete-json` として即rawを返す。timeoutまで待たない**

- cancel要求が5秒以内に反映
- split結果がPowerShellで再JSON化されない

## 8. Phase 3: 見落とし探しpass

### 8.1 既出一覧

既出一覧は先頭50件を単純に採用しない。ページ前半へ偏るため、次の順で最大50件を選ぶ。

1. 各ページから最低1件をround-robinで採る
2. 残枠をcategoryが偏らないように採る
3. quoteは正規化後40文字
4. 同一page/category/quoteは1行にまとめる

併せて全対象ページの既出件数を渡す。

```text
P.1: 2件
P.2: 0件
P.3: 5件
```

0件ページを優先するが、「0件だから必ず誤りがある」とは指示しない。

### 8.2 PSの最小parse

共通helperを1つだけ作る。

- 読むフィールド: `page`、`quote`、`category`
- 文字列長、配列件数、page範囲を検証
- 制御文字を除去
- promptへ埋め込む際に明確な区切りを付け、抽出値を命令として扱わない
- parse失敗時は `warning_code=gap_source_parse_failed`
- 残存分があればgap passは続行

### 8.3 受入条件

- gap passの妥当な新規指摘数を記録
- 既出の言い換えだけの再出力率を記録
- 2回連続でincremental yieldが0なら、当該profileでの既定有効化を見直す

## 9. Phase 4: 観点別pass

### 9.1 観点

| key | 内容 |
|---|---|
| `broad` | 全体走査。各観点の代表的な誤りを浅く確認 |
| `spelling` | typo、大文字小文字、重複語、欠落語 |
| `grammar` | 冠詞、時制、単複、前置詞、主述一致、句読点 |
| `numbers` | 金額、単位、通貨、%、桁、符号、日付、年度 |
| `names` | 社名、製品名、部門名、人名、略語、役職 |
| `translation` | REFとの意味、否定、条件、範囲のずれ |
| `structure` | 表、注記、見出し、脚注、図表label、相互参照 |
| `gap` | 既出一覧にない指摘 |

### 9.2 profile

| profile | pass |
|---|---|
| `quick` | broad |
| `standard` | broad → numbers → names → gap |
| `thorough` | broad → spelling → grammar → numbers → names → translation※ → structure → gap |

※ REFがないpacketではtranslationをskipする。

- profileに含まれる通常pass上限: 8
- completeness repairは通常passと別に数える
- packet全体の生成turn上限: 10
- completeness repairはpassごとに乱発せず、packet全体で最大2turn
- retryとrestartを含む絶対上限も設定し、無限ループを防ぐ

一括・個別の判定をpacket数から暗黙推定せず、UIが `profile` を明示してAPIへ渡す。APIはallowlist検証する。

### 9.3 broad pass

broad passを「全観点を完全に確認」と表現しない。これは初回の広い走査であり、専門passと重複してよい。

各passの回答にlens値を書かせる必要はない。サーバーが実行計画から `pass_lens` を付与する。

### 9.4 profile決定

Phase 0の結果で、追加passごとのincremental yield、precision、所要時間を比較する。効果の低いpassを「理論上必要だから」という理由だけでstandardへ残さない。

## 10. Phase 5: `page_checks` と限定追撃

### 10.1 schema

passのlensは外側のメタデータにあるため、回答内に重複保持しない。

```json
{
  "page_checks": {
    "ok_pages": "7,10-13,15",
    "exceptions": [
      { "page": 8, "verdict": "finding" },
      { "page": 9, "verdict": "unreadable" },
      { "page": 14, "verdict": "skipped" }
    ]
  }
}
```

### 10.2 厳密検証

専用のrange parserを作り、次を検証する。

- 許可文字
- 昇順・降順range
- 重複
- 対象外page
- `ok_pages` とexceptionsの重複
- 不正verdict
- `finding` pageに対応するfindingがあるか
- 極端に長いrange文字列
- 空文字とnull

新形式のcomplete条件は100%である。

```text
covered = ok_pages ∪ exceptions.page
complete = covered == expected_pages
```

`coverage_warning_threshold=0.95` を表示用に持つことはできるが、complete判定には使わない。

旧形式は互換のため `coverage_threshold_legacy=0.70` を残し、UIに「旧形式判定」と表示する。

### 10.3 限定追撃

- packet全体で最大2turn
- missing pageだけを対象
- 同じpassの同じmissing setを繰り返さない
- 追撃後も欠落するpageはwarning表示
- unreadableは「未確認」ではなく、判読不能として別表示
- parse失敗はjob失敗にせず `warning_code=page_checks_invalid`

### 10.4 注意

`page_checks` はモデルの自己申告であり、本当に全ページを精査した証明ではない。目的は「明示的な未確認を検知すること」であり、recallの評価はPhase 0のgold setで行う。

## 12. Phase 6: 文書横断候補

### 12.1 表記変異

全ページから候補を抽出し、変異が2種類以上あるものだけを渡す。

追加要件:

- 頻度だけでなく出現pageを付ける
- case差、hyphen差、全半角差を別typeで記録
- 正規化で意味が変わり得るminus/dashは自動同一視しない
- 最大100group、合計4,000文字
- prompt injection対策として抽出文字列をdata区画に置く

### 12.2 数値候補

単純な文書全体の集合差だけでは誤検知が多いため、可能な範囲で対応pageまたは近接見出し単位に比較する。

正規化:

- 桁区切り
- 全半角
- 括弧負数
- minus記号
- %
- 通貨
- 単位倍率

単位が不明な数値は「不一致」ではなく「要確認候補」とする。

### 12.3 prompt予算

文字数上限だけでなく、次を個別記録する。

- instruction文字数
- TARGET/REF sidecar文字数
- 表記変異文字数
- 数値候補文字数
- 期待responseの最大項目数

上限超過時は、候補表を頻度・重要度で縮小し、instructionを切らない。

- 会話URL変更
- Edge target再取得
- response marker欠落
- 前turn marker混入
- JSON文字列内のmarker部分一致（完了扱いしない）
- marker後に非空文字がある応答（完了扱いしない）
- 有効JSONの直後に独立最終行markerがある応答（完了扱いする）
- **marker直後だが末尾カンマ等でJSONが厳密でない応答（修復して成功扱い、hangしない）**
- **marker直後だが切断されたJSON＋生成停止（`incomplete-json` として即rawを返し、timeoutまで待たない）**
- session lost → RestartWithContext
- 添付参照の維持
- 中止
- **新規チャットの送信前assistant 0件**（`empty-conversation` とし、初回passを送信できること）
- **ストリーミング中の空assistant要素先行出現**（要素数+1のみでは確定せず、marker出現まで待つこと）
- **selectorフォールバック跨ぎ**（固定selector消失後、全selectorから今回markerを持つ応答だけを選び直すこと）
- **全selector不一致**（初回turnだけlegacy fallbackを許可し、取得できた結果を保持して単一passへdowngradeすること。後続turnでは明示エラーとし、`RestartWithContext` を発動しないこと）
- **一時的CDP切断**（target再取得後に最大2回再試行し、selector不一致と誤分類しないこと）
- **DOM仮想化による過去turn要素の除去**（今回turn応答が取得できるかぎりsession喪失・restartとしないこと）

## 16. リスクと対策

| リスク | 対策 |
|---|---|
| multipassで所要時間増 | profile、turn絶対上限、incremental yieldでpass削減 |
| 同一チャットが添付を忘れる | production相当の5turn試験、喪失時はRestartWithContext |
| DOM変更 | 全selector snapshot、初回turnのbootstrap、固定selector消失時の再選択、main text依存の縮小。初回fallback結果は保持するがmultipassへ進めない |
| CDP一時障害をDOM非互換と誤診断 | 状態を分離し、target再取得後に最大2回だけ再試行 |
| marker厳格化で復旧可能応答を取りこぼす | 完了検知と成功分類を分離。現行の修復パイプラインとincomplete-json脱出を維持し、rawはJS側取り込みへ渡す |
| tail_hashをCDP注入JSで計算しようとしてasync化・二重管理 | tail_hashはPS側で `latest_text` から導出。CDP evalは同期を維持 |
| DOM仮想化を喪失と誤判定してrestart多発 | 要素数巻き戻しは今回turn応答も取得不可の場合のみ喪失とする |
| 低確信度候補で回答・確認工数が膨張 | compact schema、最大20件、UI折りたたみ、candidate/combined precisionとreview burdenを受入判定 |
| dedupeで別指摘を失う | exact削除と類似groupを分離 |
| PS 5.1 JSON事故 | raw保持、最小parse、再JSON化禁止、fixture |
| `page_checks` 自己申告を過信 | gold set recallを主指標に維持 |
| 統計CSV破損 | lock、escape、InvariantCulture、固定schema |
| prompt内の抽出文字列が命令化 | data区画、制御文字除去、長さ制限 |
| streaming/selector跨ぎで応答誤識別 | markerを有効JSON直後の独立最終行に限定し、固定selector消失時は全snapshotから今回markerを持つ候補だけを選ぶ |
