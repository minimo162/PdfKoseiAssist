# 数値マスキング仕様書（外部送信前のプレースホルダー化）

状態: **草案**（実装前）。合意を取ってから着手する。
背景: Copilot は Microsoft の外部サーバーで動く。現在は **PDF をそのまま添付している**ため、
文書の中身が丸ごと社外に出ている。機密管理上、数値を外部へ出さないようにしたい。

---

## 0. 適用範囲: 数値のみ（決定済み）

隠すのは**数値だけ**です。会社名・拠点名・取引先名・役員名・戦略やリスクの記述文・
ファイル名は、これまでどおり外部へ送られます。これは仕様上の割り切りであって、
実装漏れではありません。

将来これを広げる場合に備えて、プレースホルダーの形式は種別を持てるようにしておきます（§4.3）。

---

## 1. 現状（実装の事実）

送信物は3点セットで、`attach_mode = 'pdf'` のとき**すべて添付**されます。

| # | 中身 | 作っている場所 | 外部へ出るもの |
|---|---|---|---|
| A | 確認用PDF（対象ページ＋REF候補ページを1本に綴じたもの） | `buildReviewPacketPdfBytes()` | **紙面そのもの。表も数値も画像として全部** |
| B | 抽出テキスト（TEXT サイドカー） | `buildPacketTextSidecar()` → `extractTextLayerText()`（PDF.js のテキストレイヤ） | 本文テキスト全部 |
| C | 依頼文（プロンプト） | `buildPacketPromptText()` / `buildConsistencyPromptText()` | 指示文・ページ表・ファイル名 |

- クライアント → `POST /api/review/jobs` に `pdf_base64` / `text` / `prompt` を渡す（`index.html:5034` 付近）。
- サーバは `<job>/` 配下にファイルとして保存し（`Server.ps1:120-160`）、
  `ReviewJob.ps1:384-408` が Copilot へ添付する。
- 戻ってきた `quote` は PDF のテキストレイヤと突き合わせてハイライト位置を出す。

**したがって「数値を隠す」には A を送るのをやめる必要があります。** PDF を送る限り、
どんなマスキングをしても紙面に数値が写っています。これが本変更の最大の帰結です。

---

## 2. 変更の全体像

```
  現在:  PDF ─────────────────────────────► Copilot
         抽出テキスト（PDF.js）────────────►

  変更後: PDF ──► パーサ ──► 構造化テキスト ──► マスカー ──► 検証 ──► Copilot
                              │                    │            │
                              │                    └─ 辞書（ローカルのみ・外部へ出さない）
                              │                                  │
                              └──────────► ローカル数値照合 ◄────┘
                                              （日英の数値を機械的に突き合わせる）
```

3つの新しい部品が要ります。

| 部品 | 役割 | 置き場所（案） |
|---|---|---|
| **P. パーサ** | PDF → 表構造を保った テキスト/Markdown | ローカル実行（§3） |
| **M. マスカー** | 数値 → プレースホルダー、辞書の作成 | `js/number-mask.mjs`（純関数） |
| **V. 検証器** | 送信直前に「数字が残っていないか」を機械的に確認し、**残っていたら送らない** | `js/number-mask.mjs` |
| **L. ローカル数値照合** | 日英の数値を突き合わせ、外部へ出さずに不一致を見つける | `js/number-audit.mjs` |

## 3. パーサ（PDF → テキスト）

現在の `extractTextLayerText()`（PDF.js のテキストレイヤを視覚行で再構成）は、
**表の構造を失います**。数値は表の中に集中しているので、マスク後は
「どの見出しの数値か」が分からなくなり、モデルは何も判断できません。
そのため表を保てるパーサへ差し替えます。

### 要件

1. **ローカルで完結すること**（クラウドAPIのパーサは、それ自体が漏洩になるので不可）。
2. **日本語を正しくテキスト化できること**（CID埋め込みフォント・全角・濁点）。→ §3.3 で実測: **問題なし**
3. 表をセル構造として出せること（Markdown表 or セル座標付き）。→ §3.3 で実測: **一部壊れる**
4. 見出し階層を保てること。
5. 出力の各要素が **元PDFのページ番号と座標** に紐づくこと。
   ハイライト表示（`highlight_boxes`）は座標が要るので、ここが切れると指摘を紙面上に出せなくなる。
6. Windows・オフラインで動くこと。

### 3.1 前提: ランタイム同梱は可。ただしサイズは膨らませない

配布形態は「`PDF校正アシスト起動.cmd` を叩くだけ」で、中身は **PowerShell 5.1 ＋ 単一HTML** です。
Java / Rust / Python の同梱は**可**ですが、**配布サイズを膨らませない**ことが条件です。
したがって比較軸に「配布サイズ（実測）」を入れます。

### 3.2 候補の比較（2026-08 時点で調査）

| | 実行形態 | ライセンス | 表の扱い | bbox | 追加ランタイム |
|---|---|---|---|---|---|
| **LiteParse**（run-llama） | Rust。CLI / Python / Node / **WASM（ブラウザ）** | Apache-2.0 | **ヒューリスティック**（規則ベース）。Markdown の表として出す | あり（text + bbox の JSON） | **不要**（WASM を同梱） |
| **Docling**（IBM/DS4SD） | Python | MIT | **TableFormer**（学習モデル）。「罫線が部分的／無い表、空セル、セル結合、階層」を扱うと明記 | セル対応付けは後処理で PDF セルへ戻す | Python ＋ PyTorch ＋ モデル |
| **OpenDataLoader PDF** | Java エンジン（Python / Node SDK あり） | Apache-2.0（v2.0 で MPL-2.0 から変更） | local モードは規則ベース、hybrid モードで AI バックエンド | あり（JSON に bbox） | **Java 11+**（hybrid は別途 Python サーバ） |
| **MinerU**（opendatalab） | Python（CPU可・GPU推奨） | MinerU OSS License（Apache-2.0 ベース） | VLM ベース。**財務文書・複雑な表に強い**と主張 | あり | Python ＋ 1.2B VLM |

### 3.3 LiteParse を実際に走らせた結果（2026-08-04 実測）

長尺フィクスチャ（139/140ページ、Chromium 印刷・IPAGothic 埋め込み）を
`liteparse 2.11.0` にかけました。**以下は引用ではなく、この環境で実行した結果です。**

#### 日本語のテキスト化は問題なし

```
140ページ / 0.11秒。OCR不要。
  株式会社アオイ精機 2026年3月期（第73期）
  3 事業の内容 - 電子部品事業
  当連結会計年度における当該事業の従業員数は243人であり、主要な生産拠点はタイ工場である。
  当連結会計年度の研究開発人員は312人である。
```

濁点・全角括弧・漢数字・桁区切りカンマ、いずれも崩れませんでした。
**日本語文章のテキスト化は懸念不要**というのが結論です。

ただし、実運用で必ず踏む落とし穴が2つありました。**どちらも既定値の問題です。**

1. **`ocr_enabled` の既定が `True`**。テキストが取れる PDF でも OCR 経路に入り、
   `tessdata` をネットから取りに行きます。取れないと `ocr_failure_fatal` の既定が `True` なので
   **parse 全体が例外で落ちます**（実測: HTTP 403 で140ページ全滅）。
   → オフライン運用では **`ocr_enabled=False` を明示**するか、tessdata を同梱する。**必須設定**。
2. **`output_format` の既定が `json`**。この状態だと `page.markdown` が**空文字**で返り、
   表が1つも出てきません。実際これで一度「表が取れない」と誤診しかけました。
   → **`output_format="markdown"` を明示**する。

#### 表: 壊れるのは「2列のラベル｜値」表で、罫線が無いとき

長尺フィクスチャ（**全セルに罫線あり**）で、表を含む75ページのうち
**8ページ（11%）で値が全部欠落**しました。しかも不安定です。
同じレイアウトの隣り合うページで結果が割れます。

```
p71（正しい）                          p72（壊れた）
| 建物及び構築物（百万円） | 14,000 |   | 建物及び構築物（百万円） |  |
| 機械装置（百万円）     | 27,700 |   | 機械装置（百万円）     |  |
| 従業員数（人）        |    689 |   | 従業員数（人）        |  |
                                       10,600 8,100 4,200 537   ← 値が段落へ落ちた
```

罫線あり／なしを揃えた対照実験（同じ表を3ページずつ）で、原因が切り分けられました。

| 表の形 | 罫線あり | 罫線なし |
|---|---|---|
| **2列（ラベル｜値）** | ✅ 行の対応は保つ（ただし空列が3本入る） | ❌ **ラベル行と値行が完全に分離** |
| 4列（セグメント表） | △ 空列が1本混入 | ✅ **むしろ綺麗に4列** |

罫線なし2列表の実際の出力:

```
建物及び構築物（百万円） 機械装置（百万円） 土地（百万円） … 従業員数（人）

14,000 27,700 7,900 1,250 3,480 54,330 689
```

**ラベルと値が別の段落に分かれ、対応が失われています。** マスクするとこうなります。

```
建物及び構築物（百万円） 機械装置（百万円） … 従業員数（人）
⟦#QAF⟧ ⟦#MRT⟧ ⟦#BXK⟧ ⟦#LDW⟧ ⟦#JVN⟧ ⟦#PSC⟧ ⟦#HGE⟧
```

モデルに渡せる情報が何も残りません。**有報の【表紙】【設備の状況】がまさにこの2列形式**なので、
実務では確実に踏みます。

参考までに、OpenDataLoader が公表している
「複雑な表で table accuracy **0.489（規則ベース）→ 0.928（AI）**」という比較とも整合します。
Docling の TableFormer は「partial or no borderlines, empty cells, cell spans and hierarchy」を
扱うと技術報告書に明記があり、この2列問題に効くと期待できます
（代償は 0.6〜1.3ページ/秒・メモリ約6GB）。

#### ⚠️ 既定のまま使うと数値の1/3が消える（3つ目の落とし穴）

140ページ分の数値を数え、PyMuPDF の素のテキスト抽出（1,289個）を基準に取りこぼしを測りました。

| 設定 | 取りこぼし |
|---|---|
| `keep_headers_footers=False`（**既定**） | **417 / 1,289 = 32.4%** |
| `keep_headers_footers=True` | **0 / 1,289 = 0.0%** |

既定ではヘッダ・フッタを捨てます。そこには**ページ番号と柱（「2026年3月期（第73期）」）**が
入っているので、**数値の1/3が黙って消えます**。エラーも警告も出ません。
マスキングでは消えた数値は照合対象から丸ごと落ち、しかもローカル数値照合（§6）が
日英の数を比べるので**存在しない不一致を報告し始めます**。

→ **`keep_headers_footers=True` を明示すること。§9.1 のテストで固定します。**

**これは LiteParse 固有の話ではありません。** §3.4 で他も測ったところ、
レイアウト解析を行うパーサは**軒並み既定でヘッダ・フッタを捨てていました**。

| パーサ | 既定での数値取りこぼし |
|---|---|
| Docling | **39.4%** |
| LiteParse | **32.4%** |
| OpenDataLoader | **20.2%** |
| pdfplumber / PyMuPDF（素のテキスト抽出） | 0.0% |

いずれも消えているのは同じもの——**柱（「2026年3月期（第73期）」）とページ番号**です。
「賢い」パーサほど本文以外を捨てるので、この用途では**その賢さが仇になります**。
**どれを採用するにせよ、最初に数値の総数を素のテキスト抽出と突き合わせること。**

この設定さえ正せば、**数値の取りこぼしはゼロ**（140ページ 0.17秒）です。順序も保たれます。
つまり LiteParse で壊れるのは**対応関係だけ**で、
**ローカル数値照合（§6）は表崩れの影響を受けません**
（§6 はページ単位で数値の多重集合を比べるだけで、「どの見出しの値か」を必要としないため）。

ただし**3つの罠を全部ふさいでも、表の問題は直りません**。罫線なし2列表は依然として
ラベル行と値行に分かれます。設定の問題ではなく、レイアウト解釈の問題です。

> ⚠️ 以下は §3.5 で覆ります。ここでは「壊れるのは2列表だけ」と読めますが、
> 体裁を8種類に増やして測ると**そうではありませんでした**。

### 3.4 他のパーサも同じ条件で走らせた（2026-08-04 実測）

同じ2つの入力（140ページの日本語フィクスチャ／罫線あり・なしを揃えた対照PDF）を、
`pdfplumber 0.11.10` `PyMuPDF` `opendataloader-pdf`（local モード、Java 21）にかけました。

| | 日本語テキスト | 140p 速度 | 数値取りこぼし | 罫線あり2列表 | **罫線なし2列表** |
|---|---|---|---|---|---|
| **pdfplumber** | ✅ | 0.1秒 | **0.0%** | ✅ 完全（余分な列なし） | 既定 ❌ 0個検出 / **`text`戦略 ✅ 復元できる** |
| **PyMuPDF** | ✅（全角空白も保持） | 0.13秒 | **0.0%**（基準） | ✅ 完全 | ❌ 0個検出 |
| **LiteParse** | ✅ | 0.11秒 | 0.0%（要 `keep_headers_footers`） | △ 空列が3本入る | ❌ ラベル行と値行が分離 |
| **OpenDataLoader** | ✅（`—` も保持） | 1.7秒 | **20.2%**（JSONでも欠落） | ✅ 完全 | ❌ **表ごと消える** |
| **Docling**（5.5GB） | ✅ | 0.93 p/s（本文）／0.08 p/s（表だらけ） | **39.4%**（既定） | ✅ 完全 | **✅ 行対応を保つ**（空列3本） |

#### OpenDataLoader は数値が消えるので不可

対照PDFで、罫線ありページの値は3ページ分すべて出るのに、
**罫線なしページの値は JSON にも1つも出てきませんでした**（各値の出現が期待6回に対し3回）。
140ページの本番相当でも **JSON 段階で20.2%の数値が欠落**します。
マスキングでは数値の消失が致命的なので、**この用途では採用できません**。

#### pdfplumber の `text` 戦略が、まさにこの穴を塞ぐ

罫線なし2列表に `vertical_strategy="text"` を当てた結果:

```
['建物及び構', '築物（百万円）', '', '', '14,000']
['機械装置（', '百万円）',     '', '', '27,700']
```

日本語に語間空白が無いためラベルが2セルに割れますが、**行の対応は完全に保たれています**。
セルを連結すれば `建物及び構築物（百万円）` ＋ `14,000` が復元できます。

これは §3.7 の **A′（x座標クラスタリングで2列表を復元する）が実際に効く**という裏づけです。
pdfplumber の `text` 戦略は、まさにその手法だからです。
LiteParse は `emit_word_boxes` で語ごとの座標を返すので、同じことを JS 側で書けます。

#### Docling だけが罫線なし2列表の行対応を保った（ただし遅い・重い）

venv を分けて導入し直して実測しました（`docling 2.118.0`）。

**罫線なし2列表の出力:**

```
| 建物及び構築物（百万円） |  |  |  | 14,000 |
| 機械装置（百万円）    |  |  |  | 27,700 |
| 従業員数（人）      |  |  |  |    689 |
```

空列が3本入るものの、**ラベルと値の行対応が保たれています**。
罫線なしでこれができたのは**4つの中で Docling だけ**でした。
TableFormer が「partial or no borderlines」を扱うという記述は、実物で確認できたことになります。
罫線ありは4列表も含めて完璧でした。

代償は速度と資源です。

| | 実測 |
|---|---|
| 導入サイズ | **5.5 GB**（`torch` だけで 1.2GB。モデル 342MB は初回実行時に別途DL） |
| 本文中心のページ | 0.93 ページ/秒 → **139ページで約2.5分** |
| 表だらけのページ | **0.08 ページ/秒** → 同じ密度なら 139ページで**約29分** |

速度は**表の密度に強く依存します**。上の2.5分は本文中心の先頭20ページから出した値で、
**下限**です。有報の財務諸表部分は表だらけなので、実際はこの中間のどこかになります。

**サイズ 5.5GB は §3.6 の制約と両立しません。** 表の精度では最も優れているので、
採るなら **TableFormer だけを ONNX 化して約150MB に落とす B 案**の形になります。

### 3.5 8体裁で測り直した結果、方針を変えます（2026-08-04 実測）

「2列表の復元が要るなら、他の未知の体裁も結局復元が要るのでは」という指摘を受けて、
**有報でよく出る体裁を8種類（すべて罫線なし＝実務の既定）**作り、3つのパーサにかけました。

評価は「表として組めたか」ではなく、**マスキングで実際に必要なこと**——
`ラベルの直後に値が来るか（間に他のラベル・値を挟まないか）`——で測ります。

| 体裁 | LiteParse | pdfplumber(`text`戦略) | Docling(5.5GB) |
|---|---|---|---|
| L1 2列 ラベル｜値 | ❌ 0/3 | ✅ 3/3 | ✅ 3/3 |
| L2 3列 項目｜前期｜当期 | △ 2/4 | △ 2/4 | △ 2/4 |
| L3 単位行＋右寄せ | ❌ 0/3 | ✅ 3/3 | ❌ 0/3 |
| L4 空セル（該当なし ―） | ✅ 2/2 | ✅ 2/2 | ✅ 2/2 |
| L5 階層インデント | ❌ 0/3 | ❌ 0/3 | ❌ 0/3 |
| L6 負数△と注記※ | ❌ 0/3 | ✅ 3/3 | △ 1/3 |
| L7 セル内改行 | ❌ 0/2 | ❌ 0/2 | △ 1/2 |
| L8 4列＋結合ヘッダ | ❌ 0/4 | △ 2/4 | △ 2/4 |
| **合計** | **4/24 (17%)** | **15/24 (63%)** | **11/24 (46%)** |

#### 結論1: 指摘のとおりで、自前復元は終わりません

**8体裁のうち、どれか1つでも全部落とさずに済んだパーサはありません。**
`L5 階層インデント` は**3つとも全滅**しました。
「2列表だけ直せばよい」という前の見立ては誤りです。体裁ごとに手当てを足していく方針は収束しません。

#### 結論2: TableFormer（B案）は期待した効果を出しません

これが今回いちばん重要な結果です。**5.5GB の学習モデルを積んだ Docling が 11/24 で、
純 Python のヒューリスティック（pdfplumber の `text` 戦略, 15/24）に負けました。**

さらに致命的な性質が見つかりました。**数値の並び順が保たれません。**

| | 紙面どおりの並び順を保てたページ |
|---|---|
| pdfplumber | **8/8** |
| LiteParse | 7/8 |
| **Docling** | **0/8** |

TableFormer はグリッドを組み直して行優先で吐くため、**視覚上の読み順と一致しません**。
マスキングでは日英のプレースホルダー列を位置で突き合わせるので、
**並び順が崩れることは、表が崩れることより深刻です**。

したがって **TableFormer を ONNX 化する B案は、払うコストに対して買えるものがありません。**
（ちなみに移植コストも小さくありません。`predict()` は自己回帰ループで、
Python 側の構造補正ロジック——`if line_num == 0: xcel → lcel` 等——がステップ間に挟まっています。
encoder / decoder-step を別々に ONNX 化し、KVキャッシュとループと補正規則を JS で書き直す作業になります。
加えて表の検出には別のレイアウトモデル（実測 164MB）も要るので、モデルだけで約300MBです。）

#### 結論3: 表を復元しない設計にします

3つの実測が同じ方向を指しています。

1. どのパーサも体裁ごとに落ちる（表の復元は当てにできない）
2. **数値そのものは失われない**（設定さえ正せば取りこぼし 0.0%）
3. **並び順は素直な抽出なら保たれる**（pdfplumber 8/8・LiteParse 7/8）

そこで、**グリッドを組み直すのをやめ、数値1つひとつに座標から文脈を添える**方式にします。

```
  現在の発想:  表を復元 → マスク → 送る            ← 体裁ごとに壊れる
  変更後:      数値ごとに「左隣の語」「上のヘッダ」を座標から拾って添える
```

- 必要なのは各数値について**左隣のテキスト**と**同じ列の上にあるヘッダ**だけで、
  グリッド全体の整合は要りません。規則が1つで済み、体裁が増えても破綻の仕方が局所的です。
- 座標は**現行の PDF.js テキストレイヤでも取れます**（`extractTextLayerText()` が使っている
  `getTextContent()` の item 座標）。つまり**新しいパーサ無しでも着手できます**。
- 値の一致判定はローカル（§6）が持つので、モデルに渡すのは文脈だけでよい。
- 並び順が保たれるので、**日英のプレースホルダー列を位置で突き合わせる**検査も成立します。

> ⚠️ この8体裁は合成で、判定基準も「隣接」という1つの操作化にすぎません。
> 実物の有報で再確認するまでは**傾向**として扱ってください。
> ただし3つのパーサで一貫して同じ方向が出ており、判断を変えるには十分だと考えます。

#### 副産物: 「―」（該当なし）が負号に化ける

L4 で `減損損失 ―` が **`減損損失 -1,240`** と出力されました（`―` が ASCII `-` に正規化され、
次の数値とくっついた）。符号を残す設計（§4.2）では、これが**存在しない負数**になります。
マスカー側で「数値の直前の `-` は、直前がセル境界・空白のみなら符号として扱わない」規則が要ります。
§9.1 のテストに入れます。

### 3.6 配布サイズの実測（2026-08-04 計測）

npm レジストリと HuggingFace から実ファイルを取って測りました。**推定ではなく実測値**です。

| 部品 | 実測サイズ | 備考 |
|---|---|---|

| LiteParse Node ネイティブ `@llamaindex/liteparse` | 33.2 MB | 全プラットフォーム分を含む。Windows だけなら数MB |

| TableFormer 公式 `tableformer_fast.safetensors` | **138.7 MB** | accurate 版は 202.9 MB。リポジトリ全体342MB |

#### ONNX 化すればモデルだけ持ってこられる（ただし要検証）

TableFormer は PyTorch がなくても **onnxruntime だけで動かせるはず**です。
その場合の内訳は `onnxruntime-web 12.9MB ＋ TableFormer 139MB` で、**約150MB**。
PyTorch 一式（GB級）とは2桁違います。しかも onnxruntime-web ならブラウザで動くので、
**ランタイムのインストールが要りません**（現行の配布形態を1ミリも変えずに済む）。

> ⚠️ HuggingFace に第三者の変換版（`asmud/ds4sd-docling-models-onnx`, CDLA-Permissive-2.0）が
> ありますが、**accurate 版と fast 版が両方とも 1,048,990 バイトで完全に同じサイズ**でした。
> 元が 202.9MB と 138.7MB で大きさが違うモデルなので、これは辻褄が合いません。
> INT8 量子化でも縮むのは4倍程度で、200倍は縮みません。**使える中身ではない可能性が高い**ので、
> これに依存する計画は立てません。**ONNX 変換は自前で行い、変換後の精度を実測で確認します。**

### 3.7 方針（改訂）

§3.5 の実測を受けて、**表の復元に投資しない**方針へ変えます。

| 案 | 構成 | サイズ | 判定 |
|---|---|---|---|
| **D（採用）** | 素直なテキスト抽出 ＋ **数値ごとの文脈付与**（左隣の語・上のヘッダを座標から） | **0〜5MB** | 体裁に依存する部分が最小。現行の PDF.js でも着手できる |
| A′ | LiteParse ＋ 2列表の自前復元 | 約5MB | **却下**。8体裁で L5/L7/L8 が別々に壊れ、手当てが収束しない |
| B | TableFormer を ONNX 化 | 約300MB（モデルのみ） | **却下**。Docling 実測 11/24 で pdfplumber(15/24) に負け、**並び順が 0/8 で崩れる** |
| C | Python embeddable ＋ Docling 相当 | 5.5GB | **却下**（サイズ・速度・上記の精度） |

**D の中身**

1. テキストと**語ごとの座標**を取る。現行の `extractTextLayerText()` が使っている
   PDF.js の `getTextContent()` で足ります。**新しいパーサ無しで着手できます。**
2. 数値を見つけたら、その数値について
   - **同じ y 帯で左側にある直近のテキスト**（＝行見出し）
   - **同じ x 帯で上方にある直近の見出し行**（＝列見出し）
   を拾い、マスク時に添える。グリッド全体の整合は取らない。
3. 値の一致判定はローカル（§6）が持つ。モデルに渡すのは文脈だけでよい。
4. 並び順は保たれるので、日英のプレースホルダー列を**位置で突き合わせる**検査も併用する。

パーサを差し替えるかどうかは、D を実装してから判断します（§3.8 の合否ラインで測る）。
差し替えるとしても **LiteParse WASM（5MB・ランタイム導入ゼロ）**が第一候補です。
pdfplumber は8体裁で最良（15/24）でしたが Python が要るので、
**D の文脈付与規則を作るときの参照実装**として使い、本体には入れません。

### 3.7b なぜこの形になるのか（設計思想）

LiteParse は「完璧なパースを目指さず、座標付きでテキスト化して解釈は LLM に任せる」
という立場を取っています。§3.5 の実測は**その立場を支持しています**。

- 構造を解釈しにいった Docling（5.5GB の学習モデル）は 11/24 で、
  ヒューリスティック（15/24）に負けました。
- しかも**読み順を壊しました**（0/8）。構造を組み直す代償として、
  「紙面に書いてある順番」という**最も確かな情報**を失っています。
- 一方、素直な抽出は**数値を1つも落とさず（0.0%）、順序も保ちます**。

つまり「解釈を足すほど良くなる」わけではなく、
**解釈を足すと元の情報が壊れる**というのが実測です。D案（§3.7）は
「壊さずに渡して、解釈は後段に任せる」というこの思想をそのまま採ったものです。

#### ただしマスキングは、その前提を一部壊します

「解釈は LLM に任せる」が成り立つのは、**LLM が中身を読めるから**です。
`14,000` を見て「これは建物の金額だろう」と判断できるのは、値そのものが手がかりになるからです。
マスク後は `⟦#QAF⟧` になり、**その手がかりが消えます**。

だから D案は「座標をそのまま渡す」だけでは足りず、
**マスクで失う分の手がかりを、こちら側で最小限だけ補う**（左隣の語・上のヘッダ）という形になります。
表を組み直すのではなく、**LLM が自力で拾えなくなったぶんだけを足す**、という位置づけです。

### 3.8 評価の手順（段階0）

同じ入力で A → B（→ C）の順に測ります。判定は「読めるか」ではなく**セル単位で正しいか**です。

1. 入力は2種類。
   - 長尺フィクスチャ（139/140ページ）。**ただし現在のフィクスチャの表は全セルに罫線があります**
     （`build-long-fixture.mjs` の CSS が `th, td { border: 1px solid #999 }`）。
     このままでは規則ベースのパーサが実力以上に良く見えます。
     → **罫線なし版の表を追加する**（`table.plain` を用意し、財務表の半分をそちらにする）。
   - 実物の有価証券報告書（英訳版・日本語版）を1組。こちらが本番条件。
2. 測る指標。
   - **セル一致率**: 正解の (行, 列, 値) 集合とパーサ出力の一致率。
   - **数値の取りこぼし率**: 原文に存在する数値のうち、出力に現れなかった割合。
     マスキングでは数値が消えることが致命的なので、これを独立に測ります。
   - **見出し帰属の正しさ**: 各数値が属する行見出し・列見出しが復元できているか。
   - 速度（139ページの処理時間）とメモリ。
   - **配布サイズ**（同梱するファイルの合計）。
3. 合否ライン（案）。
   - 数値の取りこぼし率 **1%未満**（取りこぼした数値は照合対象から丸ごと落ちる）。
   - 見出し帰属の正しさ **95%以上**。
   - 139ページを **3分以内**（現行の全体所要が約24分なので、その1割程度に収めたい）。

### 3.9 移行の逃げ道

A・B・C のいずれも合否ラインに届かない場合、現行の `extractTextLayerText()` を使い続け、
**表だけ PDF.js の item 座標からグリッドを復元する**折衷案があります
（x 座標のクラスタリングで列を、y 座標で行を推定する）。
検出力は落ちますが、**外部送信の安全性は変わりません**。マスキングは予定どおり進められます。

## 4. マスキング仕様

### 4.1 基本方針: フェイルクローズ

**既定は「マスクする」。許可リストに一致したものだけを残す。**
逆（既定は残す・危ないものを隠す）にすると、パターンの書き漏れがそのまま漏洩になります。

### 4.2 残す数値（許可リスト）

「文書の構造や固定表現の一部であって、事業データではない数値」だけを残します。

| 種別 | 例 | 備考 |
|---|---|---|
| 西暦・和暦の年 | `2026年` `令和8年` `FY2026` `2026` | 利用者が「機密でない」と明示 |
| 月日 | `6月26日` `June 26` | 年と同じ扱い |
| 固定表現に含まれる数字 | `一株当たり` `第2四半期` `第1条` `二重` `三菱` `一部` | **語として**の数字。辞書で列挙する |
| 構造番号 | 見出し番号 `(12)` `4.` 、注番号 `注1` 、ページ番号 `P.48` | 依頼文が参照するので必須 |
| 規格・様式番号 | `ISO 9001` `様式第三号` | 公知 |

**残さないもの（＝マスクする）の例**: 金額、株数、人数、比率・％、日数・時間、
持株比率、電話番号・郵便番号、証券コード、従業員数、セグメント別数値、
`100.0%`（子会社の持分比率は事業データ）。

#### 符号は残す（利用者の指示）

正負の情報は機密でないため、**符号は可視文字としてそのまま残します**。
日本語会計で使う負号は複数あるので、すべて対象です。

| 表記 | 例 | マスク後 |
|---|---|---|
| △ | `△1,234百万円` | `△⟦#QAF⟧百万円` |
| ▲ | `▲567` | `▲⟦#MRT⟧` |
| ASCII マイナス | `-890` | `-⟦#BXK⟧` |
| 全角プラス | `＋12.3％` | `＋⟦#LDW⟧％` |
| 括弧書き（英文会計の負） | `(1,234) million yen` | `(⟦#QAF⟧) million yen` |

実測で、`△ ▲ - ( ) ＋` はいずれも PDF 抽出で保持されることを確認しました
（`−` U+2212 だけは抽出時に ASCII `-` へ正規化される。マスカー側も NFKC 正規化してから扱う）。

**符号を残すことで得られるもの**: 利益と損失の取り違え、増減の向きの誤りが、
モデルに**読める文字として**残ります。マスクしていなかったときと同じ精度で指摘できます。

> 括弧は数字ではないのでマスク対象外です。したがって `(1,234)` は自然に `(⟦#…⟧)` になり、
> 構造番号の `(12)` は許可リストで数字ごと残るため、両者は取り違えません。

> ⚠️ 許可リストは**設定ファイルで編集できる**ようにします（`config/masking.json`）。
> 業種や文書によって「年は隠したい」「様式番号も隠したい」が変わるためです。
> 既定は上表。編集した内容はログに残します。

### 4.3 プレースホルダーの形式

```
  ⟦#ABC⟧        数値プレースホルダー（ID は英字のみ）
```

**ID に数字を使いません。** これで検証器（§4.5）が
「マスク後のテキストに残っている数字は、許可リストに一致するものだけ」を
単純な正規表現で確認できます。ID に数字を混ぜると、この検査が成立しなくなります。

種別を増やす場合は接頭辞で分けます（将来、固有名詞まで広げる場合）:
`⟦#ABC⟧` 数値 / `⟦@ABC⟧` 組織名 / `⟦^ABC⟧` 人名 / `⟦*ABC⟧` 地名。

### 4.4 ID の採番規則（この仕様の要）

**同じ正規化値には、日英を通じて同じ ID を振ります。**

```
  「当連結会計年度の研究開発人員は312人である。」   →  「…研究開発人員は⟦#KQD⟧人である。」
  "The number of R&D personnel ... was 321."        →  "… was ⟦#PVM⟧."
                                                          ↑ ID が違う ＝ 数値が違う
```

これにより、**モデルは値を知らないまま数値不一致を指摘できます**。
実測で 100% 取れていた `num-tr`（数値の誤訳）の相当部分が、この仕組みで生き残ります。

正規化のルール:

- 全角→半角（NFKC）、桁区切りカンマ除去、前後の空白除去。
- `48` と `48.0` は同一値として同じ ID。
- **ID は絶対値で採番する**。符号は §4.2 のとおり外に残すので、
  `△1,234` と `1,234` は**同じ ID ＋ 異なる符号文字**になります。
  これにより「日本語は `△⟦#QAF⟧` なのに英訳は `⟦#QAF⟧`」＝**符号の落ちが一目で分かります**。
  逆に絶対値ではなく符号込みで採番すると、符号違いが単なる「別の ID」に化けて、
  値そのものが違う場合と区別できなくなります。
- **単位語はマスクしない**。`48百万円` → `⟦#KQD⟧百万円`、`48 thousand yen` → `⟦#KQD⟧ thousand yen`。
  これで **単位スケールの誤り（百万 vs thousand、億 vs million）はモデルが読める文字として残ります**。
  実測で取れていた F0015 / F0021 はこの経路で維持されます。
- ID は**ジョブごとに毎回振り直す**（同じ値がいつも同じ ID だと、複数文書を突き合わせて値を推定できてしまう）。
- ID 空間は十分に広く取り、**出現順に振らない**（出現順だと大小関係が推測できる）。ランダム割当。

#### この採番でも取れないもの

| 状況 | 例 | 扱い |
|---|---|---|
| 正しい単位換算で数値が変わる | `12億円` → `1.2 billion yen` | ID が違うので**誤検知になる**。単位語が異なるときは断定させない（§5）／実値の換算はローカル照合が持つ（§6.2） |
| 端数処理 | `458,921百万円` → `458.9 billion yen` | 同上 |
| 数詞が語で書かれている | `3社` → `three subsidiaries` | マスク対象外の語なので ID が付かない |

### 4.5 送信前検証（ブロッキング）

マスク後のテキスト・プロンプトに対して、送信直前に必ず実行します。

1. 許可リストに一致しない数字が1つでも残っていたら、**そのパケットを送らずにジョブを失敗させる**。
   画面には「マスクできない数値が P.○ に残っています」と、**位置だけ**を出す（値は出さない）。
2. プレースホルダーの形式が壊れていないこと（`⟦#[A-Z]{3,}⟧` 以外の `⟦` `⟧` が無いこと）。
3. 辞書に載っていない ID がテキストに無いこと（＝復元不能な残骸が無いこと）。
4. **PDF が添付対象に入っていないこと**（`attach_mode` が `masked-text` のときは `pdf_path` を空にする）。

検証は「警告」ではなく「中止」にします。ここを警告にすると、
急いでいるときに素通りして漏洩します。

### 4.6 復元（アンマスク）

- 辞書 `⟦#ABC⟧ → "312"` は **ジョブディレクトリ内のローカルファイル**に保存し、
  外部へは一切送りません。ジョブ完了時（または保持期間経過時）に削除します。
- 復元が要る箇所:
  - `quote`（ハイライト照合と画面表示の両方）
  - `suggestion`（修正案）
  - `reference_quote`
  - `issue_summary` / `reason`（モデルが本文中の ID を引用することがある）
- **モデルは数値を発明できない**ので、`suggestion` に新しい数値が必要な指摘（例:「312 に直すべき」）は
  出せません。代わりに `⟦#ABC⟧`（＝REF側のプレースホルダー）を指す形で出させ、
  復元時に実値へ戻します。プロンプトに明記が要ります（§5）。
- 復元後に **ID の残骸が無いこと**を確認し、残っていたら `quality_warning` を立てます。

## 5. プロンプトの変更

現行の指示文に次を足します。

- 「本文中の `⟦#XXX⟧` は数値を伏せたプレースホルダーです。**同じ ID は同じ数値**、
  **違う ID は違う数値**を意味します。」
- 「数値そのものを推測・生成しないでください。修正案で数値を指す必要があるときは、
  対応するプレースホルダーをそのまま書いてください。」
- 「TARGET と REF で対応する箇所の ID が違う場合は `number_mismatch` として指摘してください。」
- 「`△` `▲` `-` `(...)` は負を表します。**ID が同じでも符号が違えば誤り**です（利益と損失の取り違え）。`number_mismatch` として指摘してください。」
- 「ただし**単位語が異なる場合**（`⟦#A⟧億円` と `⟦#B⟧ million yen` など）は、正しい換算かどうかを
  判断できません。`needs_human_review: true` にして、断定しないでください。」
- 「プレースホルダーを quote に含めるときは、**1文字も変えずに**コピーしてください。」

`buildPacketPromptText()` / `buildConsistencyPromptText()` の両方に入れます。

## 6. ローカル数値照合（外部へ出さない検査）

マスキングで失うものを取り戻すのではなく、**もともとこちらでやるべきだった検査**です。
数値の一致は決定的に判定できるので、LLM より確実です。

### 6.1 入力

- TARGET ページの数値リスト（値・単位・座標・前後の文脈）
- 対応する REF ページの数値リスト（ページ対応は既存の「REF候補ページ」を使う）

### 6.2 判定

1. **ページ単位の多重集合比較**。同一ページ対で、正規化した数値の出現回数を日英で比較する。
   片側にしか無い値・回数が違う値を候補として出す。
   > この方式は既に `docs/benchmarks/fixtures/build-long-fixture.mjs` で実装・実運用しており、
   > フィクスチャ生成の実バグ（139ページ全部の数値不一致）を検出した実績があります。
2. **単位換算を考慮した照合**。`千/万/億/兆` ↔ `thousand/million/billion/trillion`、
   `%`、`人/株/円/ドル` の対応表を持ち、換算後に一致すれば正常とする。
3. **語で書かれた数詞**（`3社` ↔ `three subsidiaries`）を数値化して比較する。

### 6.3 出力

`findings` と同じ形で、`source: "local"` を付けて統合します。画面上は
「ローカル照合」バッジを出し、Copilot 由来（`source: "llm"`）と区別できるようにします。

### 6.1b 原則をひとつにする: 「同じ実量には同じ記号」

日英の数値照合も、跨ぎと**まったく同じ原理**で片付きます。
ID を **実量（数値 × スケール語）** で振れば、日英の対応は**記号が一致するかどうか**に還元されます。

```
  JA  「研究開発人員は⟦#KQD⟧人である。」
  EN  "The number of R&D personnel ... was ⟦#PVM⟧."
                                            ↑ 記号が違う ＝ 実量が違う
```

**ID を「表面の数字」ではなく「実量」で振るのが要点です。** これで単位スケールも同じ原理に乗ります。

| 元の表記 | 実量 | 記号 |
|---|---|---|
| `48百万円` / `48 million yen` | 4.8×10⁷ | **同じ** |
| `48百万円` / `48 thousand yen` | 4.8×10⁷ / 4.8×10⁴ | **違う** → 誤りとして出る |
| `12億円` / `1.2 billion yen` | 1.2×10⁹ | **同じ** → 正しい換算なので何も出ない |
| `12億円` / `12 million yen` | 1.2×10⁹ / 1.2×10⁷ | **違う** → 誤りとして出る |

前の版では「単位語はマスクせず平文で残し、単位の誤りはモデルに読ませる」としていましたが、
**実量で ID を振ればその必要がありません**。正しい換算を誤検知することもなくなります。
（単位語自体は読みやすさのため引き続き残します。）

#### 実測: 記号の集合を比べるだけで、誤りだけが出ました

長尺フィクスチャの日英全体について ID の多重集合を作り、差だけを取り出しました。

```
JA にしか無い記号:  312 (p13) / 9.4 (p118)
EN にしか無い記号:  321 (p12) / 4.9 (p117) / 35.2 (p73)
```

**5記号・3件、誤検知ゼロ。** 内訳は

| 記号の差 | 正体 |
|---|---|
| JA 312 ↔ EN 321 | 植え込んだ数値の誤訳（F0005） |
| JA 9.4 ↔ EN 4.9 | 植え込んだ数値の誤訳（F0035・桁の入れ替え） |
| EN にだけ 35.2 | 原文に無い数値の追加（F0032） |

前の版で唯一の誤検知だった p21/p22（`5,200` と `520.0`）は、
**実量に正規化した時点で一致し、消えました**。単位換算の誤検知が原理的に起きなくなります。

#### ページ対応も diff 整列も要りません

前の版では「ページ対応 → 多重集合比較」、さらにその弱点を突かれて
「文書全体の数値列を diff で整列」としていました。**どちらも不要になります。**

| 版 | 必要なもの | 英訳の改ページがずれたら |
|---|---|---|
| ページ対応＋多重集合 | 正しいページ対応 | **崩壊**（実測 68/138 ページが誤警告） |
| 数値列を diff で整列 | 数値の並び順 | 耐える |
| **記号の集合を比較（本版）** | **なし** | **そもそも順序も位置も見ていない** |

順序にも位置にも依存しません。**集合の差を取るだけ**です。

#### 分担

記号の差は**値を一切知らなくても計算できます**（記号を数えるだけ）。
だからこの部分はローカルに置き、モデルには「その差が誤りか」の判断だけを任せます。

| 担当 | やること | 性質 |
|---|---|---|
| **ローカル** | 文書全体で ID の多重集合の差を取る | 網羅的・決定的。窓の制限なし |
| **モデル** | 差の1件ずつについて、同じ箇所を指しているか／誤りかを判断する | 意味の判断。得意な仕事 |

前の版にあった「単位換算表を持つ照合エンジン」は**不要**になります。
単位の知識は**マスカー側**（ID を振るとき）へ移ります。マスカーはどのみち単位を読む必要があるので、
仕事が増えるのではなく、置き場所が正しくなります。

#### 実物の決算短信で確かめた（2026-08-04）

マツダ株式会社 2027年3月期第1四半期決算短信の**日英そろい**（JA 14p / EN 15p、実物）で
同じ比較を走らせました。合成フィクスチャでは出なかった問題が3つ見つかりました。

| 見つかったこと | 内容 | 対処 |
|---|---|---|
| **浮動小数点は使えない** | `32.8×10⁹` が `32799999999.999996` になり、`32800000000` と別記号になった | **10進固定小数（Decimal）で計算する**。float は禁止 |
| **柱が日英で違う** | JA は全ページに `マツダ㈱(7261) 2027年３月期…` があり、EN には無い。証券コード `7261` だけで11件の差 | 柱・フッタは §4.2 の構造番号として除外（§3.3 の教訓と同じ） |
| **表のセルが連結する** | `285,700` と `1,285,700`、`434,300` と `4,434,300`。隣のセルの数字が頭にくっつく | **数値の切り出しは座標を見て行う**。テキストの並びだけで切ると偽の数値ができる |

3つとも直したうえで残った差は **JA 15種 / EN 11種**。そのうち

- **スケール語が片側だけ数値に付いていた（＝単位が見出しにある）ものは 2種だけ**でした。
- 残りは、日本語版にしかない補足表など**内容そのものの差**とみられます
  （決算短信の英訳は要約版になることがある）。

> つまり「単位が見出しにあると実量が揃わない」という前の版の懸念は、
> **実物では 15件中 2件**でした。ご指摘のとおり**まれ**です。
> 英訳は原文の表をそのまま写すので、単位の置き方も揃うのが普通、という理解で正しいです。
> 丸めについても、実物では有効桁を落とした表記は見つかりませんでした。
> どちらも**優先度を下げます**（対処はするが、これが理由で設計を変える必要はない）。

一方で、上の表の3つは**実物でしか出ませんでした**。合成フィクスチャは
「日英で数値を必ず揃える」ように作ってあるので、当然です。
**実装前に、必ず実物1組で同じ確認をしてください。**

> **限界**（正直に書いておきます）
> - **日英とも同じ誤りがある場合は出ません**（記号が両側で一致するため）。
>   ただしこれは §6.1c で拾えます（後述）。

### 6.1c 跨ぎ整合: 「同じ値には同じ記号」を使う

#### 整合性チェックには REF を渡しません（構成の変更）

日英とも同じ誤りは、REF と突き合わせても**原理的に出ません**。
しかし**英訳文書の中だけを見れば出ます**——p3 と p10 で同じ営業利益に違う記号が付いていれば、
REF が無くても矛盾だと分かるからです。

そこで2つのモードで渡すものを変えます。

| モード | 渡すもの | 見つけるもの |
|---|---|---|
| **校正（10ページ）** | TARGET ＋ REF | 訳の誤り。原文と突き合わせる必要がある |
| **整合性（広い幅）** | **TARGET のみ** | 文書内の自己矛盾。原文は要らない |

REF を外す利点は3つあります。

1. **原理的に必要ない。** 自己矛盾の検出に原文は使いません。
2. **同じ添付サイズで TARGET を倍近く入れられます。**
   跨ぎの検出は幅で決まるので、**到達できる距離がそのまま伸びます**（要実測）。
3. **タスクが純化します。** 実測で整合性モードは「REFと突き合わせて」という指示のせいで
   英語単体の観点を一切見ませんでした（綴り12.5% / 文法0%）。
   REF を外せば「この文書は自己整合的か」だけを問う形になります。

`docs/benchmarks/README.md` に構成 `consistency-noref` を追加して測ります。**未測定**。


**マスキングは、跨ぎ整合にとっては制約ではなく武器になります。**

現状この観点は最も弱く、実測で **drift 18.8% / 跨ぎ数値 0%** です。
理由は、モデルが100ページ離れた `32,450` を覚えていられないからです。**記憶の課題**なので苦手です。

§4.4 のとおり**同じ正規化値には文書を通じて同じ ID を振る**ので、こうなります。

```
  p3   「営業利益は⟦#QAF⟧百万円です。」
  p10  「営業利益⟦#MRT⟧百万円の内訳は以下のとおりです。」
                    ↑ 同じ営業利益を指しているのに記号が違う ＝ 値が違う
```

モデルがやることは「両方とも営業利益を指しているか」という**意味の判断（得意）**と、
「⟦#QAF⟧ と ⟦#MRT⟧ が同じか」という**記号の照合（ほぼ自明）**の2つだけになります。
**記憶の課題が記号照合の課題に変わる**——これが本質です。

#### さらに: 窓の制限を外せる

ID は値を漏らさないので、**全パケットに「ID の出現表」を同梱できます**。

```
  ⟦#QAF⟧ … p3, p47
  ⟦#MRT⟧ … p10
```

値を一切書かずに「この記号は文書のどこに出るか」だけを渡せます。
**マスクしていない現状では、これは不可能です**（数値そのものを載せることになるため）。
つまり**マスキングによって初めて、窓を越えた整合チェックの材料を安全に渡せる**ようになります。

#### 候補はローカルでも作れる（実測: 4組中2組、要改良）

「同じ語のそばに違う値がある」箇所を、文書全体から機械的に拾えるかを試しました。
内容語2語をキーに、数値の前後70文字を見て索引を作り、
「値が2種類以上・3ページ以上離れている」ものを候補にします。

| | 結果 |
|---|---|
| 候補の数 | **79件**（モデルに渡す確認リストとして現実的な分量） |
| gold の跨ぎ4組のうち候補に入った | **2組**（`research and development expenses` 17,400/17,900、`overseas net sales` 38.4/34.8） |

取りこぼした2組は、キーと数値の距離が70文字をわずかに超えていました
（`patents held by the Group ... was 1,860`）。**窓を広げれば改善する見込み**です。

この方式の位置づけは「**ローカルが候補を広く拾い、モデルが絞る**」です。
ローカル側は recall を優先してよく（誤候補はモデルが落とす）、
モデル側は「その2つは同じものを指しているか」という得意な判断だけを担います。

> ⚠️ 素朴な n-gram では雑音が多く出ました（セグメント表の同じ見出しが
> 正当に別の値を持つケース）。実装には財務用語の辞書か名詞句抽出が要ります。**未着手**。

### 6.3b 実測: 単純な多重集合比較でどこまで行くか（2026-08-04）

長尺フィクスチャの日英139ページ対で、**ページ単位の数値多重集合比較**を実際に走らせました。

| | 結果 |
|---|---|
| 警告を出したページ | **4 / 139** |
| gold の数値系の誤りを検出 | 3 / 10（30%） |
| precision | **75%**（唯一の誤警告 p21 は、フィクスチャ側で文書化済みの既知差分） |

種類別に見ると、何が取れて何が取れないかがはっきりします。

| 種類 | 検出 | 理由 |
|---|---|---|
| `number-local`（ENだけ誤り） | **1/1** | 数値そのものが違うので確実に出る |
| `num-tr`（数値の誤訳） | 2/6 | **残り4件は数字が同じ**（`48百万円`→`48 thousand yen`、`12億円`→`12 million yen`）。数字だけ比べても差が出ない |
| `number`（日英とも誤り・跨ぎ） | 0/3 | **設計どおり**。同じページ内では日英が一致しているので、原理的に見えない |

> ⚠️ 最初の測定では precision 9% でした。原因は**ページ番号**です。
> 日本語版は【表紙】のぶん1ページ多いので、フッタの `- 102 -` と `- 101 -` が
> 全ページで食い違い、40ページを誤警告していました。
> **許可リスト（§4.2 の構造番号）は、送信時のマスクだけでなくローカル照合でも同じものを使う**
> ——これを外すと、照合が丸ごと使い物になりません。

#### 分担がはっきりしました

`num-tr` の取りこぼし4件は、**単位語が違うだけで数字は同じ**というものです。
そして**単位語はマスクしません**（§4.4）。つまりこれは**モデル側が読めます**。

| 誤りの種類 | 見つける担当 | 根拠 |
|---|---|---|
| 数値そのものの違い（`312`→`321`、`9.4%`→`4.9%`） | **ローカル照合** | 実測 precision 75%（実質100%） |
| 単位・スケールの違い（`百万`→`thousand`、`億`→`million`） | **モデル** | 単位語は平文のまま残る |
| 符号の違い（`△` の落ち） | **モデル** | 符号は残し、ID は絶対値（§4.4） |
| 跨ぎ（日英とも誤り） | **どちらも不可** | 別の仕組みが要る（未着手） |

**この2つは重複せず、合わせて `num-tr` を覆います。**
マスキングによって数値照合が弱くなるのではなく、**担当が入れ替わるだけ**だ、というのが実測の結論です。

### 6.4 誤検知への備え

日英で数値の出方が違うのは正常なことも多い（表の合計行の有無、脚注、丸め）ので、
**既定は `needs_human_review: true` の候補**として出し、
確度が高いパターン（同一文脈・同一単位・値だけ違う）のみ確定指摘にします。
`score.mjs` の precision を見ながら閾値を決めます。

## 7. 検出力への影響（予測）

現在の実測値（gold 61件、2026-08-04）を基準に、変化を予測します。
**予測は実測前に書いておきます**（後付けの解釈を避けるため）。

| 観点 | 現在（和集合） | 予測 | 理由 |
|---|---|---|---|
| spelling 綴り | 87.5% | **変化なし** | 数値と無関係。ただし §7.1 の影響を受ける |
| grammar 文法 | 62.5% | **変化なし** | 同上 |
| omission 訳抜け | 100% | **やや低下** | 文単位の訳抜けは残るが、数値だけの脱落は ID で分かるので相殺 |
| num-tr 数値の誤訳 | 100% | **維持〜微減** | ID 不一致で読める（§4.4）。単位換算絡みは human_review へ落ちる |
| うち符号の誤り | — | **変化なし** | 符号は可視文字として残す（§4.2）。ID は絶対値なので符号違いが際立つ |
| name-tr 固有名詞・日付 | 100% | **変化なし** | 日付は許可リストで残す。固有名詞はマスクしない（§0） |
| supply / over | 100% | **やや低下** | 数値を含む補完の妥当性が判断しにくくなる |
| drift 訳語の揺れ | 18.8% | **変化なし** | もともと低い。数値と無関係 |
| 跨ぎ数値（日英とも誤り） | 0% | **上がる可能性** | ローカル照合（§6）は跨ぎでも値を直接比較できる |

### 7.1 本当の危険は「マスキング」ではなく「PDFを送らなくなること」

現在モデルは**紙面（PDF）とテキストの両方**を見ています。PDF をやめると、

- 表の行と列の対応が読めなくなる（数値の意味が分からなくなる）
- 図・脚注の位置関係が失われる
- 「PDF表示で同じ箇所が見えることも確認してください」という現行の指示が成立しなくなる

**この影響はマスキングの影響より大きい可能性があります。** したがって §8 のとおり
**2段階に分けて測ります**。一度に変えると、劣化がどちらのせいか分かりません。

| 段階 | 変更 | 測ること |

### 9.1 テストで必ず押さえること

漏洩は「静かに起きる」ので、テストは**漏れていないこと**を主張する形にします。

1. 長尺フィクスチャ（139/140ページ）全体をマスクし、**出力に許可リスト外の数字が1つも無い**こと。
2. 許可リスト（年・固定表現・構造番号）が**残っている**こと。
3. 同一値 → 同一 ID、異なる値 → 異なる ID が、日英をまたいで成立すること。
4. ID が出現順でないこと（順序から値を推測できないこと）。
5. マスク → アンマスクで**元の文字列に完全一致で戻る**こと（全ページで）。
6. 検証器が、わざと数字を残したテキストを**拒否する**こと（＝送信を止めること）。
7. 辞書ファイルが送信物に含まれないこと。
8. **パーサの既定値を固定していること**（§3.3 で3つとも実害があった）。
   `ocr_enabled=False` / `output_format="markdown"` / `keep_headers_footers=True`。
   特に3つ目は、外すと数値の1/3が警告なしに消えます。
   **140ページの数値の総数が PyMuPDF の素抽出と一致すること**をテストで固定します。
9. **「―」（該当なし）を負号と取り違えないこと**（§3.5 の副産物）。
   実測で `減損損失 ―` が `減損損失 -1,240` になり、存在しない負数が生まれました。
10. **数値の並び順が紙面と一致すること**。日英のプレースホルダー列を位置で突き合わせる
   検査が、並び順に依存するためです（Docling は実測 0/8 でここが崩れました）。
