# 数値マスキング仕様書（外部送信前のプレースホルダー化）

状態: **草案**（実装前）。合意を取ってから着手する。
背景: Copilot は Microsoft の外部サーバーで動く。現在は **PDF をそのまま添付している**ため、
文書の中身が丸ごと社外に出ている。機密管理上、数値を外部へ出さないようにしたい。

---

## 0. 適用範囲: 数値のみ（決定済み）

隠すのは**数値だけ**です。会社名・拠点名・取引先名・役員名・戦略やリスクの記述文・
ファイル名は、これまでどおり外部へ送られます。これは仕様上の割り切りであって、
実装漏れではありません。

将来これを広げる場合に備えて、プレースホルダーの形式は種別を持てるようにしておきます（§4.3）。

---

## 1. 現状（実装の事実）

送信物は3点セットで、`attach_mode = 'pdf'` のとき**すべて添付**されます。

| # | 中身 | 作っている場所 | 外部へ出るもの |
|---|---|---|---|
| A | 確認用PDF（対象ページ＋REF候補ページを1本に綴じたもの） | `buildReviewPacketPdfBytes()` | **紙面そのもの。表も数値も画像として全部** |
| B | 抽出テキスト（TEXT サイドカー） | `buildPacketTextSidecar()` → `extractTextLayerText()`（PDF.js のテキストレイヤ） | 本文テキスト全部 |
| C | 依頼文（プロンプト） | `buildPacketPromptText()` / `buildConsistencyPromptText()` | 指示文・ページ表・ファイル名 |

- クライアント → `POST /api/review/jobs` に `pdf_base64` / `text` / `prompt` を渡す（`index.html:5034` 付近）。
- サーバは `<job>/` 配下にファイルとして保存し（`Server.ps1:120-160`）、
  `ReviewJob.ps1:384-408` が Copilot へ添付する。
- 戻ってきた `quote` は PDF のテキストレイヤと突き合わせてハイライト位置を出す。

**したがって「数値を隠す」には A を送るのをやめる必要があります。** PDF を送る限り、
どんなマスキングをしても紙面に数値が写っています。これが本変更の最大の帰結です。

## 2. 変更の全体像

```
  現在:  PDF ─────────────────────────────► Copilot
         抽出テキスト（PDF.js）────────────►

  変更後: PDF ──► パーサ ──► 構造化テキスト ──► マスカー ──► 検証 ──► Copilot
                              │                    │            │
                              │                    └─ 辞書（ローカルのみ・外部へ出さない）
                              │                                  │
                              └──────────► ローカル数値照合 ◄────┘
                                              （日英の数値を機械的に突き合わせる）
```

3つの新しい部品が要ります。

| 部品 | 役割 | 置き場所（案） |
|---|---|---|
| **P. パーサ** | PDF → 表構造を保った テキスト/Markdown | ローカル実行（§3） |
| **M. マスカー** | 数値 → プレースホルダー、辞書の作成 | `js/number-mask.mjs`（純関数） |
| **V. 検証器** | 送信直前に「数字が残っていないか」を機械的に確認し、**残っていたら送らない** | `js/number-mask.mjs` |
| **L. ローカル数値照合** | 日英の数値を突き合わせ、外部へ出さずに不一致を見つける | `js/number-audit.mjs` |

## 3. パーサ（PDF → テキスト）

現在の `extractTextLayerText()`（PDF.js のテキストレイヤを視覚行で再構成）は、
**表の構造を失います**。数値は表の中に集中しているので、マスク後は
「どの見出しの数値か」が分からなくなり、モデルは何も判断できません。
そのため表を保てるパーサへ差し替えます。

### 要件

1. **ローカルで完結すること**（クラウドAPIのパーサは、それ自体が漏洩になるので不可）。
2. **日本語を正しくテキスト化できること**（CID埋め込みフォント・全角・濁点）。→ §3.3 で実測: **問題なし**
3. 表をセル構造として出せること（Markdown表 or セル座標付き）。→ §3.3 で実測: **一部壊れる**
4. 見出し階層を保てること。
5. 出力の各要素が **元PDFのページ番号と座標** に紐づくこと。
   ハイライト表示（`highlight_boxes`）は座標が要るので、ここが切れると指摘を紙面上に出せなくなる。
6. Windows・オフラインで動くこと。

### 3.1 前提: ランタイム同梱は可。ただしサイズは膨らませない

配布形態は「`PDF校正アシスト起動.cmd` を叩くだけ」で、中身は **PowerShell 5.1 ＋ 単一HTML** です。
Java / Rust / Python の同梱は**可**ですが、**配布サイズを膨らませない**ことが条件です。
したがって比較軸に「配布サイズ（実測）」を入れます。

### 3.2 候補の比較（2026-08 時点で調査）

| | 実行形態 | ライセンス | 表の扱い | bbox | 追加ランタイム |
|---|---|---|---|---|---|
| **LiteParse**（run-llama） | Rust。CLI / Python / Node / **WASM（ブラウザ）** | Apache-2.0 | **ヒューリスティック**（規則ベース）。Markdown の表として出す | あり（text + bbox の JSON） | **不要**（WASM を同梱） |
| **Docling**（IBM/DS4SD） | Python | MIT | **TableFormer**（学習モデル）。「罫線が部分的／無い表、空セル、セル結合、階層」を扱うと明記 | セル対応付けは後処理で PDF セルへ戻す | Python ＋ PyTorch ＋ モデル |
| **OpenDataLoader PDF** | Java エンジン（Python / Node SDK あり） | Apache-2.0（v2.0 で MPL-2.0 から変更） | local モードは規則ベース、hybrid モードで AI バックエンド | あり（JSON に bbox） | **Java 11+**（hybrid は別途 Python サーバ） |
| **MinerU**（opendatalab） | Python（CPU可・GPU推奨） | MinerU OSS License（Apache-2.0 ベース） | VLM ベース。**財務文書・複雑な表に強い**と主張 | あり | Python ＋ 1.2B VLM |
| PyMuPDF / pdfplumber | Python | AGPL / MIT | 罫線検出に依存 | あり | Python |

### 3.3 LiteParse を実際に走らせた結果（2026-08-04 実測）

長尺フィクスチャ（139/140ページ、Chromium 印刷・IPAGothic 埋め込み）を
`liteparse 2.11.0` にかけました。**以下は引用ではなく、この環境で実行した結果です。**

#### 日本語のテキスト化は問題なし

```
140ページ / 0.11秒。OCR不要。
  株式会社アオイ精機 2026年3月期（第73期）
  3 事業の内容 - 電子部品事業
  当連結会計年度における当該事業の従業員数は243人であり、主要な生産拠点はタイ工場である。
  当連結会計年度の研究開発人員は312人である。
```

濁点・全角括弧・漢数字・桁区切りカンマ、いずれも崩れませんでした。
**日本語文章のテキスト化は懸念不要**というのが結論です。

ただし、実運用で必ず踏む落とし穴が2つありました。**どちらも既定値の問題です。**

1. **`ocr_enabled` の既定が `True`**。テキストが取れる PDF でも OCR 経路に入り、
   `tessdata` をネットから取りに行きます。取れないと `ocr_failure_fatal` の既定が `True` なので
   **parse 全体が例外で落ちます**（実測: HTTP 403 で140ページ全滅）。
   → オフライン運用では **`ocr_enabled=False` を明示**するか、tessdata を同梱する。**必須設定**。
2. **`output_format` の既定が `json`**。この状態だと `page.markdown` が**空文字**で返り、
   表が1つも出てきません。実際これで一度「表が取れない」と誤診しかけました。
   → **`output_format="markdown"` を明示**する。

#### 表: 壊れるのは「2列のラベル｜値」表で、罫線が無いとき

長尺フィクスチャ（**全セルに罫線あり**）で、表を含む75ページのうち
**8ページ（11%）で値が全部欠落**しました。しかも不安定です。
同じレイアウトの隣り合うページで結果が割れます。

```
p71（正しい）                          p72（壊れた）
| 建物及び構築物（百万円） | 14,000 |   | 建物及び構築物（百万円） |  |
| 機械装置（百万円）     | 27,700 |   | 機械装置（百万円）     |  |
| 従業員数（人）        |    689 |   | 従業員数（人）        |  |
                                       10,600 8,100 4,200 537   ← 値が段落へ落ちた
```

罫線あり／なしを揃えた対照実験（同じ表を3ページずつ）で、原因が切り分けられました。

| 表の形 | 罫線あり | 罫線なし |
|---|---|---|
| **2列（ラベル｜値）** | ✅ 行の対応は保つ（ただし空列が3本入る） | ❌ **ラベル行と値行が完全に分離** |
| 4列（セグメント表） | △ 空列が1本混入 | ✅ **むしろ綺麗に4列** |

罫線なし2列表の実際の出力:

```
建物及び構築物（百万円） 機械装置（百万円） 土地（百万円） … 従業員数（人）

14,000 27,700 7,900 1,250 3,480 54,330 689
```

**ラベルと値が別の段落に分かれ、対応が失われています。** マスクするとこうなります。

```
建物及び構築物（百万円） 機械装置（百万円） … 従業員数（人）
⟦#QAF⟧ ⟦#MRT⟧ ⟦#BXK⟧ ⟦#LDW⟧ ⟦#JVN⟧ ⟦#PSC⟧ ⟦#HGE⟧
```

モデルに渡せる情報が何も残りません。**有報の【表紙】【設備の状況】がまさにこの2列形式**なので、
実務では確実に踏みます。

参考までに、OpenDataLoader が公表している
「複雑な表で table accuracy **0.489（規則ベース）→ 0.928（AI）**」という比較とも整合します。
Docling の TableFormer は「partial or no borderlines, empty cells, cell spans and hierarchy」を
扱うと技術報告書に明記があり、この2列問題に効くと期待できます
（代償は 0.6〜1.3ページ/秒・メモリ約6GB）。

#### 救いになる事実: 数値そのものは1つも失われていない

壊れたのは**対応関係だけ**で、数値は全部テキストに残り、**順序も保たれています**。
これは重要で、**ローカル数値照合（§6）は表崩れの影響を受けません**。
§6 はページ単位で数値の多重集合を比べるだけなので、
「どの見出しの数値か」を必要としないからです。

つまり表崩れで失うのは、**マスク後のモデルが「どのラベルの値か」を判断する材料**だけです。

### 3.4 配布サイズの実測（2026-08-04 計測）

npm レジストリと HuggingFace から実ファイルを取って測りました。**推定ではなく実測値**です。

| 部品 | 実測サイズ | 備考 |
|---|---|---|
| LiteParse WASM `liteparse_wasm_bg.wasm` | **5.09 MB** | ＋ JS 40KB。同梱ファイルはこの2つだけ |
| LiteParse Node ネイティブ `@llamaindex/liteparse` | 33.2 MB | 全プラットフォーム分を含む。Windows だけなら数MB |
| onnxruntime-web `ort-wasm-simd-threaded.wasm` | **12.86 MB** | ＋ ローダ JS 約1MB。パッケージ全体137MBは各種ビルドの寄せ集めで、配るのは1本 |
| TableFormer 公式 `tableformer_fast.safetensors` | **138.7 MB** | accurate 版は 202.9 MB。リポジトリ全体342MB |
| **PyTorch を含む Docling 一式** | **GB級** | 公開されている Docker 実測で 9.74GB、CPU版に絞っても約5.5GB |

**PyTorch を入れた時点でGB級になります。** サイズ制約から、Docling を**公式の経路のまま**
同梱するのは現実的ではありません。

#### ONNX 化すればモデルだけ持ってこられる（ただし要検証）

TableFormer は PyTorch がなくても **onnxruntime だけで動かせるはず**です。
その場合の内訳は `onnxruntime-web 12.9MB ＋ TableFormer 139MB` で、**約150MB**。
PyTorch 一式（GB級）とは2桁違います。しかも onnxruntime-web ならブラウザで動くので、
**ランタイムのインストールが要りません**（現行の配布形態を1ミリも変えずに済む）。

> ⚠️ HuggingFace に第三者の変換版（`asmud/ds4sd-docling-models-onnx`, CDLA-Permissive-2.0）が
> ありますが、**accurate 版と fast 版が両方とも 1,048,990 バイトで完全に同じサイズ**でした。
> 元が 202.9MB と 138.7MB で大きさが違うモデルなので、これは辻褄が合いません。
> INT8 量子化でも縮むのは4倍程度で、200倍は縮みません。**使える中身ではない可能性が高い**ので、
> これに依存する計画は立てません。**ONNX 変換は自前で行い、変換後の精度を実測で確認します。**

#### 参考: ランタイムを別プロセスで持つ場合の目安

| 方式 | 目安 | 備考 |
|---|---|---|
| jlink で削った JRE（OpenDataLoader local） | 40〜60MB（**要実測**） | Java 側だけ。hybrid にすると Python も要る |
| Python embeddable ＋ numpy/opencv/onnxruntime | 80〜120MB（**要実測**） | PyTorch を入れなければこの程度に収まる |

### 3.5 方針: サイズの段で3案を持ち、上から試す

| 案 | 構成 | 配布サイズ | ランタイム導入 | 表 |
|---|---|---|---|---|
| **A** | LiteParse WASM のみ | **約5MB** | 不要 | 罫線なし2列表が壊れる（§3.3 実測） |
| **A′** | A ＋ **2列表の自前復元**（座標クラスタリング） | **約5MB**（コードのみ増） | 不要 | A の唯一の穴を塞ぐ |
| **B** | A′ ＋ onnxruntime-web ＋ TableFormer(ONNX 自前変換) | 約150MB | **不要**（全部ブラウザ内） | TableFormer 相当 |
| **C** | Python embeddable ＋ onnxruntime ＋ Docling のパイプライン（PyTorch 抜き） | 250MB〜 | 同梱Pythonを起動 | Docling 相当 |

**§3.3 の実測を踏まえ、本命は A′ です。** 実測で判明した穴は
「罫線なしの2列（ラベル｜値）表でラベル行と値行が分離する」という**一点**であり、
表全般が駄目なわけではありません（4列表はむしろ罫線なしのほうが綺麗に出た）。
LiteParse は `emit_word_boxes` で語ごとの座標を返すので、
**x座標のクラスタリングで2列に割り直す**のは数十行で書けます。
150MB のモデルを持ち込む前に、まずこれを試すべきです。

B は A′ でも足りなかったときの受け皿で、**ランタイム導入ゼロのまま**精度だけ上げられます。
C は B の ONNX 変換が失敗した場合の最後の手段。

**Docling を公式経路（PyTorch）で同梱する案は、サイズ制約により却下します。**
OpenDataLoader は、精度を取るなら hybrid が要り Java ＋ Python の二重ランタイムになるため、
B より不利。MinerU の 1.2B VLM は CPU 速度・サイズとも本件の制約に合いません。

> B の onnxruntime-web でスレッド版 wasm を使う場合、`SharedArrayBuffer` のために
> COOP/COEP ヘッダが要ります。配信しているのは自前の PowerShell サーバ（`Server.ps1`）なので、
> ヘッダは付けられます。付けられない場合は非スレッド版に落とす（遅くなるが動く）。

### 3.6 評価の手順（段階0）

同じ入力で A → B（→ C）の順に測ります。判定は「読めるか」ではなく**セル単位で正しいか**です。

1. 入力は2種類。
   - 長尺フィクスチャ（139/140ページ）。**ただし現在のフィクスチャの表は全セルに罫線があります**
     （`build-long-fixture.mjs` の CSS が `th, td { border: 1px solid #999 }`）。
     このままでは規則ベースのパーサが実力以上に良く見えます。
     → **罫線なし版の表を追加する**（`table.plain` を用意し、財務表の半分をそちらにする）。
   - 実物の有価証券報告書（英訳版・日本語版）を1組。こちらが本番条件。
2. 測る指標。
   - **セル一致率**: 正解の (行, 列, 値) 集合とパーサ出力の一致率。
   - **数値の取りこぼし率**: 原文に存在する数値のうち、出力に現れなかった割合。
     マスキングでは数値が消えることが致命的なので、これを独立に測ります。
   - **見出し帰属の正しさ**: 各数値が属する行見出し・列見出しが復元できているか。
   - 速度（139ページの処理時間）とメモリ。
   - **配布サイズ**（同梱するファイルの合計）。
3. 合否ライン（案）。
   - 数値の取りこぼし率 **1%未満**（取りこぼした数値は照合対象から丸ごと落ちる）。
   - 見出し帰属の正しさ **95%以上**。
   - 139ページを **3分以内**（現行の全体所要が約24分なので、その1割程度に収めたい）。

### 3.7 移行の逃げ道

A・B・C のいずれも合否ラインに届かない場合、現行の `extractTextLayerText()` を使い続け、
**表だけ PDF.js の item 座標からグリッドを復元する**折衷案があります
（x 座標のクラスタリングで列を、y 座標で行を推定する）。
検出力は落ちますが、**外部送信の安全性は変わりません**。マスキングは予定どおり進められます。

## 4. マスキング仕様

### 4.1 基本方針: フェイルクローズ

**既定は「マスクする」。許可リストに一致したものだけを残す。**
逆（既定は残す・危ないものを隠す）にすると、パターンの書き漏れがそのまま漏洩になります。

### 4.2 残す数値（許可リスト）

「文書の構造や固定表現の一部であって、事業データではない数値」だけを残します。

| 種別 | 例 | 備考 |
|---|---|---|
| 西暦・和暦の年 | `2026年` `令和8年` `FY2026` `2026` | 利用者が「機密でない」と明示 |
| 月日 | `6月26日` `June 26` | 年と同じ扱い |
| 固定表現に含まれる数字 | `一株当たり` `第2四半期` `第1条` `二重` `三菱` `一部` | **語として**の数字。辞書で列挙する |
| 構造番号 | 見出し番号 `(12)` `4.` 、注番号 `注1` 、ページ番号 `P.48` | 依頼文が参照するので必須 |
| 規格・様式番号 | `ISO 9001` `様式第三号` | 公知 |

**残さないもの（＝マスクする）の例**: 金額、株数、人数、比率・％、日数・時間、
持株比率、電話番号・郵便番号、証券コード、従業員数、セグメント別数値、
`100.0%`（子会社の持分比率は事業データ）。

#### 符号は残す（利用者の指示）

正負の情報は機密でないため、**符号は可視文字としてそのまま残します**。
日本語会計で使う負号は複数あるので、すべて対象です。

| 表記 | 例 | マスク後 |
|---|---|---|
| △ | `△1,234百万円` | `△⟦#QAF⟧百万円` |
| ▲ | `▲567` | `▲⟦#MRT⟧` |
| ASCII マイナス | `-890` | `-⟦#BXK⟧` |
| 全角プラス | `＋12.3％` | `＋⟦#LDW⟧％` |
| 括弧書き（英文会計の負） | `(1,234) million yen` | `(⟦#QAF⟧) million yen` |

実測で、`△ ▲ - ( ) ＋` はいずれも PDF 抽出で保持されることを確認しました
（`−` U+2212 だけは抽出時に ASCII `-` へ正規化される。マスカー側も NFKC 正規化してから扱う）。

**符号を残すことで得られるもの**: 利益と損失の取り違え、増減の向きの誤りが、
モデルに**読める文字として**残ります。マスクしていなかったときと同じ精度で指摘できます。

> 括弧は数字ではないのでマスク対象外です。したがって `(1,234)` は自然に `(⟦#…⟧)` になり、
> 構造番号の `(12)` は許可リストで数字ごと残るため、両者は取り違えません。

> ⚠️ 許可リストは**設定ファイルで編集できる**ようにします（`config/masking.json`）。
> 業種や文書によって「年は隠したい」「様式番号も隠したい」が変わるためです。
> 既定は上表。編集した内容はログに残します。

### 4.3 プレースホルダーの形式

```
  ⟦#ABC⟧        数値プレースホルダー（ID は英字のみ）
```

**ID に数字を使いません。** これで検証器（§4.5）が
「マスク後のテキストに残っている数字は、許可リストに一致するものだけ」を
単純な正規表現で確認できます。ID に数字を混ぜると、この検査が成立しなくなります。

種別を増やす場合は接頭辞で分けます（将来、固有名詞まで広げる場合）:
`⟦#ABC⟧` 数値 / `⟦@ABC⟧` 組織名 / `⟦^ABC⟧` 人名 / `⟦*ABC⟧` 地名。

### 4.4 ID の採番規則（この仕様の要）

**同じ正規化値には、日英を通じて同じ ID を振ります。**

```
  「当連結会計年度の研究開発人員は312人である。」   →  「…研究開発人員は⟦#KQD⟧人である。」
  "The number of R&D personnel ... was 321."        →  "… was ⟦#PVM⟧."
                                                          ↑ ID が違う ＝ 数値が違う
```

これにより、**モデルは値を知らないまま数値不一致を指摘できます**。
実測で 100% 取れていた `num-tr`（数値の誤訳）の相当部分が、この仕組みで生き残ります。

正規化のルール:

- 全角→半角（NFKC）、桁区切りカンマ除去、前後の空白除去。
- `48` と `48.0` は同一値として同じ ID。
- **ID は絶対値で採番する**。符号は §4.2 のとおり外に残すので、
  `△1,234` と `1,234` は**同じ ID ＋ 異なる符号文字**になります。
  これにより「日本語は `△⟦#QAF⟧` なのに英訳は `⟦#QAF⟧`」＝**符号の落ちが一目で分かります**。
  逆に絶対値ではなく符号込みで採番すると、符号違いが単なる「別の ID」に化けて、
  値そのものが違う場合と区別できなくなります。
- **単位語はマスクしない**。`48百万円` → `⟦#KQD⟧百万円`、`48 thousand yen` → `⟦#KQD⟧ thousand yen`。
  これで **単位スケールの誤り（百万 vs thousand、億 vs million）はモデルが読める文字として残ります**。
  実測で取れていた F0015 / F0021 はこの経路で維持されます。
- ID は**ジョブごとに毎回振り直す**（同じ値がいつも同じ ID だと、複数文書を突き合わせて値を推定できてしまう）。
- ID 空間は十分に広く取り、**出現順に振らない**（出現順だと大小関係が推測できる）。ランダム割当。

#### この採番でも取れないもの

| 状況 | 例 | 扱い |
|---|---|---|
| 正しい単位換算で数値が変わる | `12億円` → `1.2 billion yen` | ID が違うので**誤検知になる**。単位語が異なるときは断定させない（§5）／実値の換算はローカル照合が持つ（§6.2） |
| 端数処理 | `458,921百万円` → `458.9 billion yen` | 同上 |
| 数詞が語で書かれている | `3社` → `three subsidiaries` | マスク対象外の語なので ID が付かない |

### 4.5 送信前検証（ブロッキング）

マスク後のテキスト・プロンプトに対して、送信直前に必ず実行します。

1. 許可リストに一致しない数字が1つでも残っていたら、**そのパケットを送らずにジョブを失敗させる**。
   画面には「マスクできない数値が P.○ に残っています」と、**位置だけ**を出す（値は出さない）。
2. プレースホルダーの形式が壊れていないこと（`⟦#[A-Z]{3,}⟧` 以外の `⟦` `⟧` が無いこと）。
3. 辞書に載っていない ID がテキストに無いこと（＝復元不能な残骸が無いこと）。
4. **PDF が添付対象に入っていないこと**（`attach_mode` が `masked-text` のときは `pdf_path` を空にする）。

検証は「警告」ではなく「中止」にします。ここを警告にすると、
急いでいるときに素通りして漏洩します。

### 4.6 復元（アンマスク）

- 辞書 `⟦#ABC⟧ → "312"` は **ジョブディレクトリ内のローカルファイル**に保存し、
  外部へは一切送りません。ジョブ完了時（または保持期間経過時）に削除します。
- 復元が要る箇所:
  - `quote`（ハイライト照合と画面表示の両方）
  - `suggestion`（修正案）
  - `reference_quote`
  - `issue_summary` / `reason`（モデルが本文中の ID を引用することがある）
- **モデルは数値を発明できない**ので、`suggestion` に新しい数値が必要な指摘（例:「312 に直すべき」）は
  出せません。代わりに `⟦#ABC⟧`（＝REF側のプレースホルダー）を指す形で出させ、
  復元時に実値へ戻します。プロンプトに明記が要ります（§5）。
- 復元後に **ID の残骸が無いこと**を確認し、残っていたら `quality_warning` を立てます。

## 5. プロンプトの変更

現行の指示文に次を足します。

- 「本文中の `⟦#XXX⟧` は数値を伏せたプレースホルダーです。**同じ ID は同じ数値**、
  **違う ID は違う数値**を意味します。」
- 「数値そのものを推測・生成しないでください。修正案で数値を指す必要があるときは、
  対応するプレースホルダーをそのまま書いてください。」
- 「TARGET と REF で対応する箇所の ID が違う場合は `number_mismatch` として指摘してください。」
- 「`△` `▲` `-` `(...)` は負を表します。**ID が同じでも符号が違えば誤り**です（利益と損失の取り違え）。`number_mismatch` として指摘してください。」
- 「ただし**単位語が異なる場合**（`⟦#A⟧億円` と `⟦#B⟧ million yen` など）は、正しい換算かどうかを
  判断できません。`needs_human_review: true` にして、断定しないでください。」
- 「プレースホルダーを quote に含めるときは、**1文字も変えずに**コピーしてください。」

`buildPacketPromptText()` / `buildConsistencyPromptText()` の両方に入れます。

## 6. ローカル数値照合（外部へ出さない検査）

マスキングで失うものを取り戻すのではなく、**もともとこちらでやるべきだった検査**です。
数値の一致は決定的に判定できるので、LLM より確実です。

### 6.1 入力

- TARGET ページの数値リスト（値・単位・座標・前後の文脈）
- 対応する REF ページの数値リスト（ページ対応は既存の「REF候補ページ」を使う）

### 6.2 判定

1. **ページ単位の多重集合比較**。同一ページ対で、正規化した数値の出現回数を日英で比較する。
   片側にしか無い値・回数が違う値を候補として出す。
   > この方式は既に `docs/benchmarks/fixtures/build-long-fixture.mjs` で実装・実運用しており、
   > フィクスチャ生成の実バグ（139ページ全部の数値不一致）を検出した実績があります。
2. **単位換算を考慮した照合**。`千/万/億/兆` ↔ `thousand/million/billion/trillion`、
   `%`、`人/株/円/ドル` の対応表を持ち、換算後に一致すれば正常とする。
3. **語で書かれた数詞**（`3社` ↔ `three subsidiaries`）を数値化して比較する。

### 6.3 出力

`findings` と同じ形で、`source: "local"` を付けて統合します。画面上は
「ローカル照合」バッジを出し、Copilot 由来（`source: "llm"`）と区別できるようにします。

### 6.4 誤検知への備え

日英で数値の出方が違うのは正常なことも多い（表の合計行の有無、脚注、丸め）ので、
**既定は `needs_human_review: true` の候補**として出し、
確度が高いパターン（同一文脈・同一単位・値だけ違う）のみ確定指摘にします。
`score.mjs` の precision を見ながら閾値を決めます。

## 7. 検出力への影響（予測）

現在の実測値（gold 61件、2026-08-04）を基準に、変化を予測します。
**予測は実測前に書いておきます**（後付けの解釈を避けるため）。

| 観点 | 現在（和集合） | 予測 | 理由 |
|---|---|---|---|
| spelling 綴り | 87.5% | **変化なし** | 数値と無関係。ただし §7.1 の影響を受ける |
| grammar 文法 | 62.5% | **変化なし** | 同上 |
| omission 訳抜け | 100% | **やや低下** | 文単位の訳抜けは残るが、数値だけの脱落は ID で分かるので相殺 |
| num-tr 数値の誤訳 | 100% | **維持〜微減** | ID 不一致で読める（§4.4）。単位換算絡みは human_review へ落ちる |
| うち符号の誤り | — | **変化なし** | 符号は可視文字として残す（§4.2）。ID は絶対値なので符号違いが際立つ |
| name-tr 固有名詞・日付 | 100% | **変化なし** | 日付は許可リストで残す。固有名詞はマスクしない（§0） |
| supply / over | 100% | **やや低下** | 数値を含む補完の妥当性が判断しにくくなる |
| drift 訳語の揺れ | 18.8% | **変化なし** | もともと低い。数値と無関係 |
| 跨ぎ数値（日英とも誤り） | 0% | **上がる可能性** | ローカル照合（§6）は跨ぎでも値を直接比較できる |

### 7.1 本当の危険は「マスキング」ではなく「PDFを送らなくなること」

現在モデルは**紙面（PDF）とテキストの両方**を見ています。PDF をやめると、

- 表の行と列の対応が読めなくなる（数値の意味が分からなくなる）
- 図・脚注の位置関係が失われる
- 「PDF表示で同じ箇所が見えることも確認してください」という現行の指示が成立しなくなる

**この影響はマスキングの影響より大きい可能性があります。** したがって §8 のとおり
**2段階に分けて測ります**。一度に変えると、劣化がどちらのせいか分かりません。

### 9.1 テストで必ず押さえること

漏洩は「静かに起きる」ので、テストは**漏れていないこと**を主張する形にします。

1. 長尺フィクスチャ（139/140ページ）全体をマスクし、**出力に許可リスト外の数字が1つも無い**こと。
2. 許可リスト（年・固定表現・構造番号）が**残っている**こと。
3. 同一値 → 同一 ID、異なる値 → 異なる ID が、日英をまたいで成立すること。
4. ID が出現順でないこと（順序から値を推測できないこと）。
5. マスク → アンマスクで**元の文字列に完全一致で戻る**こと（全ページで）。
6. 検証器が、わざと数字を残したテキストを**拒否する**こと（＝送信を止めること）。
7. 辞書ファイルが送信物に含まれないこと。

## 10. 未決事項

1. **パーサの選定（§3）。段階0の評価を回すまで決まりません。** これが最大の未決事項で、
   結果によっては配布形態（Python 同梱の要否）まで変わります。
2. 罫線なし版フィクスチャの追加（§3.6-1）。現行フィクスチャは全セル罫線ありなので、
   このままでは規則ベースのパーサを過大評価します。
3. 年を残してよいか。利用者は「機密でない」と言っているが、
   未公表の契約年・取得年は機密になり得る。許可リストで切り替えられるようにはする。
4. 辞書の保持期間。ジョブ完了で即削除か、指摘レポートを閉じるまで保持か
   （復元済みレポートを再表示するだけなら不要）。
5. Copilot 側の会話履歴に残るものの扱い（マスク後テキストは残る）。運用ルールとして明文化するか。
