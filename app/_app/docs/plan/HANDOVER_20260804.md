## 1. 今どういう状態か

数値マスキング（`attach_mode = masked-text`）が**既定で有効**です（`index.html` の
`const MASKING_ENABLED = true`）。この状態では:

- Copilot へ送るのは **PROMPT と、数値をプレースホルダー `⟦#XXX⟧` に置き換えた TEXT だけ**。
- **PDF は送りません。** 自動送信も手動ZIPも、どちらもPDFを外します。
- 送信前に `verify()` が走り、伏せ漏れが1つでもあれば**例外で送信を中止**します（警告では済ませない）。
- 戻ってきた指摘は、貼り戻し時にアプリ内の辞書で実数値へ復元します。

辞書は**ブラウザのタブの中にしかありません**。タブを閉じる／再読み込みすると復元できません。
手動ZIPの README にもその旨を書いてあります。

## 2. このセッションでやったこと

### 2.1 実機のマスク実行（利用者が流した分）を検査して直した

すでに開示済みの決算短信で流した成果物を調べ、**5つの欠陥**を見つけて直しました（`1b3ff71`）。

| # | 欠陥 | 実害 |
|---|---|---|
| 1 | 英文表の括弧付き負値が平文で出ていた | `(603) (643) (926) (429)` など**33件が外へ出た**。`verify()` も同じ許可リストを見ていたので**OKと報告していた** |
| 2 | 許可パターンが数値の頭だけを食っていた | `Code No. 7261` → `7261` が残る、`up 1.2%` の "p 1" をページ番号と誤読して `1.2` が残る、`※ 1,234` → `1,234` が残る |
| 3 | プロンプトが、添付していないPDFを参照させていた | 1行目が「添付した確認用PDF『…』を確認してください」のまま。`read_error` か取りこぼしを招く |
| 4 | レポートの「理由」に記号が残っていた | `reason` は戻していたが、レポートが使うのは `displayReason` だった |
| 5 | 手動ZIPには素のPDFとTEXTが入っていた | 3層防御を抜ける経路。READMEどおり手で添付されたら意味がない |

#1 の切り分け方: 見出し番号は**行頭（か `:` 直後）にあって直後が文字**、表の値は**行の途中で直後が数値・記号・行末**。
代償として本文中の章参照 `…the Quarterly Period (3) Future Estimates…` の `(3)` も伏せます。
構造番号がひとつ読めなくなるより、負値がひとつ漏れるほうが重いのでこの向きに倒しています。

#2 の直し方は2つ。`spanCovers()` で「トークン**全体**が許可スパンに収まっているときだけ許可」にしたのと、
ページ番号に `(?<![A-Za-z])` を足したこと（`up` `Group` `top` の末尾の p を拾わないため。
こちらは `p 10` のように全体が収まるので containment では防げません）。

### 2.2 ローカルで校正を回して測った

実機の Copilot は1本20分近くかかるので、**アプリ本体を headless Chromium で動かす**
評価ドライバを作りました（`tools/Eval-Driver.mjs`）。Copilot の役だけをサブエージェントに置き換えます。

26ページのフィクスチャ（gold 30件）・校正10p×3パケット・3条件、各1回:

| 条件 | 検出 (30件中) | 誤検知 |
|---|---|---|
| A: マスクあり（行またぎ修正**前**） | 23 | **1** |
| B: マスクなし（対照） | 24 | 0 |
| **C: マスクあり（修正後）** | **24** | **0** |

数値（numbers）は3条件とも 9/9。**マスキングによる検出力の低下は観測されませんでした。**

### 2.3 その測定で見つけたマスカーのバグを直した（`1eef287`）

条件Aの唯一の誤検知は、モデルではなく**マスカーが原因**でした。

```
その他事業68,921百
万円である。          ← 段組みで「百万」が行またぎ
```

`百万` が繋がっていないため `68,921` を裸の数値として読み、英文 `68,921 million yen`（10⁶倍）と
**別の実量＝別の記号**になっていました。モデルは設計どおり「その他事業だけ記号が違う」と正しく振る舞い、
**正しい訳を誤りとして報告**しました。

> この種の誤りは**モデル側では見抜けません**。記号しか見えない以上、記号が違えば違うと信じるほかない。
> マスカーの実量計算は、検出力そのものより先に守る必要があります。

直し方はスケール語の途中の空白・改行を吸収すること（`百万` → `百\s*万`）。

## 4. 触るときの注意

### 4.1 `js/number-mask.mjs`

- **部分的にマスクしない**のが最優先。実測でモデルが漏れた桁から記号の値を逆算しました。
  一部だけ漏れるのは全部漏れるのと同じです。
- 桁数で構造番号を判定してはいけません（表の2桁データが漏れた実績あり）。**書式で判定**します。
- 許可リストを足すときは `spanCovers()` の性質を思い出してください。頭だけ食うパターンは
  containment で潰れますが、`p 10` のように**全体が収まってしまう**形は潰れません。
- 実量は BigInt のマイクロ単位。**浮動小数点は使わない**（32.8×10⁹ が 32799999999.999996 になった）。
- 触ったら必ず `tools/Test-NumberMask.mjs` を通すこと。

### 4.2 `index.html` のプロンプト

- `MASKING_ENABLED` の分岐が、材料行・作業順・根拠規則・締めの4箇所に入っています。
  片方だけ直すと「PDFを見ろ」と「PDFは無い」が同居します。
- 記号照合の手順 **a〜d を消さないこと**。A/B実測で、これが無い版は `num-tr` が 0/6 でした。
  モデルは「記号が違えば数値が違う」と知っていても、**自分から照合作業をしません**。

### 4.3 指摘の復元

`restoreMaskedFindings` はフィールドを列挙しません。**記号を含む文字列を全部走査**します。
`coerceFindings` に文字列フィールドを足しても自動で拾われますが、
英文の断片（`quote` / `suggestion` / `areaHint`）だけは `EN_FIELDS` に足してください。

## 6. 並列化について（未検証。コードの下調べだけ済み）

「CDPを複数持って Copilot も並列に動かせば速くなるか」という問い。**理屈は通ります。**
パケットは設計上すでに独立で、結果の合流も既にあります（`js/review-merge.mjs`、貼り戻しは累積）。
現状は `proofread10` が14パケット×約80秒で**約19分**。整合性25pと合わせて約24分。
これがワーカー数で割れるなら効果は大きいです。

ただし、実機で確かめないと分からない前提が3つあります。

### 6.1 Copilot 側の同時実行制限（**これが本丸・未知**）

同一ユーザーが並列に投げたとき、テナント側で直列化されるのか、429 が返るのか、
「少し時間をおいてから」表示になるのか。**ここが塞がっていたら他の工夫は無意味です。**
まず2ワーカーで4パケットだけ流して、逐次のときの所要時間と比べてください。

### 6.2 タブが隠れると読めなくなる問題（**一度踏んでいる**）

このセッションの前半で実測しています。アプリ画面のタブと同じウィンドウに Copilot を置いたら、
`visibilityState: hidden` になり、`getBoundingClientRect()` が 0、`innerText` が空になりました。
並列にすると N−1 個が常に非アクティブになるので、この問題が**構造的に効きます**。

対策は入れてあります。

- `Target.createTarget` に `newWindow = $true`（タブではなく**別ウィンドウ**にする）
- `innerText` の代わりに `textContent` へフォールバック（`Get-KoseiLatestResponseText` ほか）
- 開始前に `visibilityState` を見て `Page.bringToFront`

Windows の Chromium は**ウィンドウが完全に隠れると occlusion 判定で hidden にします**が、
これは Edge の起動オプションで既に塞いであります（`CopilotClient.ps1` の `Start-KoseiEdge`）。

```
--disable-background-timer-throttling
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-features=CalculateNativeWinOcclusion,msEdgeTranslate
```

なので**フラグ側は並列化の準備ができています**。残るのは
「並列ウィンドウでも本当に `visibilityState` が `visible` のままか」の実測だけです。
1本流すたびに `visibilityState` をログへ落として確認してください。
既定は `--window-position=-32000,-32000` の画面外配置なので、
そもそも重なりようがない点も味方します（`browser_display_mode`）。

### 6.3 ストール検出のしきい値

`CopilotClient.ps1` のストール判定は**1タブ前提で調整してあります**。
並列にすると1本あたりの生成が遅く見えるので、誤って「停止した」と判定しかねません。
`$stallSec` は応答検出前は2倍にしてありますが、並列時の実測で見直しが要ります。

### 6.4 コードはどこまで並列化に耐えるか（調べた結果）

**思ったより準備ができています。** CDP 層は**すでに呼び出しごとに独立**です。

| 見たところ | 状態 |
|---|---|
| `Invoke-KoseiCdpMethod` / `Invoke-KoseiCdpEval` | `-WebSocketUrl` を**引数で受け取り**、その場で接続して `Dispose` する。共有ソケットは持っていない |
| ジョブ本体 | すでに別 PowerShell インスタンスで非同期実行（`$script:KoseiJobHandles`） |
| ジョブ状態 | `[hashtable]::Synchronized(@{})` なので同時アクセス自体は想定済み |
| パケット | 設計上すでに独立。合流も既にある（`js/review-merge.mjs`、貼り戻しは累積） |

つまり「ワーカーごとに ws URL を持たせて別々に叩く」形には**素直に持っていけます**。
直すべき箇所は限られていて、次の5つです。

| # | 場所 | 何が問題か | どうするか |
|---|---|---|---|
| 1 | `Get-KoseiCopilotPage`（`CopilotClient.ps1:191`） | 条件に合う**最初のページを返す**ので、全ワーカーが同じタブを掴む | ワーカーごとに `Target.createTarget`（`newWindow=$true`）でページを作り、その ws URL を握らせる。掴んだ target id をワーカーに固定する |
| 2 | `$script:KoseiCdpNextId`（同 16行目） | CDPメッセージIDの採番が単なる `+1`。同時に走ると衝突しうる | `[System.Threading.Interlocked]::Increment` にするか、ワーカーごとに採番レンジを分ける（worker0=41000〜, worker1=51000〜 …）。**後者のほうが PS 5.1 では安全で、ログも読みやすい** |
| 3 | `$script:KoseiWindowStateResetDone`（同 18行目） | 1回だけ走らせたい初期化が、ワーカーごとに走る／競る | 起動時に1回だけやる処理として、ワーカー生成の**前**に出す |
| 4 | packetループ（`ReviewJob.ps1:371`） | `foreach` で逐次。`$State.current_packet` が単数 | RunspacePool（`$maxWorkers`）に置き換える。各ワーカーは**自分の `$p` エントリだけ**を触る。`current_packet` は配列にするか `current_packets` を足す |
| 5 | `Write-KoseiLog` | 同時書き込みでログが混ざる／壊れる | `Server.ps1:180` の `$script:KoseiPassStatLock` と同じ形で `[System.Threading.Monitor]` を噛ませる。行頭に `worker=N` を付ける（**付けないと並列時のログは読めません**） |

`Invoke-KoseiCopilotAttachFiles` など DOM を触る関数は全部 `-WebSocketUrl` を引数で取るので、
**関数側の書き換えはほぼ不要**です。呼ぶ側がワーカーごとの ws URL を渡すだけで済みます。

### 6.5 進め方（この順番で）

**先に測るべきものがあります。** masked-text にしたことで**PDFの添付が消えました**。
アップロード待ちがほぼゼロになっているはずで、それだけで何分縮んだかまだ測っていません。
分母が変われば並列化の投資判断も変わります。

| 段 | やること | 決め手 |
|---|---|---|
| **0** | `proofread10` を masked-text で1本流し、**逐次のままの所要時間**を測る | ここが新しい基準線。19分がすでに何分になっているか |
| **1** | 2ワーカーで4パケットだけ流す（コードは手で仮組みでよい） | **§6.1 の同時実行制限。ここが塞がっていたら以降は無意味なので、必ず最初に見る** |
| 2 | 各ワーカーの `visibilityState` をログに落とす | §6.2。`visible` のままか。1つでも `hidden` が出たら配置を見直す |
| 3 | 通るなら 3〜4ワーカーへ。ストール判定の実測値を集める | §6.3。応答が出るまでの実時間の分布 |
| 4 | `ReviewJob.ps1` を RunspacePool 化（§6.4 の #1〜#5） | ここで初めて本実装 |

段1で見るべき失敗のサイン:

- Copilot 側に「少し時間をおいてから」「リクエストが多すぎます」の類が出る
- 2ワーカーの所要時間が逐次の**半分にならず、ほぼ同じ**（＝テナント側で直列化されている）
- 片方の応答が途中で止まる（§6.2 の再発か、同時実行制限の別の出方）

段1が通れば期待値は**ワーカー数にほぼ比例**（19分 → 5〜6分）。
塞がっていたら 1.0 倍で、それ以上は何をしても伸びません。

### 6.6 やらないほうがいいこと

- **1つのウィンドウに複数タブを並べる。** §6.2 で一度踏んでいます。必ず `newWindow=$true`。
- **Edge を複数プロセス起動する。** `--user-data-dir` が同じだと片方が既存プロセスに合流して
  CDPポートが取れません。プロファイルを分けるとサインインもやり直しになります。
  **1プロセス・複数ウィンドウ**が正解です。
- **同時実行制限を測る前に RunspacePool を実装する。** 段1で塞がっていたら全部無駄になります。

### 6.4 やる順番の提案

1. **まず masked-text の効果を測る。** PDFを送らなくなったので添付が消え、
   アップロード待ちがほぼゼロになっているはずです。**並列化する前に、これだけで
   何分縮んだかを測ってください。** 分母が変われば並列化の投資判断も変わります。
2. 2ワーカーで4パケット。6.1 の同時実行制限を見る。
3. 通るようなら 3〜4ワーカー。6.2 のウィンドウ可視性を `visibilityState` のログで監視する。
4. `ReviewJob.ps1` のループを runspace 化。ワーカーごとに CDP セッションとウィンドウを持たせる。

期待値は、6.1 が塞がっていなければ**ワーカー数にほぼ比例**（19分 → 5〜6分）。
塞がっていたら 1.0 倍で、それ以上は何をしても伸びません。**先に 6.1 を測ってください。**
