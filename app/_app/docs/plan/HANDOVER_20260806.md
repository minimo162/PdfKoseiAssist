# 引き継ぎ書 2026-08-06 — 指摘レポートの「該当箇所へ飛べるか」

前日（[HANDOVER_20260805.md](HANDOVER_20260805.md)）の続き。この日はモデルへの指示は触っていない。
**書き出した指摘レポートから、指摘の両側（自分側と相手側）を確認できるか**だけを扱った。

## 1. 何が問題だったか

整合性レビューの指摘は「離れた2箇所が食い違う」という対である。
ところがレポートのレコードは**片側（page / quote）しか持っていない**。相手側は理由文の中にしかない。

> P.96では当期のorders receivedを478,600 million yenとしており、P.6の476,800と一致しない。

実測（200ページ・63件）で **63件中57件が理由に相手ページ `P.N` を含んでいた**。
それなのにレポートから飛べるのは自分側だけで、相手ページは利用者が手で探すことになっていた。
2箇所を見比べるのが整合性レビューの仕事なので、これは機能として欠けている。

## 2. 入れたもの

### 2.1 相手側へのジャンプ（`attachCounterpartHighlights`）

書き出し時に理由文から相手ページと相手側の位置を割り出し、`counterparts` としてレコードに持たせる。
カードにも選択中の詳細にも「P.98 も表示」ボタンが出る。位置まで取れなかった場合は「（位置不明）」と添える。

ハイライトの座標は**書き出し時にしか計算できない**（ビューアはPDF.jsで再照合しない）ので、
自分側の `highlight_boxes` と同じ経路（`locateQuoteHighlightBoxes`）でここでも計算しておく。

### 2.2 数値を手がかりにする（`counterpartNumberNeedles`）

「」付きの引用があれば、それを相手ページで照合する。しかし**数値の食い違いは「」を使わない**。
上の例のように値をそのまま書くので、引用だけでは相手側がページ止まりになる（62件中28件がこれだった）。

そこで、相手ページの記述より後ろにある数値を手がかりに使う。単位語が続く場合は付ける（`478,600 million yen`）。
**そのページで一意に決まるときだけ採る**。誤った場所を指すくらいならページだけの方がよい。

> ⚠️ ここで一度踏んだ罠: 素朴に数字を拾うと「P.137」の `137` 自体を拾い、
> **P.137 のノンブルにハイライトが付いた**。しかもページ内で一意なので一意性の検査をすり抜ける。
> ページ表記の範囲を候補から除き、区切りも小数点も無い裸の整数は4桁以上に限ることで直した。

## 3. 測った結果

同一入力（1回の整合性レビュー・63件）で、書き出しデータを直接比較した。

| | 相手側cp | 位置まで特定 | ページ止まり |
|---|---|---|---|
| 数値手がかり無し | 62 | 34 | 28 |
| 数値手がかり有り（ノンブル混入） | 62 | 57 | 5 |
| **ノンブル除外後（確定）** | 62 | **49** | 13 |

新たに位置が付いた15件はすべて単位付きの実数値（`478,600 million yen` `35.2 hours` `49,130 tons` …）で、
失ったものは0件。座標は**y 8.8〜26.7%** に収まり、ノンブル帯（y≧88%）は0件だった。

自分側は **63件中63件がハイライト成功**（`highlight_status: ok`）。

## 4. REF側（比較資料）— 対象と同じ水準にした

当初は `files/reference_N.pdf#page=N` への外部リンクだけだった。別のPDFビューアが開いてレポートを離れ、
`reference_quote` の位置も出ない。校正モードでは指摘の根拠がREFにあるので、これでは**片側しか確認できない**。

**やったこと**

1. 書き出し時にREF側の座標も計算する（`attachReferenceHighlights`）。
   テキストレイヤーの取得（`getReportTextLayerIndex` / `getReportVisualLineIndex` / `locateQuoteHighlightBoxes`）に
   `source` を足し、対象PDFとREFを同じ経路で照合できるようにした。
   キャッシュキーに文書名を混ぜないと**REFのページが対象の結果を返す**ので注意。
2. REF PDFも分割Base64で同梱する（`buildReportReferencePdfPayloadFiles`）。
   `files/reference_N.pdf` を置くだけでは `file://` から `fetch` できず**ビューアから読めない**。対象PDFと同じ理由。
   生PDFは残さず置き換えた（残すと容量が二重になる）。
3. ビューアはカードの「比較資料 P.N を表示」で同じ枠内にREFを描画し、`reference_quote` を矩形で示す。
   「校正対象に戻る」を必ず添える。REF表示中はハイライトもREF側の座標を使う（`viewRefIndex`）。

**測った結果**（校正 幅10・20パケット・指摘88件・REFは201ページの日本語原文）

| | 件数 |
|---|---|
| REFを根拠にした指摘（`reference_pages` と `reference_quote` の両方あり） | 64 |
| **REF側の位置まで特定** | **64（ページ止まり0）** |
| 対象側のハイライト成功 | 80 / 88 |

ZIPは 5.58MB → **6.88MB**（201ページのREF込み）。Base64は約1.33倍になるがdeflateで戻るので、
生PDFを同梱していた頃と大きくは変わらない。

実Edgeで、対象 → REF → 対象と往復して確認した。往復後の対象の描画は初回と**画素単位で一致**する。

> ⚠️ モデルが挙げたページに `reference_quote` が無い場合がある（表レイアウトのずれ・ページ取り違え）。
> REFが200ページ以内のときだけ全ページ探しに行き、見つかれば `ok-other-page` として「別ページで一致」と出す。

## 4b. 残った欠陥: マスク復元が別表記を当てる

校正モードで対象側が8件ハイライトできなかった。**8件とも同じ原因**である。

Copilotの生回答は `⟦#RUK⟧ Supplementary Schedules (continued) — Schedule of Long-term Borrowings`。
本文は `15 Supplementary Schedules (continued) — …` だが、復元後の quote は **`15.0 Supplementary…`** になっていた。

`15` と `15.0` は同じ実数量なので同じ記号になる。復元（`unmaskFragment`）は
**「その言語で最初に見た表記」**を当てるので、`15.0` を先に見ていると `15` の側にもそれを書いてしまう。
結果、**文書に存在しない引用がレポートに出て、ハイライトも当たらない**。

直すなら、照合が失敗したときに同じ記号の他の表記も試す（辞書は書き出し時点で生きている）。
9%（8/88）が失われているので優先度は低くない。REFとは別件なので今回は手を付けていない。

## 5. 計測用に足したフック

`window.__koseiBenchmark.reportHighlights()` は、ハイライト付きの書き出しデータを返す。

**なぜ必要か**: CDP から `click()` してもユーザー操作扱いにならず、
**Edgeが2回目以降のダウンロードを黙って捨てる**。ZIPを落とさずに照合結果だけ測るための口である。
`Page.setDownloadBehavior` も `Browser.setDownloadBehavior` も効かなかった。
1回目だけは落ちるので、ZIPそのものを見たいときはページを開き直すこと。

## 6. 途中で踏んだ計測ミス（記録）

- **保存済み回答を手で取り込んで測った**ら、引用に `⟦#EAE⟧` が残り「50/88がハイライト不可」と出た。
  原因は製品ではなく手順。`restoreMaskedFindings` は `jobMasker` が無いと素通りするので、
  ジョブを介さない取り込みでは記号が戻らない。**マスク辞書はジョブごとの使い捨てなので再現できない。**
  実ジョブで測り直したら記号残りは0件だった。
- **非表示のブラウザペインで測った**ら「ハイライト0件」に見えた。描画が止まっていただけで、
  実Edgeでは自分側も相手側も正しく矩形が出た。**ビューアの見た目は実Edgeで確かめること。**
- python の text モードで `index.html` を書き戻し、**全体をCRLFに変換**してしまった。
  `Test-IndexHtmlSyntax.mjs` が `<script type="module">\n` を探すので落ちる。バイナリで読み書きすること。
