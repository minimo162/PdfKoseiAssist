# 引き継ぎ書 2026-08-06 — 指摘レポートの「該当箇所へ飛べるか」

前日（[HANDOVER_20260805.md](HANDOVER_20260805.md)）の続き。この日はモデルへの指示は触っていない。
**書き出した指摘レポートから、指摘の両側（自分側と相手側）を確認できるか**だけを扱った。

## 1. 何が問題だったか

整合性レビューの指摘は「離れた2箇所が食い違う」という対である。
ところがレポートのレコードは**片側（page / quote）しか持っていない**。相手側は理由文の中にしかない。

> P.96では当期のorders receivedを478,600 million yenとしており、P.6の476,800と一致しない。

実測（200ページ・63件）で **63件中57件が理由に相手ページ `P.N` を含んでいた**。
それなのにレポートから飛べるのは自分側だけで、相手ページは利用者が手で探すことになっていた。
2箇所を見比べるのが整合性レビューの仕事なので、これは機能として欠けている。

## 2. 入れたもの

### 2.1 相手側へのジャンプ（`attachCounterpartHighlights`）

書き出し時に理由文から相手ページと相手側の位置を割り出し、`counterparts` としてレコードに持たせる。
カードにも選択中の詳細にも「P.98 も表示」ボタンが出る。位置まで取れなかった場合は「（位置不明）」と添える。

ハイライトの座標は**書き出し時にしか計算できない**（ビューアはPDF.jsで再照合しない）ので、
自分側の `highlight_boxes` と同じ経路（`locateQuoteHighlightBoxes`）でここでも計算しておく。

### 2.2 数値を手がかりにする（`counterpartNumberNeedles`）

「」付きの引用があれば、それを相手ページで照合する。しかし**数値の食い違いは「」を使わない**。
上の例のように値をそのまま書くので、引用だけでは相手側がページ止まりになる（62件中28件がこれだった）。

そこで、相手ページの記述より後ろにある数値を手がかりに使う。単位語が続く場合は付ける（`478,600 million yen`）。
**そのページで一意に決まるときだけ採る**。誤った場所を指すくらいならページだけの方がよい。

> ⚠️ ここで一度踏んだ罠: 素朴に数字を拾うと「P.137」の `137` 自体を拾い、
> **P.137 のノンブルにハイライトが付いた**。しかもページ内で一意なので一意性の検査をすり抜ける。
> ページ表記の範囲を候補から除き、区切りも小数点も無い裸の整数は4桁以上に限ることで直した。

## 3. 測った結果

同一入力（1回の整合性レビュー・63件）で、書き出しデータを直接比較した。

|---|---|---|---|
| 数値手がかり無し | 62 | 34 | 28 |
| 数値手がかり有り（ノンブル混入） | 62 | 57 | 5 |
| **ノンブル除外後（確定）** | 62 | **49** | 13 |

## 4. REF側（比較資料）— 対象と同じ水準にした

当初は `files/reference_N.pdf#page=N` への外部リンクだけだった。別のPDFビューアが開いてレポートを離れ、
`reference_quote` の位置も出ない。校正モードでは指摘の根拠がREFにあるので、これでは**片側しか確認できない**。

**やったこと**

1. 書き出し時にREF側の座標も計算する（`attachReferenceHighlights`）。
   テキストレイヤーの取得（`getReportTextLayerIndex` / `getReportVisualLineIndex` / `locateQuoteHighlightBoxes`）に
   `source` を足し、対象PDFとREFを同じ経路で照合できるようにした。
   キャッシュキーに文書名を混ぜないと**REFのページが対象の結果を返す**ので注意。
2. REF PDFも分割Base64で同梱する（`buildReportReferencePdfPayloadFiles`）。
   `files/reference_N.pdf` を置くだけでは `file://` から `fetch` できず**ビューアから読めない**。対象PDFと同じ理由。
   生PDFは残さず置き換えた（残すと容量が二重になる）。
3. ビューアはカードの「比較資料 P.N を表示」で同じ枠内にREFを描画し、`reference_quote` を矩形で示す。
   「校正対象に戻る」を必ず添える。REF表示中はハイライトもREF側の座標を使う（`viewRefIndex`）。

**測った結果**（校正 幅10・20パケット・指摘88件・REFは201ページの日本語原文）

| | 件数 |
|---|---|
| REFを根拠にした指摘（`reference_pages` と `reference_quote` の両方あり） | 64 |
| **REF側の位置まで特定** | **64（ページ止まり0）** |
| 対象側のハイライト成功 | 80 / 88 |

ZIPは 5.58MB → **6.88MB**（201ページのREF込み）。Base64は約1.33倍になるがdeflateで戻るので、
生PDFを同梱していた頃と大きくは変わらない。

実Edgeで、対象 → REF → 対象と往復して確認した。往復後の対象の描画は初回と**画素単位で一致**する。

> ⚠️ モデルが挙げたページに `reference_quote` が無い場合がある（表レイアウトのずれ・ページ取り違え）。
> REFが200ページ以内のときだけ全ページ探しに行き、見つかれば `ok-other-page` として「別ページで一致」と出す。

## 4b. マスク復元が別表記を当てる — 直した

校正モードで対象側が8件ハイライトできなかった。**8件とも同じ原因**である。

Copilotの生回答は `⟦#RUK⟧ Supplementary Schedules (continued) — Schedule of Long-term Borrowings`。
本文は `15 Supplementary Schedules (continued) — …` だが、復元後の quote は **`15.0 Supplementary…`** になっていた。

`15` と `15.0` は同じ実数量なので同じ記号になる。復元（`unmaskFragment`）は
**「その言語で最初に見た表記」**を当てるので、`15.0` を先に見ていると `15` の側にもそれを書いてしまう。
結果、**文書に存在しない引用がレポートに出て、ハイライトも当たらない**。

**直し方**: 表記は `masker.occurrences` に全部残っている。`unmaskFragmentVariants()` で
記号ごとの別表記を組み合わせた候補を作り、**取り込み時に**レコードへ持たせる
（辞書はジョブごとの使い捨てなので、書き出し時にはもう無い）。
照合が空振りしたら候補を順に試し、当たった表記を quote 自体にも書き戻す。
**本文にあった表記こそが正しい引用**だからである（`quote_restored_from` に元の復元結果を残す）。

| | 自箇所ハイライト |
|---|---|
| 修正前（88件） | ok 80 / **error 8** |
| 修正後（79件・別ジョブ） | **ok 79 / error 0** |

8件すべてが `15.0 …` → `15 …` に直り、救えなかったものは無い。
件数の 88→79 はCopilotの出力差であって、修正とは関係ない。

> ⚠️ 同じ欠陥が**比較資料の引用にも**出た。REF本文は `(1) 監視、(2) 予防、(4) 復旧` なのに
> `reference_quote` が `(001) 監視、…` になり、REF側が1件ページ止まりになっていた。
> `reference_quote` にも同じ候補処理を入れてある。
>
> こちらは**実ジョブでの前後比較を取れていない**。対象側とまったく同じ経路を通しているのと、
> 単体テスト（`Test-NumberMask.mjs` の日本語ケース）で候補にREF本文どおりの表記が入ることを
> 確かめたところまでである。次に校正を流したときに `reference_highlight_status` を見ること。
>
> ⚠️ 測り直せなかった理由: **Edgeが2回目以降のダウンロードを黙って捨てる**（5章）。
> 1回目だけは落ちるので、ページを開き直してから1回だけ書き出すこと。

## 5. 計測用に足したフック

**なぜ必要か**: CDP から `click()` してもユーザー操作扱いにならず、

## 6c. PDF→テキストが空白を落としていた（114箇所）

「今のやり方で問題ないか」を確かめるため、素材の原文（`long-fixture-content.mjs` の en文）が
抽出テキストにそのまま出るかを数えた。**134文中35文（26%）が出てこなかった。**
35件とも**空白の欠落だけ**で、文字化けはゼロだった。`consolidatedfiscal` が**114箇所**あった。

生item（`--dump-items`）を見ると原因が分かった:

```
"…in the current consolidated"  x=42.7  w=390.6   → 右端 433.3
" "                             x=433.3 w=0.0     ← 幅0の空白item
"fi"                            x=435.9 w=6.7     → 隙間 2.6pt
"scal year was 4,270."          x=442.6
```

`fi` の合字が別itemに割れ、その手前の空白が**幅0のitem**として入る。
組み直しは `if (!str.trim()) return null` で空白itemを捨てていたので、
残った隙間 2.6pt が閾値 3.5pt（＝文字高×0.35）を下回り、空白が入らなかった。

**空白itemは「ここに空白がある」という明示の合図なので、捨てずに使う**ように直した。
隙間からの推定より優先する。

| | 修正前 | 修正後 |
|---|---|---|
| 原文134文のうち抽出テキストに一致 | 99 | **134** |
| `consolidatedfiscal` の出現 | 114 | **0** |

> ⚠️ 合字（fi / fl / ffi）は**まともな組版のPDFなら必ず出る**。合成フィクスチャで
> 114箇所なので、実物の有価証券報告書でも同じだけ踏んでいたはずである。
>
> ⚠️ ハイライトは壊れていなかった。照合も同じ抽出を使うので**両側とも同じように
> 空白が落ちていた**からである。効いていたのはモデルの読みの側で、
> `consolidatedfiscal` のような語が quote に入っていた。

## 6e. ヘッドレスEdgeが片づいておらず、434プロセスまで増えていた

抽出を直したあとベンチを取り直そうとしたら「CDP応答タイムアウト」で落ちた。
調べたら **msedge が434プロセス**動いていた。内訳は
`kosei-maskaudit-*`（監査ツールのプロファイル）が90本と、その子プロセス。

`taskkill /F /T /PID <spawnしたPID>` は書いてあったのに効いていない。
**`--headless=new` は起動したプロセスが即終了して、本体が別の親にぶら下がる**ので、
spawn した PID を `/T` で辿っても本体が見つからない。

**プロファイルディレクトリで特定して落とす**ように直した（`tools/headless-cleanup.mjs`）。
プロファイルは実行ごとに一意（mkdtemp / PID付き）なので、利用者のブラウザや
Copilotのタブは巻き込まない。`taskkill /IM msedge.exe` は**やってはいけない**。

同じ書き方をしていた3箇所を全部このヘルパー経由にした:
`Audit-DocumentMask.mjs` / `Test-FixtureTextLayer.mjs`（テストで毎回走る） /
`build-long-fixture.mjs`。

片づけたら 434 → 29。修正後はテスト一式を回しても**残留0本**である。

> ⚠️ この型の不具合は静かに進む。増えている間は何も起きず、**次に何かが遅くなって
> 初めて気づく**。しかも症状（CDPタイムアウト）は原因と無関係に見える。
> ベンチが理由不明で落ちたら、まず `Get-CimInstance Win32_Process -Filter "Name='msedge.exe'"`
> の数を見ること。

| 抽出が遅い / 無限ループ | `--dump-page 12` と `pageText(12)` | 2.4秒 / **8ms**。無関係 |
| 画面が固まっている | 別のCDP評価が返るか | 返る。メインスレッドは生きている |
| **タブが背面** | `document.hidden` | **true** |

`Page.bringToFront` を投げた瞬間に P.12 → P.206 まで一気に進み、送信が始まった。

`validatePdfJsRenderablePage` は `page.render().promise` を待つ。**Chromium は背面タブの
描画を止めるので、この Promise が返らない。** ベンチは Copilot のタブを前面に出すため、
その裏でアプリのタブが背面に落ちると止まる。

> ⚠️ 症状が原因を指さない。ログは「P.12 で止まっている」と言うので抽出やそのページを疑うが、
> 実際にはどのページでも起きる（背面になった瞬間のページが記録されるだけ）。
> **`document.hidden` を最初に見ること。**
>
**直した**。`Run-Benchmark.ps1` に `Show-AppTab`（アプリのタブへ `Page.bringToFront`）を足し、
**loadTarget の前**と**レビュー開始の前**の2箇所で呼ぶ。

> ⚠️ 開始前の1箇所だけでは足りなかった。**読み込み（`handlePdfFile`）もページを描く**ので、
> 背面だとそこで止まる。実際、開始前だけに入れて背面から流したら
> 「校正対象を読み込み」の行すら出ずに止まった。

背面のまま流して確認した:

| | 修正前 | 修正後 |
|---|---|---|
| 読み込み | 返らない | **即座に完了** |
| パケット作成 | P.12 で5分以上停止 | **12秒で通過** |
| 通し | 落ちる | **ラウンド2まで完走**（recall 60.8% / precision 95.5%） |

製品側は触っていない。利用者は見えているタブで押すので、この経路は自動実行だけの問題である。

## 6g. 抽出を直したあとの基準（取り直し）

抽出（6c/6d）を変えるとモデルへ送るTEXTが変わるので、それ以前の測定値は基準にならない。
同じ採点条件（`--reachable 200 --no-ref`）で取り直した。

| | 抽出修正前 | 抽出修正後 |
|---|---|---|
| strict recall | 60.8% | 59.8% |
| precision | 91.2% | **95.8%** |
| 数値観点の未検出 | 5件（n005 n050 n070 n110b n070c） | **3件（n005 n070 n090）** |

recall はほぼ横ばい（1回ずつなので誤差の範囲）。precision は上がったが、これも1回では断定できない。
**3回とも取れなかった `n050` が取れた**のは収穫だが、これも1回の観測である。

> ⚠️ ここで言えるのは「**抽出を直して悪化していない**」までである。
> 良くなったと言うには回数が要る。

## 6h. 基準を3回で取り直した。ついでに**採点条件の誤り**が見つかった

今日の修正（抽出3件・`numbers_r2`・マスク復元）はすべて1回ずつでしか測っていなかったので、
`rounds2` を3回回した（各7分・計25分）。

### ⚠️ まず、私がずっと間違った条件で測っていた

`--reachable 200 --no-ref` だけで採点していた。これだと**整合性モードが担当しない
局所誤り（綴り11件・文法11件）が分母に残る**。未検出の内訳を型で数えて気づいた:

```
未検出 計34〜37件  n(数値)2〜3  m(用語)5  w(表記)4  L(局所)22 ← 3回とも22で一定
```

3回とも22件ちょうどというのは、振れではなく**構造的に取れないもの**を意味する。
中身を見たら綴り誤り（`recieves`）と文法誤りで、これは**校正モードの担当**である。
`--scope consistency` を付けると分母から外れる。

| | 誤った条件 | 正しい条件（`--scope consistency`） |
|---|---|---|
| recall 中央値 | 62% | **85.7%** |
| precision 中央値 | 96% | **96%** |

**今日の会話で私が報告した 56〜62% という数字はすべてこの誤りを含む。** 実力を大きく低く
見せていた。`Run-Benchmark.ps1` の案内文に `--scope consistency` を必ず付けるよう書き足した。
