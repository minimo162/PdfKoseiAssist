GitHub Actions は利用不可のため、検証はローカル Node 実行で代替した。

真の指摘を潰す危険が上回るため見送った（理由は §6 の表）。

## 2. 原因（コードで確認済み）

### 原因A: no-op ゲートが本番経路で無効化されている（#4 / #9 の直接原因）

`js/review-merge-core.mjs` は #104 で `deterministicNoise()`（`isNoOpSuggestion` = quote と suggestion が正規化後同一／`isSelfDuplicateAlternative`／`crossLanguageScaledSymbolSubset`）を
`partitionNumericFalsePositives` の前段ドロップとして追加した。

しかし `index.html:1076` が読み込むのは **`js/review-merge.mjs`（ファサード）** で、
ファサードは `export * from "./review-merge-core.mjs"` の後に **同名の `partitionNumericFalsePositives` / `isSelfContradictoryNumericFinding` / `runNumericImportTwoPass` を自前で再定義**している（`js/review-merge.mjs:325, 321, 342`）。
再定義側は `coreIsConclusiveNumericFalsePositive`（= base 実装）だけを呼ぶため、`deterministicNoise` は本番で一度も実行されない。

回帰テスト `tools/Test-NumericFalsePositiveRegression.mjs` は `../js/review-merge-core.mjs` を直接 import しているため、
**テストは通るのにアプリでは効かない**状態になっていた。

実測（本調査で実行）:

```
review-merge.mjs (app path)     kept= [F4, F9]  dropped= []
review-merge-core.mjs (wrapper) kept= []        dropped= [F4, F9]
```

なお #9 は数値証明側（`isConclusiveNumericFalsePositive`）では `false`（＝落ちない）と確認済みで、
no-op ゲートが唯一の網になっている。

### 原因B: alignment 表示の `Number(null) === 0`（全10件が「決定的検査」に見える）

`coerceFindings` は alignment が無いとき `alignmentScore` / `alignment_score` に **`null`** を入れる（`index.html:5828-5829`）。
表示側は `Number(finding?.alignment_score ?? finding?.alignmentScore)`（`index.html:7209` と `7263`）。
`null ?? null` は `null`、`Number(null)` は **0** で `Number.isFinite(0)` が真になるため、
alignment 情報が無い指摘まで **「決定的検査 alignment候補 / alignment 0.00」** と表示される。

貼り付けられた10件すべてにこのバッジが出ているのはこのバグによるもので、
「機械的に裏取り済みの指摘」に見えてしまう点が誤指摘の体感を悪化させている。

### 原因C: quote 再バインド後に no-op / 同一性を再検査していない

`exactSame`（quote と suggestion の完全一致）は `coerceFindings` 時点のモデル出力に対してだけ計算される（`index.html:5765`）。
その後 `chooseSourceBackedQuoteVariants`（`index.html:6425`）と `validateFindingQuoteEvidence`（`index.html:6327`）が
`finding.quote` を実文書の表記へ**書き換える**ことがあり、書き換えの結果 no-op になった指摘は誰も検査しない。
貼り付け結果の #4 / #9 に「quoteとsuggestionが完全に同一です」警告が出ていないのはこの経路と整合する。

### 原因D: カテゴリ別の「主張の実在確認」が無い

`name_mismatch` は `TARGET_ONLY_REFERENCE_CATEGORIES` に入っているだけで、
**主張された名称差が quote と reference_quote の間に実在するか**は検証していない（`index.html:6356`）。
#4・#5 のように「名称が一致していない」と書きながら両側の名称が一致している指摘を止められない。
四半期表記（`Q1` / `1Q` / `第1四半期`）の同値正規化も存在しない（#5）。

### 原因E: 非文ブロックへの grammar 指摘にブロック role ゲートが無い

ローカル決定的検査 `detectFinitePredicateGap` は `paragraph|prose` 以外を除外している（`js/structural-checks.mjs:70-72`）が、
モデル出力の grammar 指摘には同じゲートが無い。#3・#6・#8 のような表ラベル／箇条書きの短縮形に
「述語欠落」「語形誤り」を high/medium で出せてしまう。

### 原因F: 決定的候補が全フィルタの後段で追加される

`buildDeterministicImportFindings()` の結果は `incoming.push(...)` で**すべてのフィルタ通過後**に足される（`index.html:6693-6699`）。
将来この経路が no-op 候補を作った場合、ゲートを一切通らずに一覧へ出る。

## 3. 修正案（優先度順）

### P1-1. ファサードの多重定義を解消する（原因A）
- `js/review-merge.mjs` の `partitionNumericFalsePositives` / `isSelfContradictoryNumericFinding` /
  `runNumericImportTwoPass` を、**wrapper（`review-merge-core.mjs`）の実装へ委譲**する形に変える。
  幅正規化・March FY 正規化はそのまま前処理として残し、判定本体だけ wrapper に渡す。
  最小変更なら、ファサード側 `isConclusiveNumericFalsePositive` の先頭で
  `core.isSelfContradictoryNumericFinding`（= deterministicNoise を含む）を呼ぶ。
- **落とし方は「削除」ではなく「除外」にする**: no-op と判定した指摘は
  `excludedReason = "no-op-suggestion"` を付けて除外一覧に残し、`EXCLUDED_REASON_LABELS` に
  「修正案が原文と同一（差分なし）」を追加する。silent drop は取りこぼしの検証ができなくなるため避ける。
- 回帰テストを `../js/review-merge.mjs`（本番と同じ入口）からの import に切り替え、
  `Test-NumericFalsePositiveRegression.mjs` に #4 / #9 の実データ形状を追加する。
  併せて「本番入口と wrapper の判定が一致すること」を検証するテストを1本足し、再発を防ぐ。

### P1-2. alignment 表示の null 取り違えを直す（原因B）
- `index.html:7209` / `7263` を
  `const raw = finding?.alignment_score ?? finding?.alignmentScore; const alignment = raw == null ? NaN : Number(raw);`
  に変更する（両方の描画関数で同一の共通関数へ切り出すのが望ましい）。
- 併せて、`deterministic_check` が空で alignment も無い指摘には「決定的検査」ボックス自体を出さない。
- `Test-ReportRender.mjs` に「alignment 未設定の指摘に決定的検査バッジが出ない」ケースを追加。

### P1-3. 検証後の no-op 再検査（原因C）
- `validateFindingQuoteEvidence` の**最後**（quote 書き換え・ハイライト確定後）に
  `quote` と `suggestion` の正規化比較を再実行し、同一なら `excludedReason = "no-op-suggestion"` を付ける。
- 「やること（instruction）」形式の suggestion（`suggestionKind` / `suggestion_kind` が置き換え文でないもの）も、
  引用中に既に存在するトークンだけを指示している場合は同じ扱いにする（#5 対策）。

### P2-1. name_mismatch / number_mismatch の実在確認（原因D）
- `name_mismatch` に決定的ゲートを追加する:
  quote と reference_quote から名称候補（ラテン文字列・型式・カタカナ語）を抽出し、
  正規化（大小文字・全半角・ハイフン・長音）後に **片側にしか無い名称が1つも無ければ**
  `excludedReason = "name-claim-unsubstantiated"` とする。
- 四半期表記の同値正規化を追加する: `Q1` / `1Q` / `第1四半期` を同一キーへ畳み、
  四半期差を根拠にした指摘は畳んだ後も差が残る場合だけ残す（#5）。
- 実装場所は `js/finding-quality.mjs`（純関数）＋ `index.html` からの呼び出しが既存構成と整合する。
  テストは `Test-FindingQuality.mjs` に追加。
- **実装は四半期表記の同値化のみに留めた**。名称抽出ゲートは、ローマ字とカタカナが対応する
  名称（Large / ラージ）を機械的に突き合わせられず、fail-open では #4 型を止められない一方、
  fail-close にすると真の名称誤りまで消す。#4・#5・#9 は no-op ゲート側で止まる。

### P2-2. 箇条書き・表ラベルへの grammar 指摘の抑制（原因E）
- quote が属する layout block の role（`getReportLayoutTextIndex` の `blockRanges[].role`）を指摘に持たせ、
  `table_cell` / `heading` / `list_item` かつ category が grammar のとき、
  severity を low に落として「文体（スライド短縮形）」として表示する。除外ではなく降格に留める。
- #6 のような「標準表記への統一」提案は残るが、high/medium から外れるため一覧の信頼度が上がる。

### P3-1. 箇条書き跨ぎ quote の警告（#2）
- `getReportLayoutTextIndex` は block 間には NUL 文字（U+0000）を挿入するが、
  **block 内の行間には区切りを入れず**、正規化で空白も落とす（`index.html:7918-7965`）。
  そのため隣接する箇条書き行を連結した quote が「厳密一致」として通る。
- 行境界（および行頭記号「・」「•」「-」）の位置を `lineRanges` として保持し、
  quote が行境界を跨いだ場合は `qualityWarning` に
  「複数行（箇条書き項目）をまたいだ引用です。原文の項目区切りを確認してください」を付ける。
- さらに、**削除を伴う修正案**（suggestion が quote の真部分文字列）で行境界跨ぎのものは
  `needsHumanReview = true` を強制する。#2 の「subordinated loan を削除」がそのまま適用されるのを防ぐ。

### P3-2. 決定的候補もゲートを通す（原因F）
- `buildDeterministicImportFindings()` の結果を `incoming.push` する前に、
  no-op ゲートと `validateFindingQuoteEvidence` を通す（またはゲートを共通関数へ切り出し、両経路から呼ぶ）。

## 4. 影響とリスク

- P1-1 は **recall を下げる方向の変更**だが、落とすのは「修正案＝原文」で適用しても何も変わらない指摘に限られる。
  除外一覧に残す方式にすれば、取りこぼしの検証は従来どおり可能。
- P2-1 の名称ゲートは、ローマ字表記とカタカナ表記が対応する名称（例: Mazda6e / マツダ6e）を
  「差あり」と誤判定しないよう、対応表ではなく**正規化後の包含判定**で fail-open にする。
  判定できないときは指摘を残す（従来どおり）。
- P2-2 は降格のみで除外しないため、真の文法誤りを失わない。
- P1-2 は表示のみの変更で、判定ロジックには影響しない。

## 5. 未確認事項

- #1・#2・#3 の最終判定には**原本PDFの目視確認**が必要。本書の判定は貼り付けテキストと
  アプリの照合仕様（厳密一致しない quote は `quote-not-found` で除外される）からの推定。
- 実データの JSON（該当ジョブの回答）があれば、`alignment_score` が実際に未設定であることと
  #4 / #9 が no-op ゲートで落ちることを、そのまま回帰テストの fixture にできる。
