## 2. 根本原因

### 原因1（発生源）: マスカーが同じ実量に別の記号を振り、プロンプトが「記号が違えば別の値」と断定させている

- 整合性プロンプトは「記号が違えば別の値」（`index.html:12543`）と指示する。モデルは数値を見られないため、
  記号の違いはすべて「不一致」として報告される。
- 一方マスカーは、**スケール（億・百万・million）の推定に失敗すると、同じ表記 `584` に別の実量 → 別の記号**を振る。
  `NUMBER_MASKING_SPEC.md` §4.2d（`195,460` が P.35 では ×10⁶、P.4 の表では単位が届かず ×1）、
  §12.2（前書きを ja でマスクして `million` が効かない）と同型。
  要約文の `584億円`（明示スケール）と、表の `584`（単位見出しを継承できなかった裸のセル）は典型例。
- 復元（`unmaskFragment`）は記号ごとに「その言語で最初に見た表記」を戻すので、**両側とも `584` と表示される**。
  利用者には「同じ値なのに不一致」と見える。

### 原因2（取りこぼし）: 既存の同値ゲート `isUnmaskedIdenticalNumericMismatchFinding` の抽出が狭い

`index.html:6763-6773`:

```js
const pairRe = new RegExp(`${numberSource}\\s*(?:と|vs\\.?|versus|and)\\s*${numberSource}`, "gi");
// 加えて、数値が4個以上・偶数個で前半＝後半の列のときだけ一致とみなす
```

- 対の判定は「**数値＋と＋数値**」が隣接しているときだけ。`要約の584と表の584` のように
  **2つ目の数値の前に場所の修飾語（表の・日本語版の・P.13の）が入ると一致しない**。
  プロンプトの雛形（「P.5の営業利益100とP.13の95」）自体がこの形を誘導しているため、実際の出力ではむしろこちらが多い。
- 列判定は数値4個以上のときだけなので、**1対1（2個）の比較は列判定でも拾えない**。
- 括弧の負値 `(579)` は `numberSource` に括弧が無く、`(579) と日本語版の (579)` は対判定にも列判定にも掛からない。
- 既存テスト `tools/Test-Issue126Regression.mjs:30-47` は隣接形（`500と500`、`347と347`）と4値の列しか持たず、
  修飾語入りの形が一度もテストされていない。

### 原因3（遮断）: `maskedSymbolsIncompatible` が「単位推定の失敗」と「本物の単位誤り」を区別できない

- `restoreMaskedFindings`（`index.html:6715-6723`）は、quote と reference_quote の記号が `areSymbolsCompatible`
  で重ならなければ `maskedSymbolsIncompatible = true` を立て、`isUnmaskedIdenticalNumericMismatchFinding`
  と `isConclusiveNumericFalsePositive` の両方がこれを見て**必ず残す**（#152: `48 thousand` ⇔ `48百万` は本物の誤り）。
- しかし原因1の幻の不一致も、記号の実量が違う（×10⁸ と ×1）ので**同じく「非互換」になる**。
  つまり原因2の正規表現を直しても、`reference_quote` に記号が入っている S1/S3 型は #152 の保護で残り続ける。
- 区別に必要な情報（その出現のスケールが**明示**されたものか、**推定・未付与**か）はトークナイザが
  `explicitScale` / `unambiguousScale` として持っている（`js/number-mask-base.mjs:1140, 1213`）が、
  `Masker.mask()` が出現記録を作るとき（`js/number-mask-base.mjs:1475-1476`）に**捨てている**。
  そのため取り込み側は「片側だけ単位が付いていた」ことを確かめられない。

### 原因4（範囲）: 数値の同値証明が numeric カテゴリ・TARGET/REF ラベル・`reason` 欄に限られている

- `isExplicitTargetReferenceSameValueClaim`（`js/review-merge.mjs:442-454`）は `reason` / `model_reason` しか読まず、
  ラベルも `TARGET|対象原文|原文|REF|比較資料|参照` だけ（`:354`）。`要約の` `表の` `英語版の` `日本語版の` は認識しない。
  `suggestion` / `issue_summary` も読まない。さらに出典本文が結び付いた指摘（同一文書の整合性はほぼこれ）では
  `hasSourceBoundContext` で最初に抜ける（`:444`）。
- base 側（`js/review-merge-core-base.mjs`）は1対1の裸の数値ペアを意図的に残す
  （`:5569 if (quote.length === 1 && reference.length === 1) return false;`）。指標名の一致か同じ保護記号が要る。
- `translation_consistency` は category としては `NUMERIC_CATEGORIES`（base `:29`）にも
  `NUMERIC_MISMATCH_CATEGORIES`（`js/review-merge.mjs:348`）にも入っておらず、`issue_scope` の正規表現でだけ扱われる。
  category が `translation_consistency` の数値指摘（S3）は数値ゲートの入口で対象外になる。

### 注意: 「主張が同値」は「誤りが無い」を意味しない（実データ F0040 / F0041）

`app/_app/tools/fixtures/review-merge-live-q4-0840-f0040.json`（F0041 も同型）:

```
quote:           Balance at April 1, 2024 283,957 193,847 73,729 509,578 (1,868) 1,059,243
reference_quote: 当期首残高 283,957 193,847 73,729 267,576 509,578 509,578 △1,868
suggestion:      資本金の期首残高「283,957」を日本語版の「283,957」と照合して修正する。
```

モデルが挙げた値（283,957 ⇔ 283,957）は同じだが、**行の数値列には本当に差がある**（`267,576` が英文側に無い）。
`Test-ReviewMerge.mjs:2478`「実export F0040/F0041は先頭列同値でも実source vector差をKEEP」がこれを固定している。
したがって**自由文の主張だけで除外してはいけない**。除外できるのは、quote / reference_quote（または出典行）の
数値列にも差が無い場合だけで、差があるなら「主張値の書き方が誤っている真の指摘」として残し、表示を直すべきである。

### 原因5（no-op ゲートの設計上の除外）

- `isNoOpSuggestionFinding` は「確認・どちら・check」を含む指示を **no-op 判定の対象外**にしている
  （`js/finding-quality.mjs:1021, 1097`、#151）。確認対象の値を「」で引くのは普通なので、それ自体は正しい。
- ただし no-op ゲートは quote と suggestion しか見ないので、**「AとBのどちらが正しいか」のAとBが同じ**という
  自己矛盾は、もともとこのゲートの守備範囲外。原因2のゲートが唯一の網になっている。

> まとめ: **発生源はマスキングの記号割れ（原因1）**。それを止める唯一の後段ゲートが
> **修飾語入りの言い回しを拾えず（原因2）**、拾えたとしても **#152 の保護が幻の不一致まで守ってしまう（原因3）**。
> 数値ゲート側は1対1の裸の数値を意図的に残す設計で（原因4）、no-op ゲートは確認指示を対象外にしている（原因5）。

## 3. 改善案

優先度は「誤指摘を止める効果」÷「真の指摘を消す危険」。**除外は silent drop にせず、必ず `excludedReason`
付きで除外一覧に残す**（2026-08-24 の方針を踏襲）。真の誤りを潰す恐れがあるものは除外ではなく降格＋要確認にする。

### P1. 同値主張の抽出を「場所の修飾語つき」に広げる（原因2）

- 対象: `app/_app/index.html` の `isUnmaskedIdenticalNumericMismatchFinding`（`:6753`）。
  純関数として `app/_app/js/finding-quality.mjs` へ移し（例: `extractClaimedValuePairs(text)` と
  `isSelfIdenticalValueClaim(finding)`）、index.html からは import して呼ぶ。テストが `extractFunction` で
  HTML を切り出す必要がなくなる。
- 抽出規則:
  - 「**〈場所〉の〈数値〉と〈場所〉の〈数値〉**」: 2つ目の数値の前に、最大 ~20 字の非数字の修飾句
    （`表の` `日本語版の` `P.13の` `REF側の` `本文の営業利益`）を許す。例:
    `(?<a>NUM)\s*(?:と|vs\.?|versus|and)\s*(?:[^\d\s、。]{1,20}?(?:の|で|における)\s*)?(?<b>NUM)`
  - `NUM` は括弧付き負値と △/▲ を含める: `[△▲+＋\-−]?\(?\d[\d,，]*(?:\.\d+)?\)?`。
  - 比較キーは「符号・桁区切り・全角を正規化した値」。**符号の表記差（`(579)` と `△579`）は同値**、
    **符号の有無の差（`579` と `(579)`）は別値**。
  - 「〜と〜のどちらが」「〜と〜を整合させ」「〜と〜で異なる」「〜と〜が一致しない」を対象にする。
  - 構造番号の除外（`FY2026` `P.13` `第3四半期` の数字は値として数えない）は `review-merge.mjs` の
    `CLAIM_STRUCTURAL_BEFORE_RE` / `CLAIM_STRUCTURAL_AFTER_RE` と同じ規則を使う。
- 判定: 主張中の**全ての対が同値**で、かつ異なる値の対が1つも無いときだけ真。1つでも `500と600` があれば偽。
- **数値列ガード（必須）**: 自由文の主張が同値でも、quote と reference_quote の**両方**に数値があり、
  符号・桁区切り・全角を正規化した数値の多重集合が一致しない場合は**除外しない**（F0040 / F0041 型）。
  出典行（`targetRowText` / `referenceRowText`）が結び付いているときはそちらで比べる。
  この場合は除外の代わりに `needsHumanReview = true` とし、`qualityWarning` に
  「指摘文に挙げた値は両側で同じです。食い違いは同じ行の別の値にある可能性があります」を付ける。
  片側しか数値を持たない（reference_quote が空の整合性指摘など）ときはガードを通過扱いにする。
- 受け入れ基準:
  - S1・S2・S3・S3′（`(579)` ⇔ `△579`）が `true`。
  - `500と600が不一致`、`要約の584と表の548`、`英語版の 579 と日本語版の (579)`（符号差）が `false`。
  - 既存 `Test-Issue126Regression.mjs` / `Test-Issue152Regression.mjs` の全ケースが変わらず通る。
  - F0040 / F0041 fixture は除外されず、上記の警告付きで残る（`Test-ReviewMerge.mjs:2478` も通る）。

### P2. 記号割れの痕跡を出現記録に残し、#152 の保護と両立させる（原因3）

- 対象: `app/_app/js/number-mask-base.mjs`
  - `Masker.mask()` の出現記録（`:1475-1476`）に、トークナイザが持つ `explicitScale` / `unambiguousScale` を保存する。
  - 新メソッド `Masker.describeSymbolSplit(symbolA, symbolB)` を追加:
    両記号の出現の `raw`（数字部分を正規化したもの）が一致し、実量の差が 10 の 3/4/6/8/9/12 乗だけで、
    **少なくとも片側の出現がすべて `explicitScale === false`**（スケールを推定・未付与）なら
    `{ kind: "inferred-scale-split" }` を返す。両側とも明示スケールで食い違うなら `{ kind: "explicit-scale-conflict" }`。
- 対象: `app/_app/index.html` `restoreMaskedFindings`（`:6715-6723`）
  - 非互換のとき、`describeSymbolSplit` の結果を `maskedSymbolSplit` として指摘に残す。
  - `explicit-scale-conflict` のときだけ従来どおり `maskedSymbolsIncompatible = true`（#152 を保護）。
  - `inferred-scale-split` は `maskedSymbolsIncompatible` を立てず、`maskedScaleUncertain = true` とする。
- 対象: `isUnmaskedIdenticalNumericMismatchFinding`（P1 で移した関数）
  - `maskedScaleUncertain` で、P1 の同値主張が成立すれば `excludedReason = "unmasked-identical-numeric-mismatch"`。
  - 除外理由の表示は既存ラベル「数値を元に戻すと同じ値だった」を使い、詳細欄に
    「片側の単位（億円・百万円など）を自動で読み取れなかった可能性があります。原本の単位見出しを確認してください」を出す。
- 受け入れ基準:
  - `Test-Issue152Regression.mjs` の `48 thousand yen` ⇔ `48百万円`（両側明示）は **従来どおり残る**。
  - 新ケース: 要約 `売上高は584億円` と、単位行を継承できない表セル `584` を同じ `Masker` に通し、
    両者の記号をそれぞれ quote / reference_quote に入れた指摘 → `maskedScaleUncertain === true` で、
    S1 の suggestion なら除外一覧へ移る。
